# 编码与压缩的下界

## 1. 从一个场景开始

一份 100 MB 的原始传感器日志，ZIP 一压只剩 30 MB。工程师自然要问：还能再压吗？压到 5 MB 行不行？有没有一条"物理定律"宣布到此为止？

有。香农的信源编码定理宣告：**无论发明多聪明的算法，无损压缩的平均码长不可能低于信源的熵**。熵不是某个算法的弱点，是信息本身的密度。这一课先学会造"好码"，再亲眼确认谁也越不过那条红线。

## 2. 直觉解释

给符号编二进制码，核心思路一句话：**常见的给短码，罕见的给长码**——就像中文里"的"一笔都不省不得，而"饕餮"写慢点没人怪你。

但变长码有个陷阱：收到 `0 10`，该切成 `0|10` 还是 `01|0`？若 A=0、B=01，那 B 开头的任何码都让解码员精神分裂。出路是**前缀码**：任何码字都不是另一个码字的开头。满足这个条件的码对应一棵二叉树——左转记 0 右转记 1，所有符号都住在叶子上（叶子上不可能再有岔路，天然互不为前缀）。

而最优的前缀码怎么造？哈夫曼（1952 年，课程作业变成传世经典）给出贪心算法：**每次把概率最小的两个节点捆在一起**，反复合并直到只剩根，再从根往回读出每个符号的码长。

## 3. 正式定义

对概率为 $p_1,\ldots,p_n$ 的信源，编码给每个符号分配长度 $l_i$：

$$\text{平均码长 } L=\sum_{i=1}^{n} p_i\, l_i, \qquad \text{下界 } H=-\sum_{i=1}^{n} p_i \log_2 p_i \le L < H+1$$

| 符号 | 名字 | 含义 |
| --- | --- | --- |
| $l_i$ | 码长 | 第 $i$ 个符号的二进制位数 |
| $L$ | 平均码长 | 每个符号平均占用多少比特 |
| $H$ | 信源的熵 | 压缩的理论地板（上一课的主角） |
| $<H+1$ | 上界 | 哈夫曼码至多比熵多 1 比特/符号 |

中间那句不等式就是**信源编码定理**的逐符号版本：熵是最优平均码长的下界，任何无损前缀码都不能低于它；定理又保证存在好码从上方逼近它。当且仅当所有 $p_i$ 恰为 2 的负幂时，哈夫曼码能精确踩到 $L=H$。

## 4. 分步例题

**例**：信源四种符号 甲 0.4、乙 0.35、丙 0.15、丁 0.1。手工造哈夫曼码。

1. 挑最小的两个：丙 0.15 与 丁 0.1 合并成节点 0.25；
2. 再挑最小的两个：甲 0.4 与……不对，当前最小是乙 0.35 与新节点 0.25，合并成 0.6；
3. 最后剩 甲 0.4 与 0.6，合并成根 1.0；
4. 从根回读：甲走一步 → 码长 1；乙两步 → 2；丙三步 → 3；丁三步 → 3；
5. 算平均码长：$L=0.4\times1+0.35\times2+0.15\times3+0.1\times3=1.85$ 比特/符号；
6. 对照下界：熵约 1.802，差距 0.048 ✓ 落在 $(H,\ H+1)$ 内。

定长码需要 $\lceil\log_2 4\rceil=2$ 位，哈夫曼把它压到 1.85——省的不多，但乘上每天十亿条消息就是真金白银。

## 5. 动手实验

### 实验 1（viz）：频率不均才是压缩空间

```viz
{
  "type": "datachart",
  "title": "四符号的出现频数：偏得越狠，压得越多",
  "labels": ["甲", "乙", "丙", "丁"],
  "values": [8, 4, 2, 2]
}
```

这份 16 条记录里"甲"占一半、"丁"只占八分之一。定长码一视同仁每人 2 位；聪明码把甲的份额兑换成短码——柱子高差越大，可省的钱越多。若四根柱子一样高（均匀分布），任何变长码都无利可图，这正是"熵即下界"的几何解释。

### 实验 2（python）：亲手实现哈夫曼贪心

```python title="迷你哈夫曼：合并、回读、对照熵"
import math   # log2 用于算下界

probs = [0.4, 0.35, 0.15, 0.1]        # 符号概率
names = ["甲", "乙", "丙", "丁"]

nodes = []                             # 每个节点记 [总概率, 成员名单]
for i in range(len(probs)):
    nodes.append([probs[i], [names[i]]])

lengths = {}                           # 字典：符号名 -> 码长
while len(nodes) > 1:
    nodes.sort()                       # 嵌套列表排序按首元素（概率）从小到大
    small1 = nodes.pop(0)              # pop(0)：取走并删除最小的节点
    small2 = nodes.pop(0)              # 再取第二小的
    members = small1[1] + small2[1]    # 两族成员合并名单
    for name in members:
        lengths[name] = lengths.get(name, 0) + 1   # get：键不存在时返回默认值 0
    nodes.append([small1[0] + small2[0], members]) # 新节点的深度全体加一已由循环记账

avg_len = 0                            # 加权平均码长
for p, name in zip(probs, names):      # zip：并行配对两个列表（首见）
    avg_len = avg_len + p * lengths[name]

h = 0                                  # 熵下界
for p in probs:
    h = h - p * math.log2(p)

print(f"各符号码长 {lengths}")
print(f"哈夫曼平均码长 {round(avg_len, 3)}")
print(f"熵下界 {round(h, 3)}")
```

输出 1.85 对 1.802，与手工例题完全一致。改改 `probs` 再跑：换成 `[0.25]*4`（均匀），你会看到码长全是 2 且 $L-H$ 归零附近徘徊——均匀世界里没有免费午餐。

### 快问快答

```quiz
为什么码表 {A: 0, B: 01} 不是合法的前缀码？
- 因为 0 比 01 短
- 因为 01 的开头包含码字 0，解码时无法切分 [*]
- 因为两位码太长了
? 前缀条件要求任何码字都不是别的码字的开头。A=0 抢占了 01 的第一位，收到 01 时解码器永远不知道该在一位后就刹车还是继续等。
```

:::warning[常见误区]

**误区一**："你以为 ZIP 达到了熵。" 远没有。ZIP（DEFLATE）用的是 LZ77 + 哈夫曼的组合拳，对付的是相邻字节的相关性；它通常显著高于一阶熵。更先进的算术编码、PPM 能贴得更近，但"低于熵"依然被数学禁止。

**误区二**："你以为压缩软件'创造'了空间。" 无损压缩只是**重新记账**：把统计冗余挤掉，一个比特都没丢。有损压缩（JPEG、MP3）才真正扔信息——它赌的是人类感知不在乎某些比特。

**误区三**："你已经压缩过的文件再压一遍还能省一半。" 已压缩数据的分布接近均匀（这正是压缩的目的），熵几乎顶满，再压只会原地踏步甚至因文件头反而变大。"二次压缩"神话可以退休了。

:::

## 6. 练习

**练习 1**：码表 甲=0、乙=10、丙=110、丁=111，消息共 16 个符号，频数为 8、4、2、2。求平均码长。下面的代码能跑但按定长码算了账——改到通过：

```exercise
# @title: 练习：变长码的平均账单
# @check: 1.75
# @hint: 平均码长是「每个符号的码长 × 频数」加起来除以总数；len(code) 能量出一个码字的位数
codes = {"甲": "0", "乙": "10", "丙": "110", "丁": "111"}   # 字典：名字 -> 码字
counts = {"甲": 8, "乙": 4, "丙": 2, "丁": 2}

total_bits = 0                       # 总比特数累加器
total_syms = 0                       # 总符号数累加器
for name in codes:
    total_bits = total_bits + 2 * counts[name]   # ← 问题在这：人人按定长 2 记账
    total_syms = total_syms + counts[name]

print(total_bits / total_syms)
```

<details>
<summary>点开查看判题参考实现</summary>

```python
codes = {"甲": "0", "乙": "10", "丙": "110", "丁": "111"}   # 字典：名字 -> 码字
counts = {"甲": 8, "乙": 4, "丙": 2, "丁": 2}

total_bits = 0
total_syms = 0
for name in codes:
    total_bits = total_bits + len(codes[name]) * counts[name]
    total_syms = total_syms + counts[name]

print(total_bits / total_syms)
```

把固定的 `2` 换成每个码字自己的长度 `len(codes[name])` 即可。

</details>

**练习 2**：上题的四个频数恰好是 8、4、2、2（占比 1/2、1/4、1/8、1/8）。验证此例中 $L=H$，并说明原因。

<details>
<summary>点开查看逐步解答</summary>

$L=(8\times1+4\times2+2\times3+2\times3)/16=28/16=1.75$。熵 $H=\frac{1}{2}\cdot1+\frac{1}{4}\cdot2+\frac{1}{8}\cdot3+\frac{1}{8}\cdot3=1.75$——分毫不差！原因是每个概率都是 2 的负幂，码长恰等于自信息 $-\log_2 p_i$，定理的下界被精确踩到。这样的分布叫"完美哈夫曼分布"，工程上可遇不可求。

</details>

**练习 3**：英文字母若等概率，每字母需 $\log_2 26\approx 4.7$ 比特；香农估算真实英语每字母只含约 1 出头比特的真信息。两者之间的差距叫什么？压缩软件能全部吃掉吗？

<details>
<summary>点开查看逐步解答</summary>

差距约 3.7 比特/字母，其中大部分是语言的结构冗余：字母搭配习惯（q 后面几乎必是 u）、词与语法约束。逐符号编码（本课的哈夫曼）只能吃到"单字母频率不均"那一小层；想逼近 1 比特的极限，必须建模上下文相关性——这正是现代压缩器用上下文混合、神经网络语言模型干的事。压缩极限的每一次逼近史，就是一部"对语言建模能力"的进步史。

</details>

## 7. 选读：哈夫曼 vs 算术编码

<details>
<summary>选读 · 为什么 JPEG2000 抛弃了哈夫曼</summary>

哈夫曼码长必须是整数，这是它天生的税：概率 0.3 的符号理想码长 $-\log_2 0.3\approx 1.74$ 位，却只能付 1 或 2 位。符号单独看损失不大，但每个符号最多浪费近 1 位，对小字母表很伤。算术编码另辟蹊径：把整条消息编码成一个 [0,1) 区间里的小数，各符号按概率瓜分区间长度，累计精度可以无限细分——整数限制消失，实际码长能任意贴近熵（差距只剩许可协议和专利史上的恩怨）。直觉总结：哈夫曼按"棵树"分房，户型只能取整；算术编码按"米尺"切地，想要多细切多细。

</details>
