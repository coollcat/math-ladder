# 符号计算与计算机代数

## 1. 从一个场景开始

在数学软件里输入根号二，它打印出精确的 √2；展开 $(x+y)^{35}$，它吐出一个三十五项的多项式，系数一个不差——其中有六位数的大家伙。第 44 章告诉我们机器里的数全是有舍入误差的浮点数，那这台机器凭什么敢自称"精确"？答案不是它算得更猛，而是它**根本没把根号二当成数**。

这就是计算机代数系统（CAS）：变量、根式、多项式是记忆里的对象，运算发生在它们的写法层面。本课拆开它的三条内部原则，并诚实交代一条天花板。

## 2. 直觉解释

浮点计算像**用现金付款**：每经一手就抹掉几毛零头，走得越远亏得越多。符号计算像**写账本**：

- 写下"√2"，账本里存的是两个字节的记号"根号+二"，不是某个近似值；
- 运算是改写记账方式：$(\sqrt{2})^2$ 按规则翻页成 2——翻页前后都是符号串，从未动用过小数；
- 直到最后一刻你才要求"兑换成数值"，误差只在最后一步产生一次。

于是符号对象"记得"自己是谁：$x^2-1$ 知道自己是差式的积，$\sqrt{x}$ 记得自己的来历——这份记忆正是精确性的来源。

## 3. 正式定义

CAS 内部有三条支柱原则：

| 原则 | 内容 |
| --- | --- |
| 树表示 | 表达式按运算优先级建成一棵树：叶子是数字与变量，内节点是运算符 |
| 规则库 | 一组受控的等价改写规则，如 $a+0 \to a$、$a \cdot 1 \to a$、$x+x \to 2x$ |
| 规范型 | 对同类表达式约定一种标准写法，逐项合并后用以比较是否同构 |

第三条最微妙。理想很美好："两个表达式恒等 ⇔ 化简成同一个规范型"。但判定**一般表达式的恒等**等价于判定其差是否恒为零：

$$E \equiv F \iff E - F \equiv 0,\qquad \text{后者的判定问题在足够广的表达式类上一般不可判定（Richardson 定理）}$$

所以任何 CAS 都只能在其覆盖的表达式类内做到"多数情况给出答案"；遇到把不透的硬骨头时，诚实的系统会把未化简的形式原样还给你——这不是无能，而是守规矩。

## 4. 分步例题

让一棵小表达式树走一遍流水线：输入 $T=(2x)+(3x)+(0y)$。

1. **建树**：顶层是两次加法嵌套，三个乘法叶子挂在下面；
2. **拍平求和项**：顺着加法边收集到三项系数对 $(2,x)$、$(3,x)$、$(0,y)$；
3. **点火规则**：乘零规则 $0y \to 0$ 划掉第三项；同类项规则把 $(2,x)$ 与 $(3,x)$ 合并成 $(5,x)$；
4. **重建规范型**：只剩 $5x$，没有更短的同构写法可选；
5. 全程没给 $x$ 赋过任何值——改动的是**式子的形**，而非某个数的大小。

对照实验预留在这里：同一个函数换两种代数写法，数学上恒等、命运却可能天差地别——下一节亲眼验证。

两条曲线肉眼无差别——**画图看不见的，账本看得见**。下面把大数场景交给浮点：

```python title="等价不等于同样可靠：让大整数与大数说话"
big = 10 ** 18 + 1              # ** 幂：Python 大整数精确存储每一位
approx = 1e18                   # 1e18 写法即浮点：只保约 16 位有效数字
print("整数世界:", big - 10 ** 18)

x = 100000000                          # 1e8：平方后正好踏进精度缝隙
bad = (x * x + 1) ** 0.5 - x           # 病态写法：两个庞然大物相减
good = 1 / ((x * x + 1) ** 0.5 + x)    # 有理化：分母变大，躲开相消
print("浮点世界:", approx - 1e18)
print("病态写法:", bad)
print("有理化写法:", good)
```

整数的 1 分文不少地回来了；浮点那行却是 0.0——充值的 1 已被舍入吞掉。同理病态写法的减法发生相消输出 0.0，有理化写法则老老实实报出约 5×10⁻⁹。**符号世界记得每个位次的来历，浮点世界只有十六张钱包位**。

### 实验 1：亲手拧一遍化简流水线

```python title="迷你 CAS：拍平、点规则、重建"
expr = ("+", ("*", 2, "x"), ("+", ("*", 3, "x"), ("*", 0, "y")))

def flatten(node, out):                 # 沿加法边收集 (系数, 符号) 对
    if isinstance(node, tuple):        # isinstance：判断对象的类型归属
        op, left, right = node         # 元组解包：一次取出三个成分
        if op == "+":
            flatten(left, out)
            flatten(right, out)
        else:
            if isinstance(right, str):
                out.append((left, right))
            else:
                out.append((right, left))

def simplify(tree):
    terms = []
    flatten(tree, terms)
    total_const = 0
    merged = {}
    order = []                         # 记录首次出现顺序，保持输出的稳定
    for coef, sym in terms:
        if sym == "":
            total_const += coef        # 纯数字叶汇入常数账
        elif coef == 0:
            continue                   # 乘零规则的触发点
        elif sym in merged:
            merged[sym] += coef        # 同类项合并
        else:
            merged[sym] = coef
            order.append(sym)
    parts = []
    for sym in order:
        parts.append("(" + str(merged[sym]) + "*" + sym + ")")
    if total_const != 0 or not parts:
        parts.append(str(total_const))
    return " + ".join(parts)           # join：用分隔串把列表缝成一个字符串

print(simplify(expr))
print(simplify(("+", ("*", 1, "a"), ("*", 4, "a"))))
```

两行输出分别是 `(5*x)` 与 `(5*a)`——分步例题的四步流程原样复现。真实的 SymPy 在这套骨架外多做了规范化排序、分数处理与上万条规则管理，但心脏就是这个节拍。

### 实验 2：修好多项式乘法的指数事故

展开 $(x+1)^3$ 的系数表 machinery 已就绪，只欠一步正确的次数记账。当前程序跑得起劲、结果却错得离谱——请修复 `poly_mul` 中标记的那一行。

```exercise
# @title: 练习：修复指数错乘的展开器
# @check: x^3 + 3x^2 + 3x + 1
# @check: [1, 3, 3, 1]
# @hint: 卷积公式来自分配律本身——第 i 位配第 j 位，贡献落在哪一位？次数应当相加还是相乘？
def poly_mul(p, q):
    res = [0] * (len(p) + len(q) - 1)    # 乘积最高次 = 两高次之和
    for i in range(len(p)):
        for j in range(len(q)):
            res[i * j] += p[i] * q[j]    # ← 问题在这：把幂当成了乘方
    return res

cur = [1]
for _ in range(3):                       # 连乘三次 (1 + x)，堆出立方
    cur = poly_mul(cur, [1, 1])

def poly_str(coefs):
    parts = []
    for d in range(len(coefs) - 1, -1, -1):
        num = coefs[d]
        if num == 0:
            continue
        if d == 0:
            parts.append(str(num))
        elif d == 1:
            head = str(num) if num != 1 else ""
            parts.append(head + "x")
        else:
            head = str(num) if num != 1 else ""
            parts.append(head + "x^" + str(d))
    return " + ".join(parts)

print(poly_str(cur))
print(cur)
```

修复一处（`i * j` 改为 `i + j`）后，输出即完全展开的标准形态——这正是各类 CAS 展开 $(x+1)^n$ 的内核循环。顺带回味初始版本的胡言乱语：指数一旦算错位置，machine 给出的仍是"一个多项式"，只是无人再认识它。

```quiz
某 CAS 无条件执行规则 sqrt(x^2) 化简为 x。这个化简在哪一类情形会出错？
- 从不出错，这是代数恒等式
- 当 x 取负数时出错：真实应得到 x 的相反数即绝对值 [*]
- 只在 x 是无理数时出错
? 开平方天生产出非负结果。规则库若不看变量的取值语境就套用等式，就会把绝对值悄悄压平——这正是符号推理必须携带条件信息的原因。
```

## 常见误区

:::warning[常见误区]

**误区一**："CAS 说'相等'就一定解决了等价判定。"
桌面级系统的"相等"通常是规范型的同构或符号引擎的有限尝试；超出能力范围它往往不吭声。涉及关键结论时，可以要求它走数值抽查交叉印证——把它当同事复核，而不是神谕宣判。

**误区二**："有了符号精确，浮点就该退役。"
两者的失败模式互补：符号怕条件遗漏（上面的绝对值陷阱），浮点怕灾难性消去。工程里的最优解常是"符号导出公式、数值批量出表"的双轨制。

**误区三**："化简结果的唯一形式当然存在。"
规范型只是人为约定。同一多项式可以按降幂排也可以因式分解排，不同系统甚至同一系统的不同函数给出的"最简"都可能不同——最简是个审美决定。

:::

<details>
<summary>点开查看逐步解答</summary>

$x^2=10^{32}$ 远超双精度 16 位量程之外的有效位，+1 完全蒸发，开方恰回落为 $10^{16}$，减法必然归零——**稳定地坏**源于结构：只要相消幅度超过保存位数，错误就无法被任何参数微调拯救。这解释了为何数值教材执着于教重排公式的手艺。

## 7. 选读：等价判定为什么难得出奇

<details>
<summary>选读 · 从 Richardson 定理到格罗布纳</summary>

Richardson 1969 年构造出一类含绝对值、指数与正弦的表达式，使"是否恒为零"编码了不可判定问题——所以不存在万能化简器，这不是工程短板而是逻辑边界。实践家们的回应各有梯队：多项式世界靠单变元唯一分解与多变元 Groebner 基把恒等问题做成可计算的机械流程；初等函数世界的策略是放宽目标——不求"判等"，只求"给足证据"，如高精度数值检核配合有限的符号约简。近年 AI 方向亦加入战局：让神经模型猜测恒等关系，再交回符号算法严格核实——猜的归模型，对的归机器，恰好是本章反复出现的分工。
</details>
