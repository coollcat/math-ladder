# Autoformalization 与数学语料

## 1. 从一个场景开始

一位研究者把刚读到的定理讲给形式化小组听："任何大于 1 的自然数都有素因子。"三分钟后机器拒绝了他的第一版翻译——他忘了把"大于 1"写进陈述；第二版通过了，又被审阅人指出"素因子"应引用库里现成的定义，而不是临时新造一个。原文一个字没改，形式语句却已返工两次。

把人类数学文本变成机器可核验的语句，这门手艺叫 autoformalization（自动形式化）。它是本章流水线的最后一环，也是 AI for Math 数据问题的总闸门：**没有大规模可靠的形式语料，前面所有的搜索与推理都无米下锅。**

## 2. 直觉解释

从自然语言到可用形式语句，中间隔着**两级失真**，像接力赛掉两次棒：

- **第一级：陈述翻译**。人类句子自带省略——量词的论域、"显然"背后的正则性条件、约定俗成的记号。"方程有解"在实数世界是假命题、在复数世界是真命题，机器没有默认世界，必须逼你站队；
- **第二级：库对齐**。就算陈述译对了，还得接上现有库的地基：用哪个版本的"整除"、哪一套实数构造。接错了，陈述自洽却与全库语义脱轨——像把自家电线焊上别人家的变压器。

第一级失真让人写出**假的定理**，第二级失真让人写出**孤立的真实**。形式化的日常，大半时间花在与这两级失真讨价还价。

## 3. 正式定义

形式化语料的最小单元是一条**可核验陈述及其证明**，入库条件可以概括为两级闸门：

$$\text{原文} \xrightarrow{\text{翻译闸门：语义忠实}} \text{形式陈述} \xrightarrow{\text{对齐闸门：接上库地基}} \text{可被全库引用的定理对象}$$

| 要素 | 含义 |
| --- | --- |
| 命名空间 | 库内目录式分层，同名的"距离"在度量空间与图论下互不干扰 |
| 依赖闭包 | 一个定理拖带的全部上游引理；库的骨架就是这张巨大的依赖网 |
| 全库重检 | 任何一条贡献被合并时，整座库在持续集成里重新机检一遍 |

第二级闸门解释了"big-theorem 库"的组织逻辑：**大定理从来不是庞然大物，而是成千上万条小引理按依赖关系码放的塔**。库的真正产品不是塔尖，而是那些被反复引用的中间层砖块——上一课热身里那座乘法交换律小厦，是 Mathlib 百万行代码的缩影。

## 4. 分步例题

对三条常见病句做一次"失真手术"：

1. **病句一**"任何大于 1 的自然数都有素因子"译成"对一切 n，n 是素数"——第一级失真：量词对象被整体掉包，存在性（"存在某个 p 整除 n"）凭空蒸发；
2. **病句二**"方程 x²+1=0 有解"译成"存在 z，z²+1=0"——还是第一级：解在哪个论域？不写明论域的存在，等于没说；
3. **病句三**"不是所有实数都有平方根"译成"对所有 r，r 没有平方根"——否定词搬错了家：原来的意思只是"存在反例"，译文却宣布全军覆没；
4. **手术原则**：先钉论域，再钉量词，最后钉否定词的作用范围——三颗钉子各归其位，两条闸门才能放行；
5. 值得回味：三句"病文"在自然语言里都没人会误读——**失真不是原文的错，是两种语言的间隙**。

### 热身：看一条陈述怎样长成砖

```viz
    { "id": "s5", "text": "你今天的作业题（直接引用）" }
  ],
  "edges": [["s1", "s2"], ["s2", "s3"], ["s3", "s4"], ["s4", "s5"]]
}
```

每一个下游节点都在调用上游的**名字**而非重抄其证明——砖块的价值随引用次数复利增长。删掉中间一条边，下游立刻悬空，这就是语料完整性的一次微缩演示。

### 实验 1：给语料算一笔"复利账"

```python title="引用扩散排名：谁是最值得维护的地基"
USERS = {                              # 谁直接引用了谁
    "归纳原理": ["自然数加法交换律", "几何级数求和", "二项式定理"],
    "二项式定理": ["组合恒等式手册", "杨辉三角程序库"],
    "组合恒等式手册": ["估值练习讲义"],
    "素数无穷性": ["模算术入门"],
}

def all_users(root):
    seen = []                          # 已登记的下游全体
    frontier = [root]                  # 本轮待展开的边界层
    for _ in range(len(USERS)):        # 层数有限：轮数封顶即库的深度
        nxt = []
        for node in frontier:
            for follower in USERS.get(node, []):
                if follower not in seen and follower not in nxt:
                    nxt.append(follower)   # 去重后再入队
        seen = seen + nxt              # 边界层并入全体
        frontier = nxt                 # 向下游推进一层
    return seen

ranking = []
for name in USERS:
    ranking.append((name, len(all_users(name))))
ranking.sort(key=lambda pair: pair[1], reverse=True)   # lambda：现场定义的小函数当排序钥匙

for name, cnt in ranking[:3]:          # 切片取前三名
    print("%s: 下游 %d 条" % (name, cnt))
```

"归纳原理"以六条下游高居榜首——它自身只有三笔直接引用，**间接传播才是复利所在**。库维护者据此决定哪一块地基值得优先加固，这正是依赖闭包数据在现实中的用法。

### 实验 2：修复两级失真

下面三条病句各配了三种候选译文。当前答案栏抄的全是"最省事"的选项，程序如实地逐条报出失真。请把 `ANSWER` 改到与形式基准逐条对齐。

```exercise
# @title: 练习：给病句做失真手术
# @check: 第1条: 与形式基准完全一致
# @check: 第2条: 与形式基准完全一致
# @check: 第3条: 与形式基准完全一致
# @check: 对齐率: 3/3
# @hint: 三颗钉子各就各位：病句一找回了丢失的存在量词，病句二补写了论域，病句三把否定词挪回"整个全称"的头顶。
CANON = {
    1: "forall n, gt(n,1) -> exists p, prime(p) and divides(p,n)",
    2: "exists z in Complex, z*z + 1 == 0",
    3: "not(forall r, has_sqrt(r))",
}
OPTIONS = {
    1: {
        "甲": "forall n, prime(n)",
        "乙": "exists p, prime(p) and divides(p,n)",
        "丙": "forall n, gt(n,1) -> exists p, prime(p) and divides(p,n)",
    },
    2: {
        "甲": "exists z, z*z + 1 == 0",
        "乙": "exists z in Complex, z*z + 1 == 0",
        "丙": "forall z, not(z*z + 1 == 0)",
    },
    3: {
        "甲": "not(forall r, has_sqrt(r))",
        "乙": "forall r, not(has_sqrt(r))",
        "丙": "exists r, not(has_sqrt(r))",
    },
}
ANSWER = {
    1: "甲",     # ← 问题在这：存在量词被整句丢掉
    2: "甲",     # ← 问题在这：解的论域没有交代
    3: "乙",     # ← 问题在这：否定词下放到了每个 r 头上
}

def align(ans_map):
    ok_count = 0
    for i in (1, 2, 3):
        if OPTIONS[i][ans_map[i]] == CANON[i]:
            print("第%d条: 与形式基准完全一致" % i)
            ok_count += 1
        else:
            print("第%d条: 存在失真" % i)
    print("对齐率: %d/3" % ok_count)

align(ANSWER)
```

三颗钉子归位后对齐率满分。再体会一遍分步例题的结论：三种病各自错在不同的语法器官上——量词、论域、否定辖域；机器逐字比对就能揪出它们，这恰是形式语料可以放心交给 CI 把关的原因。

```quiz
某大库中一条定义被人发现有笔误：写错了一个下标，但整条定义自洽、证明齐全、全库机检全绿。这说明什么？
- 机检系统出了故障，居然放行了错东西
- 库内一切引用它的结果都"正确地错了"：机器保证的是自洽与忠实，保证不了陈述贴合原意 [*]
- 没什么，自然语言文献里笔误更多，所以无所谓
? 检查器审的是推理合法性，不审定义是否合乎本意——这正是 20 课"陈述本身也要审"的语料级放大。修复笔误后，下游引用方的语义会随新定义整体校正，这既是形式库的脆弱处，也是它的可修复性所在。
```

## 常见误区

:::warning[常见误区]

**误区一**："自动形式化就是把翻译软件跑一遍。"
翻译只过第一级闸门；第二级（对齐库地基）需要理解全库 API 版本与惯用结构，是真正的研究难点。工程界的路线是让模型起草、由依赖检查与人工审阅合议放行。

**误区二**："语料越多越好，来源无所谓。"
形式语料的价值在**依赖闭包的完整性**：断头的孤证无法被引用，等于砖头没有榫头。这也是为什么 Mathlib 追求"一条主线全覆盖"，而不是堆散装结果。

**误区三**："有了大库，人类教科书过时了。"
库的行文面向机器核对，人类读者需要的是叙述、动机与反例。二者是互补的两套压缩：教科书压缩给大脑，形式库压缩给内核——开源生态（Metamath 的极简主义、Isabelle AFP 的文献伴随传统、Lean Mathlib 的工程化协作、miniF2F/ProofNet 一类基准集的桥接）各占一个生态位。

:::

<summary>点开查看逐步解答</summary>
