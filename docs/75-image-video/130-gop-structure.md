# I/P/B 帧与 GOP

## 1. 从一个场景开始

用播放器拖动进度条：有的视频一拖就到，有的却先糊成马赛克、过一两秒才恢复清晰。看直播时有人告诉你"这路流延迟低，因为没开 B 帧"。两件事看似无关，其实都在说同一个机制：编码器**怎么安排帧与帧之间的依赖**。

上一课的预测链省钱，但链条不能无限长——总得定期有人"从零讲一遍"。这一课讲编码器的排班表：I 帧、P 帧、B 帧，以及它们的节奏 GOP。

## 2. 直觉解释

把解码器想成一个讲故事的人，三种帧是三种讲法：

- **I 帧（帧内编码）**：不依赖任何别的帧，一张自包含的完整图片——"从头讲"。最贵（就是一张 JPEG 那样的图），但谁都不欠；
- **P 帧（前向预测）**："和上一帧差不多，只有这些地方要改"——参考**前面**已解码的帧，便宜很多；
- **B 帧（双向预测）**："结合前一帧和后一帧，我居中"——前后各参考一条，预测最准、**最省**。但注意那两个字：**后一帧**。B 帧要"看未来"，未来还没解码，它就没法开工。

"看未来"带来一个绕不开的推论：**显示顺序不等于解码顺序**。观众看到的第 1、2 帧如果是 B 帧，解码器必须先把第 3 帧（P 帧）解出来。解码器里因此多了一个等待区——重排缓冲。

而 GOP（图像组）是排班表的周期：**每隔多少帧放一张昂贵的 I 帧**。I 帧越密，随机访问越快、误码恢复越快，但码率越贵；I 帧越稀，压缩越好，代价是拖进度条要等更久、一个误码要污染到下一个 I 帧才止住。**GOP 的长度，本质是压缩率与随机访问之间的一纸合同。**

## 3. 正式定义

| 帧型 | 参考对象 | 相对大小 | 能否独立解码 |
| --- | --- | --- | --- |
| I | 无（自身帧内编码） | 1.00 | 是 |
| P | 前面最近的锚点帧 | 0.35 | 否 |
| B | 前后各一个锚点帧 | 0.15 | 否 |

（相对大小是工程示意值，I = 1.00、P = 0.35、B = 0.15；帧型结构也按本章组件的实际行为来——末尾凑不满一组的帧降级成 P，不是教科书的开放 GOP。）

**GOP**：相邻两个 I 帧之间的帧序列。闭合 GOP 的规矩：

- 每个 GOP 从 I 帧开始；
- 之后每隔 (B 帧数 + 1) 帧放一个锚点 P（两个锚点之间夹着的就是 B）；
- B 帧不跨 GOP 边界（B 的两个参考必须都已解码，不能去借下一组的 I）；
- GOP 末尾凑不满一组时，凑不满的帧全部降级成 P（只参考前面最近的锚点）。

**解码顺序**：锚点（I/P）按显示顺序逐个解码；B 帧排在**它后面的那个锚点**之后——因为 B 的参考之一是后面的锚点。

**相对码率**：一个 12 帧、每组 2 个 B 帧的 GOP（I B B P B B P B B P P P——末尾凑不满一组的两帧降级成 P），按上表折算 $1.0 + 5\times0.35 + 6\times0.15 = 3.65$，而 12 个全 I 帧要 12.00——**不到三分之一**。

## 4. 分步例题

显示顺序 `I B B P B B P`（7 帧），求解码顺序。

1. **帧 0（I）**：锚点，直接解码 → 解码队列 [0]；
2. **帧 1、2（B）**：要参考帧 3，先攒进等待区；
3. **帧 3（P）**：锚点，解码 → [0, 3]；等待区里的 1、2 两个参考齐了，依次解码 → [0, 3, 1, 2]；
4. **帧 4、5（B）**：参考帧 6，继续攒；
5. **帧 6（P）**：解码 → [0, 3, 1, 2, 6]；4、5 放行 → [0, 3, 1, 2, 6, 4, 5]；
6. **结论**：解码顺序 `0 3 1 2 6 4 5`——注意第 1 帧要等第 3 帧先解。播放端拿到的顺序才是 0,1,2,…，重排缓冲负责把解码顺序捋回显示顺序。

## 5. 动手实验

### 实验 1：拖着看（lab 组件）

```lab
{
  "type": "gop-structure",
  "title": "上排显示顺序、下排解码顺序：弧线就是依赖",
  "gop": 12,
  "bframes": 2,
  "frames": 24
}
```

上排是观众看到的顺序，弧线画出依赖：P 帧一条、B 帧两条。下排是解码顺序，中间的斜线就是重排。点任意一个方框看它的参考关系；点「播放」让解码器按真实顺序走一遍，顺带盯住重排缓冲怎么被 B 帧撑开。最后看最下面那条相对码流：24 个全 I 帧要 24.00，排上 P/B 之后只剩个零头。把 GOP 长度滑块从 4 拖到 16，码流一路变瘦——但随机访问越来越差，两件事永远拧在一起。

### 实验 2：自己算（Python）

```python title="一段 12 帧排班表的两本账"
types = ["I","B","B","P","P","P", "I","B","B","P","P","P"]   # 显示顺序，GOP=6、2 个 B，末尾凑不满的降级成 P
SIZE = {"I": 1.00, "P": 0.35, "B": 0.15}                     # 工程示意值

total = sum(SIZE[t] for t in types)                          # 相对码流总量
all_i = sum(SIZE["I"] for t in types)                        # 同样 12 帧全用 I 的账
print(f"含 P/B 码流 = {total:.2f}，全 I 码流 = {all_i:.2f}")
print(f"压缩到 {total / all_i * 100:.1f}%")

order = []                     # 解码顺序：锚点先解，B 帧跟在后面的锚点之后
pending = []
for i, t in enumerate(types):
    if t == "B":
        pending.append(i)      # B 帧等它后面的锚点
    else:
        order.append(i)
        order.extend(pending)  # 锚点解完，攒着的 B 放行
        pending = []
order.extend(pending)          # 兜底：末尾若还有攒着的 B 也放行
print("解码顺序:", " ".join(str(i) for i in order))
print("显示顺序:", " ".join(str(i) for i in range(len(types))))
```

第一本账：4.70 对 12.00，帧间预测加 B 帧把码流压到 39.2%。第二本账：解码顺序不是 0,1,2,…——第 1、2 帧（B）要等第 3 帧（P）解完，第 7、8 帧（B）要等第 9 帧。**两本账合起来就是 GOP 的全部**：省下的码率，是用"解码端多一道重排工序 + 随机访问变慢"换来的。

### 快问快答

```quiz
视频点播网站想让你拖进度条时"秒到"，编码时应该怎么调 GOP？
- I 帧间隔加大，GOP 拉长，压缩更好
- I 帧间隔缩短，GOP 变短，随时有"从头讲"的入口 [*]
- 全部用 B 帧，解码最快
? 拖动只能从 I 帧开始解码。GOP 越长，离你最近的 I 帧越远，等待与糊屏越久。短视频平台常用 1~2 秒一个 I 帧——用码率换进度条的跟手。
```

::::warning[常见误区]

**误区一**："解码顺序就是播放顺序，只是个实现细节。"
你以为顺序无关紧要——B 帧要参考"未来"，解码顺序必须重排。这个重排直接决定**延迟**：B 帧要等后面的帧解码完才能输出。直播为什么常关掉 B 帧？就是拿压缩率换毫秒级延迟。

**误区二**："I 帧越密越可靠，就该多放。"
你以为 I 帧是保险就多多益善——每张 I 帧都是全价图片，I 帧翻倍码率立涨几成。误码恢复、频道切换、随机访问三件事才需要 I 帧，静态场景下密 I 帧是纯浪费。

**误区三**："B 帧最省，所以多多益善。"
你以为 B 帧密度越大越好——B 帧越多，重排缓冲越大、延迟越高，而且每个 B 要两条参考、对参考帧质量更敏感。工程典型值是每组 1~3 个 B，再多省钱不明显、代价先爆表。

::::

## 6. 练习

**练习 1**：下面的重排代码把 B 帧跟着显示顺序走了，解码器拿到的是不可能的顺序。请修好它，让 B 帧等在后面的锚点之后：

```exercise
# @title: 练习：把解码顺序排对
# @check: 0 3 1 2 6 4 5
# @hint: B 帧的参考之一是它后面的那个锚点，所以锚点必须先解码。B 先攒着，锚点解码完立刻放行
types = ["I", "B", "B", "P", "B", "B", "P"]

order = []
pending = []
for i, t in enumerate(types):
    if t in ("I", "P"):
        order.append(i)
        order.extend(pending)
        pending = []
    else:
        order.append(i)      # ← 问题在这：B 帧不等后面的锚点，跟显示顺序走了
print(" ".join(str(i) for i in order))
```

修正后输出 `0 3 1 2 6 4 5`：P 帧先于它前面的 B 帧。原代码输出 `0 1 2 3 4 5 6`——B 帧抢在参考帧之前解码，解码器面对一个"未来还没发生"的依赖，无能为力。

**练习 2**：一段 30 fps 的视频，GOP = 60（2 秒一个 I 帧）。用户拖动进度条时最坏要等多久才能看到第一幅完整画面？GOP 改成 15 呢？

<details>
<summary>点开查看逐步解答</summary>

1. 最坏情况：刚错过一个 I 帧，要等下一个。GOP = 60 → 最坏等 60 帧 ÷ 30 fps = 2 秒；
2. GOP = 15 → 最坏 0.5 秒；
3. 代价按实验 2 的账本算：I 帧密度翻 4 倍，码率明显上涨。点播站常在"清晰度切换、进度条体验"与"带宽成本"之间反复调这个数；直播还要另算 B 帧带来的延迟。

</details>

## 7. 选读：开放 GOP 与封闭 GOP

<details>
<summary>选读 · B 帧能不能跨组借参考</summary>

封闭 GOP（本课模型）规定 B 帧不跨组：组尾的 B 只参考组内锚点。**开放 GOP** 允许组尾的 B 参考下一组的 I 帧——下一组 I 反正先解码，参考它不违规，还能再省一点码率。

开放 GOP 更省，代价是随机访问变别扭：从组尾 I 帧切入时，它名下那些"向后借参考"的 B 帧解不出来，只能跳过或丢弃，表现为切入瞬间掉几帧。流媒体切片（HLS/DASH）通常强制封闭 GOP——每个切片必须能独立解码，切片边界就是 GOP 边界。

</details>
