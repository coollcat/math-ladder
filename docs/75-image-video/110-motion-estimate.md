# 块匹配与运动估计

## 1. 从一个场景开始

摄像机对着一段匀速行驶的列车拍了 30 秒。30 fps，900 帧画面，每帧 200 万个像素——可画面里绝大部分内容根本没变：背景一动不动，列车只是整体往右挪。

上一课的帧间差分告诉你"哪些地方变了"，但只回答"变了没有"。想压缩，还得回答更精细的一问：**这一块内容，是从上一帧的哪个位置挪过来的？** 找到了这个"从哪挪到哪"，编码器只需要发一个箭头，而不是一整块新像素。

## 2. 直觉解释

把当前帧切成许多小方块（比如 16×16），对每一块做一件事：**拿着这块图案，去上一帧里它周围的一小片邻域里"找自己"**——像拿着照片在人群里找人。

- 找到了：记下"从左边第 6 像素处搬来的"，这就是一个**运动矢量**；
- 没找到（新出现的物体、被遮挡的区域）：那块只好老老实实自己编码。

"找自己"怎么个找法？逐个位置试，比较候选位置和当前块**像不像**，选最像的。这正是第 43 章优化问题的最小实例：

- **目标函数**：两块像素的差异程度（差异越小越像）；
- **可行域**：上一帧里以原位置为中心的一小片**搜索窗口**；
- **任务**：在窗口里找目标函数的最小点。

唯一的区别是：43 章里你可以求导、沿梯度下山，而像素差异函数是锯齿状的——差一个像素，代价就可能跳一大截，**导数根本不存在**。所以这里的优化更原始：要么老老实实穷举（全搜索），要么用多起点式的启发式（三步搜索）。

## 3. 正式定义

**块匹配**：把当前帧第 $t$ 帧切成 $n \times n$ 的块，对每个块在参考帧（通常是上一帧）的搜索窗口里寻找最相似的块。

**SAD（绝对误差和）**——最常用的相似度代价，两块逐像素求差的绝对值再加总：

$$\mathrm{SAD}(dx, dy) = \sum_{v=0}^{n-1}\sum_{u=0}^{n-1} \left| C(x+u,\, y+v) - R(x+u+dx,\, y+v+dy) \right|$$

**运动矢量**：让 SAD 最小的那个位移 $(dx^*, dy^*)$，即

$$(dx^*, dy^*) = \arg\min_{(dx,dy) \in W} \mathrm{SAD}(dx, dy)$$

| 符号 | 名字 | 含义 |
| --- | --- | --- |
| $C$ | 当前帧 | 被匹配的那一帧，块就切在它上面 |
| $R$ | 参考帧 | 通常是上一帧，搜索在这里进行 |
| $n$ | 块边长 | 常用 16；块太小易歧义，太大装不下复杂运动 |
| $(dx, dy)$ | 候选位移 | 搜索窗口内的一个候选位置 |
| $W$ | 搜索窗口 | 半径 $S$ 的方形邻域，共 $(2S+1)^2$ 个候选 |

**全搜索的代价**：每个候选要做 $n^2$ 次减法与取绝对值，总共 $(2S+1)^2 \cdot n^2$ 次运算。$S=8$、$n=16$ 时是 73,984 次——而这只是一个块的一帧。所以工程上有各种加速法，最经典的是**三步搜索**：先大步跳着找大致方向，再逐级缩小步长，计算量从 289 次候选比较降到 27 次。

## 4. 分步例题

拿一台 8×8 的"微型帧"来手算。参考帧 $A$ 按公式 $A(x,y) = (7x + 5y + xy) \bmod 100$ 生成（纹理处处不同，匹配不会有歧义），当前帧 $B$ 是 $A$ 整体**右移 1 列**、最左列补 0。要给块 $n=4$、位于 $(bx, by) = (2, 2)$ 找运动矢量，搜索半径 2。

1. **算 (dx, dy) = (0, 0)**（原地比较）：$B$ 的块相当于把 $A$ 的块整体左挪一列，每个像素差 $7 + y$（$y$ 是行号，本块四行分别差 9、10、11、12），SAD = $4 \times (9 + 10 + 11 + 12) = 168$ —— 不为零，说明物体挪过了；
2. **算 (1, 0)**：$B$ 的块正好和 $A$ 的块逐像素相同，SAD = **0** —— 完美匹配；
3. **算 (2, 0)**：$B$ 比对的块又偏回一列，每个像素差同样拉开成 9~12，SAD = 168；
4. **结论**：全窗口里唯一的最小点在 $(1, 0)$，运动矢量就是"向右 1 像素"——与构造（右移 1 列）完全一致。

留意第 2 步：**SAD = 0 是"找到了"的铁证，但前提是纹理处处唯一**。如果画面里有一大片天空，天空里的块搬到哪儿 SAD 都是 0，矢量就随机器心情了。

## 5. 动手实验

### 实验 1：拖着看（lab 组件）

```lab
{
  "type": "motion-estimate",
  "title": "左边找块、右边看代价曲面：蓝洼就是运动矢量",
  "blockSize": 16,
  "search": 8,
  "dx": 6,
  "dy": 0,
  "fast": false,
  "field": true
}
```

右边那张 SAD 曲面是本课的灵魂：搜索窗口里每个候选位置的匹配代价，蓝 = 像、红 = 不像，蓝环标出算法找到的最优点，叉号是真实位移。做三件事：

- 把真实位移 $dx$ 拖到 6 以内再拖动画面，看蓝洼怎么跟着叉号跑；
- **把搜索半径拖到比真实位移还小**——最优点被逼到窗口边缘，整幅矢量场立刻散掉。这就是"搜索窗口必须罩得住真实运动"的几何含义；
- 切到「三步搜索」，对比它和全搜索找到的矢量：大多数块一样，个别块会掉进邻近的小坑——启发式省时间，但偶尔看走眼。

### 实验 2：自己算（Python）

```python title="全搜索 vs 三步搜索：省了多少次比较"
import math

def full_cost(S, n):          # 全搜索：每个候选位置都比较一遍
    return (2 * S + 1) ** 2 * n * n

def three_step_cost(S, n):    # 三步搜索：每步 3×3 个候选，步数 = log2(S)
    return 9 * int(math.log2(S)) * n * n

print(f"{'S':>3} {'n':>3} {'全搜索':>10} {'三步':>8} {'倍数':>6}")
for S in (4, 8, 12):
    for n in (8, 16):
        f = full_cost(S, n)
        t = three_step_cost(S, n)
        print(f"{S:>3} {n:>3} {f:>10} {t:>8} {f/t:>6.1f}")
```

六行表给出同一个结论：三步搜索把计算量砍掉一个数量级（S=8、n=16 时 73,984 → 6,912），而且**块越大省得越多**。代价是它只看 27 个候选、可能错过真最小点——快速算法永远在"够用"和"最优"之间讨价还价。

### 快问快答

```quiz
把搜索半径从 8 缩到 3，而画面里的物体每帧实际移动 6 个像素，块匹配会发生什么？
- 算得更快，而且结果不受影响
- 搜不到真实位置，矢量被夹在窗口边缘，整幅运动矢量场乱掉 [*]
- SAD 全部变成 0
? 真实位移 (6, 0) 根本不在半径 3 的窗口里，最小点只能落在窗口边界上。压缩里表现为残差突然变大，追踪里表现为目标跟丢。搜索窗口必须罩得住最大的预期运动。
```

::::warning[常见误区]

**误区一**："运动矢量就是物体的真实运动。"
你以为矢量是物理量——其实它只是"块的最佳平移近似"。物体旋转、缩放、形变、被遮挡、光照变化时，矢量只是给出了一个最不坏的解释，未必对应任何真实像素的旅程。

**误区二**："SAD = 0 说明找到了同一块图案。"
你以为零代价就是命中——在平坦区域（天空、白墙）里，块搬到窗口内任何位置 SAD 都是 0，匹配完全歧义。所以真实编码器还要给矢量本身编码算成本：残差一样时，偏爱离原点近的矢量。

**误区三**："学了梯度下降，块匹配也能沿梯度找最小。"
你以为可以套用第 43 章的连招——SAD 对 $(dx, dy)$ 是阶梯状函数，不连续、不可导，梯度根本不存在。这里能做的是穷举（全搜索）或粗到细的启发式（三步、菱形搜索），本质是"在离散格子上的搜索"。

::::

## 6. 练习

**练习 1**：下面的块匹配代码跑出了"负的代价"，显然不对。请修正比较函数，让它输出正确的运动矢量：

```exercise
# @title: 练习：修好坏掉的 SAD
# @check: 1 0 0
# @hint: 差值有正有负，直接求和会正负相消，甚至推出负代价。比较前先把每个差值取绝对值
A = [(7*x + 5*y + x*y) % 100 for y in range(8) for x in range(8)]   # 参考帧
B = []
for y in range(8):              # 当前帧：整幅右移 1 列，最左列补 0
    B.append(0)
    for x in range(7):
        B.append(A[8*y + x])

bx, by, n = 2, 2, 4             # 块位置与边长
best = None
for dy in range(-2, 3):
    for dx in range(-2, 3):
        s = 0
        for v in range(n):
            for u in range(n):
                d = B[(by+dy+v)*8 + (bx+dx+u)] - A[(by+v)*8 + (bx+u)]
                s = s + d       # ← 问题在这：差值带符号，正负相消
        if best is None or s < best[2]:
            best = (dx, dy, s)
print(best[0], best[1], best[2])
```

修正后输出 `1 0 0`：运动矢量向右 1 像素、SAD 为 0——物体确实右移了一列。带符号的版本会"最小化"到 -676 这种荒谬值，因为正负差互相抵消，哪个候选抵消得最干净哪个"代价"就越负。

**练习 2**：把当前帧的构造改成**右移 2 列**（`B.append(A[8*y + x - 2] if x >= 2 else 0)`），搜索窗口保持 `range(-1, 2)` 不变，再跑一遍，输出变成什么？真实最优在哪？

<details>
<summary>点开查看解答</summary>

输出变成 `1 1 48`——不但没找到真实位移 $(2, 0)$，连**方向都错了**（对角线，而物体是水平移动的）。真实位移 $(2, 0)$ 根本不在半径 1 的窗口里；把窗口恢复到 `range(-2, 3)` 就能搜到 $(2, 0)$、SAD = 0。窗口小于真实运动，矢量必然失真——这正是实验 1 里矢量场散掉的代码版。

</details>

## 7. 选读：更快的搜索与更细的精度

<details>
<summary>选读 · 菱形搜索与半像素运动</summary>

三步搜索的路线是"大步跳、逐级停"：步长 4 → 2 → 1，每步只在当前最优点周围 3×3 的九个位置里再挑，总候选 27 个，是全搜索 289 个的 9.3%。它的隐含假设是**代价曲面大致单坑**——而真实画面里 SAD 曲面常有多个局部坑，大步跳可能一步跨进错误的坑。菱形搜索用紧凑的菱形模板反复贴合，先大范围滑移、命中后再换小菱形精修，对多坑曲面更稳。

另一个工程细节是**亚像素精度**：真实运动未必恰好落在整数像素上。编码器先把参考帧用双线性插值加密一倍（半像素格点），再在加密后的格点上搜索——精度提高半像素，残差通常还能再降一截。代价是搜索空间变成原来的 4 倍。H.264 之后的编码标准普遍支持 1/4 像素精度。

</details>
