## 1. 从一个场景开始
浏览器开了 30 个标签页，其中一个页面死循环了，鼠标卡住——可其他 29 个标签照常滚动，浏览器的下载也还在跑。
同一个程序里，为什么"一部分死了"而"另一部分活着"？更根本的问题是：**进程和线程到底差在哪，为什么操作系统要造两个词？**
## 2. 直觉解释
**进程是一栋房子，线程是住在里面的人。**
- 房子里有客厅（代码段、数据段、堆），有门牌号（地址空间），还有邮箱（打开的文件）——**这些是房子的一部分**；
- 住在里面的人各有一本私人记事本（栈）和各自的当前动作（寄存器、PC）——**这些是人的**；
- 一家人共享客厅，所以抢电视要商量（锁）；隔壁房子的人进不来，因为门牌号体系根本不同（页表不同）。
于是：
| 视角 | 谁独占 | 谁共享 | 切换时要换什么 |
| --- | --- | --- | --- |
| **进程** | 整个地址空间 | 几乎没有（除非显式共享内存） | 页表（CR3）+ 寄存器 + 栈，TLB 被刷 |
| **线程** | 栈、寄存器、PC | 代码、数据、堆、打开的文件 | 只有寄存器与栈 |
**换房子贵（要换门牌号体系），换人便宜。**
## 3. 正式定义
**进程（process）** = 一个独立的**地址空间** + 至少一条执行流 + 一整套内核登记的内核对象（PCB）。
**线程（thread）** = 进程内部的一条**执行流**，是 CPU 调度的最小单位；它独占栈与寄存器，共享所属进程的地址空间。
$\text{进程} = \text{地址空间} \cup \lbrace\text{线程}_1, \ldots, \text{线程}_n\rbrace, \qquad n \ge 1$
| 符号 / 术语 | 含义 |
| --- | --- |
| PCB（进程控制块） | 内核里登记 pid、页表基址 CR3、打开文件表、cwd 的结构体 |
| TCB（线程控制块） | 登记 tid、栈范围、保存的寄存器、调度状态 |
| CR3 | x86-64 上存放页表根地址的寄存器，**换进程就是换它** |
| 上下文切换（context switch） | 保存当前执行流的寄存器、恢复下一条的，并切换地址空间（如需要） |
**切换成本的真实量级**（x86-64 Linux 典型值）：
- 直接开销（保存/恢复寄存器、切换内核栈）约 **1~10 µs**；
- 线程切换：不换 CR3，TLB 保留，**这是它便宜的全部原因**；
- 进程切换：换 CR3 后所有用户态 TLB 项失效，后续若干次内存访问都要走多级页表。以第 50 课的数字算，TLB 命中率从 99% 掉下去的一瞬间，平均访存从 **105 ns** 爬向几百 ns；
- 创建成本：Linux `fork` + 写时复制约 **0.1~1 ms**，`pthread_create` 约 **20~50 µs**；默认线程栈 **8 MB**（虚拟大小，按需调页，实际物理占用通常只有几十 KB）。
## 4. 分步例题
**例**：时间片 1 ms，每次上下文切换 5 µs。问切换开销占比；若时间片缩到 100 µs 呢？
1. 统一单位：1 ms = 1000 µs；
2. 每个时间片跑满后切一次，占比 $= \dfrac{5}{1000 + 5} \approx 0.50\%$；
3. 时间片 100 µs 时：$\dfrac{5}{100 + 5} \approx 4.76\%$；
4. 若时间片只剩 20 µs：$\dfrac{5}{25} = 20\%$——**CPU 五分之一的时间在换人，不在干活**。
这就是"时间片不能无限小"的定量理由：公平性买的是响应速度，付的却是切换开销。

- 看读数里的"切换代价"一栏：进程是"换页表 + 刷 TLB"，线程只是"换寄存器与栈"。
点一下"栈 stack"再点一下"堆 heap"，把这两句话连起来读一遍——**并发 bug 几乎全出在"你以为是私有的，其实是共享的"**。
### 实验 2（python）：共享代码页省了多少物理内存
```python title="两个进程共享同一个物理页帧"
page = 4096                      # 一页 4 KB
# 页表：虚拟页号 → 物理页帧号
proc_a = {0: 100, 1: 101, 2: 205}    # A：0/1 私有数据，2 是共享库代码
proc_b = {0: 130, 1: 131, 2: 205}    # B：私有数据不同，但虚拟页 2 也指向帧 205
for name, tbl in [("进程 A", proc_a), ("进程 B", proc_b)]:
    vaddr = 2 * page + 0x40      # 虚拟地址 = 虚拟页号 × 页大小 + 页内偏移
    vpn = vaddr // page          # // 是整除：取出虚拟页号
    off = vaddr % page           # %  是取余：取出页内偏移
    print(f"{name}：虚拟地址 0x{vaddr:x} → 虚拟页 {vpn} → 物理帧 {tbl[vpn]} + 偏移 0x{off:x}")
frames_a = set(proc_a.values())  # set：去重集合，用来数「不同的物理页帧」
frames_b = set(proc_b.values())
print(f"\n各自占用物理帧：{len(frames_a)} + {len(frames_b)} = {len(frames_a) + len(frames_b)}")
print(f"共享后实际只需：{len(frames_a | frames_b)} 帧（| 是集合并集）")
print(f"节省物理内存：{(len(frames_a) + len(frames_b) - len(frames_a | frames_b)) * page / 1024:.0f} KB")
```
两个进程的虚拟地址**完全相同**（都是 `0x2040`），却指向不同的物理帧——除了那一页共享库代码。共享代码页是"虚拟内存"最直接的红利：一千个进程跑同一份 libc，物理内存里只需一份。
:::warning[常见误区]
**误区一**："线程一定比进程快，所以能多线程就多线程。" 你以为切换成本是唯一考量——线程的**创建**确实比进程便宜一个数量级，但**共享**是双刃剑：一个线程踩坏堆内存，整个进程一起崩；一个线程死锁，其余线程全被拖住。浏览器的做法恰恰是**每标签一个进程**（站点隔离），宁可付切换成本换故障隔离。**先问"崩了要连坐吗"，再问"哪个快"。**
**误区二**："不同进程的地址空间完全隔离，所以不需要同步。" 你以为只要不共享内存就安全——进程之间还能共享：显式 `mmap(MAP_SHARED)`、System V 共享内存、同一个文件上的 `write`、甚至是父进程 fork 后继承的文件描述符偏移。**"不共享内存"不等于"不共享状态"。**
**误区三**："上下文切换的成本就是那段切换代码的执行时间。" 你以为账面上 5 µs 就完了——真正的开销在**切换之后**：新进程的代码与数据不在缓存里（冷缓存），TLB 被刷掉，分支预测器也要重新热身。实测中"间接开销"常常是直接开销的数倍。**所以缓存与 TLB 的命中率，才是并发结构设计的隐藏裁判。**
:::

```exercise
switch_us = 5.0                  # 一次上下文切换 5 微秒
times = 10000                    # 每秒切换一万次
total_ms = switch_us * times     # ← 问题在这：算出来的是 µs，不是 ms
print(total_ms)
```
**练习 2**：某服务有 4 个工作线程，每个线程默认栈 8 MB（虚拟大小）。若实际每线程只用到 60 KB 物理页，问虚拟占用与实际物理占用各是多少？
<details>
<summary>点开查看逐步解答</summary>
1. 虚拟占用：$4 \times 8\ \text{MB} = 32\ \text{MB}$——这是"申请到的地址范围"，不是内存；
2. 物理占用：$4 \times 60\ \text{KB} = 240\ \text{KB}$——只有真正被读写过的页才会通过缺页异常调进来；
3. 所以"线程栈 8 MB"吓人但无害：**虚拟地址空间是 128 TB 的纸面额度，物理内存才是真金白银**。这也是为什么能开几千个线程而机器不炸（真炸通常是别的原因：调度开销与锁竞争）。
</details>
## 7. 选读：fork 的写时复制与"线程"的三种实现
<details>
<summary>选读 · 为什么 fork 这么快，以及协程是什么</summary>
**写时复制（Copy-on-Write）**：`fork` 时内核**不复制**任何物理页，只是把父子进程的页表都指向同一批帧，并把所有页标记为只读。谁先写，谁触发一次保护异常，内核此时才复制那一页并改成可写。于是 `fork` + `exec` 的成本几乎只有"复制一张页表"——而绝大多数 `fork` 后面紧跟 `exec`，复制纯属浪费。
**三种"线程"**：
| 实现 | 谁在调度 | 切换成本 | 特点 |
| --- | --- | --- | --- |
| 内核线程（1:1） | 内核 | 1~10 µs | Linux pthread 的做法，能真正用满多核 |
| 用户线程（N:1） | 运行时库 | ~100 ns | 切换极快，但一个线程阻塞则全体阻塞 |
| 协程 / 有栈协程 | 程序自己 | ~50 ns | Go 的 goroutine、Python asyncio 属于这一类 |
协程本质上是"**在用户态自己保存和恢复栈**"——把内核做的上下文切换手工做了一遍，换来的是批量调度与更小的栈（goroutine 初始栈 2 KB）。**它替代不了线程，只是把"什么时候切换"这个决定权从内核手里拿了回来。**
</details>
