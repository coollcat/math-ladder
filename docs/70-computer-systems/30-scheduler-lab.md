# 调度算法与权衡

## 1. 从一个场景开始

食堂只有一个打饭窗口。前面排着一位端着四菜一汤的（要打 2 分钟），你只要一个包子（10 秒）。

让你先打，所有人的平均等待时间最短——可那位端盘子的会一直等下去，直到又来一个只要包子的。**对整体最优的规则，对个人可能最残忍。** 操作系统的调度器每天都在做这个选择。

## 2. 直觉解释

调度器是"发牌员"。每一轮它只回答一个问题：**接下来这若干毫秒，给谁？**

| 规则 | 大白话 | 好处 | 代价 |
| --- | --- | --- | --- |
| FCFS | 先来后到，排队 | 绝对公平、零饥饿 | 一个长任务堵死全场（护航效应） |
| SJF | 谁快谁先 | **平均等待时间最短**（可证） | 长任务可能永远排不上（饥饿） |
| RR | 每人发一张 q 毫秒的票，用完排到队尾 | 响应快、公平 | 切换次数多，周转时间长 |
| 优先级 | 重要的先 | 贴合业务 | 低优先级饿死，还会"优先级反转" |
| MLFQ | 多级队列，用得多就降级，定期全体升回 | 兼顾响应与吞吐 | 参数难调，行为难预测 |

**没有免费午餐**：响应时间、周转时间、公平性、开销，四者只能挑两三个。

## 3. 正式定义

对每个任务 $i$，记到达时刻 $a_i$、需要 CPU 的总时长（服务时间）$b_i$、完成时刻 $c_i$：

$$\text{周转}\ T_i = c_i - a_i, \qquad \text{等待}\ W_i = T_i - b_i, \qquad \text{响应}\ R_i = s_i - a_i$$

| 符号 | 名字 | 含义 |
| --- | --- | --- |
| $a_i$ | 到达时刻 | 任务变为可运行的时间 |
| $b_i$ | 服务时间（burst） | 需要的 CPU 时间总量 |
| $c_i$ | 完成时刻 | 最后一次运行结束的时间 |
| $s_i$ | 首次运行时刻 | 决定"响应"快慢 |
| $T_i$ | 周转时间 | 用户感受到的"总耗时" |
| $W_i$ | 等待时间 | 在就绪队列里干等的时间 |

**SJF 最优性**：在所有非抢占调度中，按 $b_i$ 升序执行可使 $\overline{W} = \frac{1}{n}\sum W_i$ 最小（选读部分给出交换论证）。

**轮转（Round Robin）**：就绪队列 FIFO，每任务最多运行 $q$（时间片）后被剥夺并排到队尾。$q \to \infty$ 退化为 FCFS；$q \to 0$ 则全部时间都在切换。

**真实量级**：Linux 的 **CFS（完全公平调度器）**已经不用固定时间片，它按"虚拟运行时间"挑最亏的那个，靠两个参数控制节奏——调度周期 `sched_latency` 默认 **6 ms**，单任务最小粒度 `sched_min_granularity` 默认 **0.75 ms**。也就是说，在 4 核满载时，每个可运行任务大约每 6 ms 内至少被轮到一次。传统固定时间片系统常用的量级是 **10~100 ms**，而每次上下文切换要 **1~10 µs**。

## 4. 分步例题

**例**：四个任务同时在 0 时刻到达，$b = (8, 4, 2, 6)$。分别算 FCFS（顺序 P1,P2,P3,P4）与 SJF 的平均周转与平均等待。

1. **FCFS**：完成时刻依次 $8,\ 12,\ 14,\ 20$；周转 $8,\ 12,\ 14,\ 20$ → $\overline{T} = 13.5$；等待 $= T - b$ 得 $0,\ 8,\ 12,\ 14$ → $\overline{W} = 8.5$；
2. **SJF**：按 $b$ 升序 P3(2), P2(4), P4(6), P1(8)；完成时刻 $2,\ 6,\ 12,\ 20$；周转 $2,\ 6,\ 12,\ 20$ → $\overline{T} = 10$；等待 $0,\ 2,\ 6,\ 12$ → $\overline{W} = 5$；
3. 对比：SJF 把平均等待从 8.5 压到 5（**降低 41%**），而总完成时刻都是 20——**CPU 忙到最后一刻，谁先谁后不改变总工作量，只改变每个人的体验**；
4. 代价：P1 在 SJF 下从"立刻开跑"变成"等到第 12 秒"。若后续不断有短任务进来，它可能永远排不上——这就是**饥饿**。

第一排按钮换任务集（同时到达 / 错峰到达 / 长任务先到），第二排换算法，下面的滑块改 RR 的时间片。重点看读数里的**平均周转**与**平均等待**两项，它们常常往相反方向走。

做三组对照：

- 预设"同时到达"，FCFS → SJF：平均等待从 8.5 掉到 5.0，而总时长不变（都是 20）；
- 预设"长任务先到"，切到 FCFS 看**护航效应**：P1(9) 一堵，后面三个短任务全部陪等；切 SJF 立刻缓解；
- 选 RR，把时间片从 1 拖到 6：平均周转先变好（切换少了），但**响应时间**单调变差（第一个字节要等更久）。**周转与响应不可兼得**，这就是那个取舍。

### 实验 2（python）：手搓一台离散事件模拟器

```python title="同一个循环骨架，换一行挑任务的规则"
tasks = [("P1", 0, 8), ("P2", 0, 4), ("P3", 0, 2), ("P4", 0, 6)]   # (名字, 到达, 服务时间)

def simulate(jobs, algo):
    left = list(jobs)      # 还没跑完的任务
    out = []               # 结果账本
    t = 0                  # 模拟时钟
    while left:            # 只要还有活没干完就继续推进
        ready = [x for x in left if x[1] <= t]     # 列表推导：挑出「已到达」的那些
        if not ready:
            t = min(x[1] for x in left)            # CPU 空转：时钟直接跳到下一个到达点
            continue
        if algo == "fcfs":
            pick = min(ready, key=lambda x: x[1])  # lambda：临时匿名函数，x[1] 是到达时刻
        else:
            pick = min(ready, key=lambda x: x[2])  # x[2] 是服务时间 → SJF
        name, arrive, burst = pick                 # 元组解包
        t = t + burst
        out.append((name, t - arrive, t - arrive - burst))   # (名字, 周转, 等待)
        left.remove(pick)
    return out

for algo in ["fcfs", "sjf"]:
    res = simulate(tasks, algo)
    tat = sum(r[1] for r in res) / len(res)        # 生成器表达式：先取出所有周转再求和
    wait = sum(r[2] for r in res) / len(res)
    print(f"{algo:>5}  平均周转 {tat:5.1f}   平均等待 {wait:5.1f}")
```

输出正是例题的两个数字（13.5 / 8.5 与 10.0 / 5.0）。**注意这个循环骨架本身就是全部调度器的共性**：挑一个、跑一段、推进时钟。换算法只是换"挑谁"和"跑多长"两行。

### 快问快答

```quiz
SJF 的平均等待时间最短，为什么没有通用操作系统真的把它当主调度器？
- 因为它的实现太复杂
- 因为操作系统无法预知每个任务要跑多久，而且它会使长任务饥饿 [*]
- 因为它的平均周转时间最差
? 服务时间只能靠历史行为预测（指数平均），猜错了就退化成随机排序。更要命的是饥饿：只要短任务源源不断，长任务永远排不上。MLFQ 用「降级 + 定期全体提升」两招来救，代价是多了一堆要调的参数。
```

:::warning[常见误区]

**误区一**："时间片越小越公平，所以越小越好。"
你以为 q 越小响应越好——响应确实变好，但**每 q 毫秒就要切换一次**：q = 1 ms、切换 5 µs 时开销 0.5%，q = 100 µs 时飙到 4.8%，q = 20 µs 时高达 20%。**公平性是用 CPU 时间买的，价格标签就是切换开销。**

**误区二**："SJF 可证最优，所以它是'最好的'算法。"
你以为"最优"是全面最优——那个证明只针对**平均等待时间**这一个指标，并且假设服务时间**事先已知**。真实系统里它既猜不准 burst，又会让长任务饥饿。**任何"最优"结论都要先问：最优的是哪个指标、在什么假设下。**

**误区三**："给重要任务高优先级，就一定能优先跑。"
你以为优先级是绝对的——经典的**优先级反转**：低优先级任务持有一把锁，高优先级任务等这把锁，而中优先级任务不断抢占 CPU，结果高优先级被中优先级堵着。火星探路者号就栽在这上面，解法是**优先级继承**（持锁者临时升到等待者的优先级）。

:::

**练习 2**：三个任务 A(到达 0，需 6)、B(到达 2，需 3)、C(到达 4，需 2)，用 RR、时间片 $q = 2$ 调度。画出甘特图并求三个任务的周转时间。

<details>
<summary>点开查看逐步解答</summary>

1. $t=0$：只有 A 就绪，跑 2 → A 剩 4，时刻 2；
2. $t=2$：B 到达，队列 [A, B]，A 跑 2 → A 剩 2，时刻 4；
3. $t=4$：C 到达，队列 [B, C, A]，B 跑 2 → B 剩 1，时刻 6；
4. $t=6$：队列 [C, A, B]，C 跑 2 → C 完成于 8；
5. $t=8$：队列 [A, B]，A 跑 2 → A 完成于 10；
6. $t=10$：B 跑 1 → B 完成于 11；
7. 周转：$T_A = 10 - 0 = 10$，$T_B = 11 - 2 = 9$，$T_C = 8 - 4 = 4$；平均 **7.67**；
8. 对比 FCFS（A 到 6，B 到 9，C 到 11）：周转 6、7、7，平均 6.67。**RR 的平均周转更差，但每个任务都在两秒内第一次摸到了 CPU**——这就是它的卖点。

## 7. 选读：SJF 最优性的交换论证

<details>
<summary>选读 · 为什么「短作业优先」给出的平均等待最小</summary>

设有两个相邻执行的任务，服务时间为 $b_1 > b_2$，当前时刻为 $t$，前面已无人。

- 按此顺序：两者等待之和 $= (t - a_1) + (t + b_1 - a_2)$（到达时刻不影响差值，可令二者同时到达，则和为 $0 + b_1 = b_1$）；
- 交换顺序：和为 $0 + b_2 = b_2$；
- 因 $b_1 > b_2$，交换后**总和严格变小**，而这两个任务之外的所有任务完成时刻不变（因为这一段的总长度 $b_1 + b_2$ 没变）。

于是：**任何"长任务排在短任务前面"的相邻对，交换后总等待只会更小。** 反复交换下去，最终收敛到按 $b$ 非降序排列——这就是全局最优。这类证明叫**交换论证（exchange argument）**，第 30 章的贪心算法里你会反复遇见它。

注意证明用到了两个前提：① 服务时间已知；② 非抢占、所有任务同时可得。放宽任何一条，结论都要重新证。

</details>
