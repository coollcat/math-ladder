# 文件系统与持久化

## 1. 从一个场景开始

你在程序里写下一行 `open("/home/alice/notes.txt")`。磁盘上只有磁道、扇区和一堆 0/1——**它根本不知道什么叫"目录"，什么叫"文件名"**。

那么，从一串斜杠分隔的名字，到电机转动、磁头读取某个扇区，中间那张"翻译表"是谁、长什么样？

## 2. 直觉解释

文件系统是一套**图书馆编目法**：

- **目录**是卡片柜里的抽屉：里面只有一行行的"书名 → 索书号"，**不存书的内容**；
- **inode** 是那本书的索引卡：作者、页数、位置、借出状态——**元数据集中放在这里**，与书名分开；
- **数据块**是书架上的实际书页。

这样设计的关键收益：**改书名不用动书**（重命名只改一个目录项）、**同一本书可以有多个书名**（硬链接）、**书可以放在任意书架上**（块号随便指）。

## 3. 正式定义

**目录项（dentry）**：一条 `(文件名, inode 号)` 的映射。目录本身也是一种文件，它的数据块里存的就是这张表。

**inode（索引节点）**：文件的元数据 + 块指针，不含文件名。ext4 默认 inode 大小 **256 字节**，包含权限、大小、时间戳、链接计数，以及 **15 个块指针**：

| 指针 | 数量 | 4 KB 块、4 字节块号时能寻址 |
| --- | --- | --- |
| 直接块 | 12 | $12 \times 4\ \text{KB} = 48\ \text{KB}$ |
| 一级间接 | 1 | $1024 \times 4\ \text{KB} = 4\ \text{MB}$ |
| 二级间接 | 1 | $1024^2 \times 4\ \text{KB} = 4\ \text{GB}$ |
| 三级间接 | 1 | $1024^3 \times 4\ \text{KB} \approx 4\ \text{TB}$ |

一个间接块里装的是**块号**（4 KB / 4 B = 1024 个），它自己不存文件内容——所以访问它指向的数据要**多读一次盘**。

**超级块（superblock）**：整个文件系统的"户口本"，记录块大小、总块数、空闲块数、inode 表位置。它坏了整个分区就废了，所以有多份备份。

**链接计数（link count）**：有多少个目录项指向这个 inode。`rm` 其实是 `unlink`：把目录项删掉、计数减一；**计数归零且没有进程打开它时**，数据块才真正被回收。

**碎片（fragmentation）**：一个文件的数据块在磁盘上不连续。顺序读一个跨 3 段的文件，机械硬盘要 3 次寻道（每次约 **10 ms**），而连续存放只需 1 次。

## 4. 分步例题

**例**：冷缓存下（目录项与 inode 缓存都是空的）读取 `/etc/passwd` 的第一个数据块，需要多少次磁盘读？

1. 读根 `/` 的 inode——根目录的 inode 号是固定的（ext4 里是 2），无需查找：**1 次**；
2. 读根的数据块，在里面线性匹配字符串 `etc`：**1 次**（大目录用哈希或 B 树索引，可省掉这一步的扫描）；
3. 读 `etc` 的 inode：**1 次**；
4. 读 `etc` 的数据块，匹配 `passwd`：**1 次**；
5. 读 `passwd` 的 inode：**1 次**；
6. 读它的第一个数据块：**1 次**；
7. 合计 **6 次**磁盘 I/O。按每次 10 ms 算，就是 **60 ms**——而你感觉"文件是秒开的"。

差额从哪来？**dentry 缓存与 inode 缓存（页缓存）**：第二次打开同一个文件时，六步全部命中内存，耗时降到微秒级。这就是为什么"第一次打开慢"是普遍现象。

**点磁盘里任一块**，下方会告诉你它是谁：块 0 是超级块、块 1–8 是 inode 表、带颜色的是当前文件的地盘。

做三个观察：

- 选 `/home/bob/big.bin`（20 KB）：它有 3 个直接块 + 1 个**一级间接块**，而间接块指向的两个数据块 **#70、#71 与前面的 #43、#45、#52 完全不连着**——读数里"碎片：跨 N 段"就是在数这个；
- 点"碎片整理"：数据块被搬到连续区，跨段数变 1，**顺序读只需 1 次寻道**；
- 点紫色的一级间接块，看提示："它里面全是块号，自己不存文件内容"——**小文件永远不要走这条路**，这就是 48 KB 直接块存在的意义。

### 实验 2（python）：一个 inode 到底能管多大的文件

```python title="12 个直接块 + 三级间接，能撑到多大"
block = 4096                 # 块大小 4 KB
ptr = 4                      # 一个块号占 4 字节
per = block // ptr           # 一个间接块里能放多少个块号（1024）

direct = 12 * block
lvl1 = per * block
lvl2 = per * per * block
lvl3 = per ** 3 * block      # ** 是乘方运算

print(f"{'12 个直接块':<12} {direct / 1024:>12.1f} KB")
print(f"{'一级间接':<12} {lvl1 / 1024 ** 2:>12.1f} MB")
print(f"{'二级间接':<12} {lvl2 / 1024 ** 3:>12.1f} GB")
print(f"{'三级间接':<12} {lvl3 / 1024 ** 3:>12.1f} GB")
print(f"\n单文件上限约 {lvl3 / 1024 ** 3:.1f} GB（ext4 用 48 位块号可到 16 TiB）")
print(f"写满 4 MB 大文件需要 {lvl1 // block} 个数据块 + 1 个间接块")
```

注意最后一行：**4 MB 以上的文件，每 4 MB 就要多付一次"读间接块"的 I/O**。这也是数据库倾向于用**大文件 + 顺序写**而不是一堆小文件的原因之一。

### 实验 3（python）：冷缓存下打开一个文件要碰几次盘

```python title="把「路径解析」拆成一张 I/O 清单"
depth = 3                    # /home/bob 三层目录
plan = []
for d in range(depth):
    plan.append(f"读第 {d + 1} 层目录的 inode")
    plan.append(f"读第 {d + 1} 层目录的数据块，线性匹配名字")
plan.append("读目标文件的 inode")
plan.append("读目标文件的第一个数据块")

total = 0
for i, what in enumerate(plan, start=1):   # start=1：让编号从 1 开始
    total = total + 1
    print(f"{i}. {what:<34} +1 次 I/O")
print(f"\n合计 {total} 次磁盘 I/O × 10 ms ≈ {total * 10} ms（冷缓存）")
print("第二次打开：dentry / inode 缓存全命中 → 微秒级")
```

8 次 I/O、80 ms 对 0.001 ms——**缓存把这件事加速了近十万倍**。文件系统性能调优的绝大部分工作，本质上都是在提高这几个缓存的命中率。

:::warning[常见误区]

**误区一**："文件名存在 inode 里。"
你以为 `ls` 读的是 inode——**inode 里没有文件名**，只有权限、大小、时间戳和块指针。名字在**目录的数据块**里。这解释了两条反直觉的行为：① 改文件名只需改一个目录项，不动文件本身；② 同一个 inode 可以有好几个名字（硬链接），`rm` 只是减少链接计数，**计数没归零时文件还在**。

**误区二**："`rm` 之后数据就没了。"
你以为删除会擦除——`rm` 只是把目录项标记为未用、块放回空闲位图，**数据块的内容原封不动地留在盘上**，直到被新文件覆盖。这正是数据恢复软件的工作原理，也是"安全删除"必须用 shred 覆写的原因。**同理，`write()` 返回成功也不代表数据到了盘上**——它可能还在页缓存里，要 `fsync()` 才落盘。

**误区三**："碎片整理只是让磁盘'更整齐'，不影响正确性。"
你以为它只是优化——对机械硬盘，随机小块读的吞吐可能只有顺序读的**百分之一**（每次寻道 10 ms 摊到 4 KB 上，有效带宽低得惊人）。SSD 没有寻道时间，碎片影响小得多，但**写入放大**与**磨损均衡**又成了新的约束。**"碎片重不重要"取决于介质**，这就是为什么现代系统对不同设备用不同的文件系统与挂载参数。

:::

```exercise
# @check: 4194304
# @hint: 4 KB 的间接块里塞的是「块号」而不是数据，每个块号占 4 字节 → 4096 / 4 = 1024 个块号，每个指向一个 4 KB 数据块。代码按 8 字节算块号了

ptr = 8                  # ← 问题在这：32 位块号是 4 字节，不是 8 字节
per_block = block // ptr   # 一个间接块里能放的块号个数
capacity = per_block * block
print(capacity)
```

**练习 2**：一个 100 KB 的文件，块大小 4 KB。问：需要多少个数据块？其中几个走直接块、几个要走一级间接？若文件被删到只剩 40 KB 又写回 100 KB，最坏情况下块布局会变成什么样？

<details>
<summary>点开查看逐步解答</summary>

1. $100\ \text{KB} / 4\ \text{KB} = 25$ 个数据块；
2. 前 12 个走直接块，**第 13 个起要走一级间接**：需要 1 个间接块承载剩下的 13 个块号（1024 个槽位绰绰有余）；
3. 所以总共 25 个数据块 + 1 个间接块 = 26 次块分配；
4. 删除后重写：原来的 25 个块被回收，但它们中间可能已被其他文件占用，于是新文件被切成若干段——**这就是碎片**。反复"删大文件、写大文件"是碎片的最大来源；
5. 对策：预分配（`fallocate`）一次性占住连续块，或者像数据库那样**一开始就建一个固定大小的大文件**，自己在里面管理空闲空间，绕开文件系统的分配器。

</details>

## 7. 选读：日志（journaling）与崩溃一致性

<details>
<summary>选读 · 为什么拔电源不会毁掉你的文件系统</summary>

写一次文件可能要修改三处磁盘结构：**数据块、inode、空闲块位图**。若在改完 inode 但还没改位图时断电，文件系统就进入了不一致状态——这就是早期 Linux 开机要跑十几分钟 `fsck` 的原因。

**日志（journaling）** 的做法是**先把"我打算做什么"写进日志区**：

1. 把要修改的元数据写进日志，尾部写一个提交记录（commit record）；
2. 提交记录落盘后，才真正把元数据写到它们该去的地方；
3. 全部写完后，在日志里把这条记录标记为"已完成"（checkpoint）。

崩溃恢复时只需扫描日志：**没有提交记录的，整条丢弃；有提交记录的，重放一遍**。因为重放是**幂等**的（把同一个块写成同一个值，做几次都一样），所以断电在任何时刻发生都安全。

代价是**每个元数据操作都要写两次盘**。ext4 提供三种模式权衡：`journal`（数据也记日志，最安全最慢）、`ordered`（默认：先写数据、再记元数据日志）、`writeback`（只记元数据，最快但可能留旧数据）。

数据库里的 **WAL（Write-Ahead Log）** 与 redo/undo 日志，思想上和它是同一件事——只是把"文件系统元数据"换成了"行记录"。第 110 课的 ACID 里的 D（持久性），最终就落在这套机制上。

</details>
