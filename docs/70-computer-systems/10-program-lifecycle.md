# 程序是怎么跑起来的

## 1. 从一个场景开始

你在终端敲下 `./hello`，回车，不到百分之一秒后屏幕上跳出一行 `Hello, world`。

这百分之一秒里，磁盘上那串"人写得懂"的字符，变成了一串"CPU 吃得下"的电平。中间隔着的不是一步，而是**七道工序**——而绝大多数程序员只在其中一道里干活。

## 2. 直觉解释

把程序想成一份**菜谱翻译成后厨动作**的过程：

- **源码**是写给人看的菜谱："加盐少许"；
- **预处理**是把引用的其他菜谱整本抄进来（`#include`），并把缩写展开（宏）；
- **编译**是总厨把它翻成后厨行话（汇编）："取 3 克盐，撒入"；
- **汇编**是再把行话压成手势暗号（机器码）：一个手势就是一个二进制数；
- **链接**是把"去 3 号灶台取盐"这句话里的"3 号灶台"填成真实位置——**你写的 `printf` 不在你的文件里**；
- **加载**是把整本后厨手册摆到操作台上，每个工位对应一个固定的台面编号（地址）；
- **执行**是终于开火。

关键在第五步：**你的目标文件里全是"欠条"**。凡是引用了别处定义的符号，那个位置暂时填 0，等链接器拿真实地址来赎。

## 3. 正式定义

**翻译流水线**：源程序 $S$ 经一串工具变换为进程 $P$：

$$S \xrightarrow{\text{cpp}} I \xrightarrow{\text{cc1}} A \xrightarrow{\text{as}} O \xrightarrow{\text{ld}} E \xrightarrow{\text{execve}} P$$

| 符号 | 产物 | 是谁 | 关键动作 |
| --- | --- | --- | --- |
| $S$ | `hello.c` | 编辑器 | 人写的文本，含预处理指令 |
| $I$ | `hello.i` | 预处理器 cpp | 展开头文件与宏，仍是 C 文本 |
| $A$ | `hello.s` | 编译器 cc1 | 词法→语法→语义→IR 优化→目标汇编 |
| $O$ | `hello.o` | 汇编器 as | 指令逐条编码，产出**可重定位**目标文件 |
| $E$ | `a.out` | 链接器 ld | **符号解析 + 重定位**，地址最终确定 |
| $P$ | 进程 | 装载器 + CPU | 建页表、映射段、装栈，PC 指向 `_start` |

**重定位（relocation）**：目标文件里每条引用外部符号的指令旁边都留着一张**重定位条目**，写着"这里的字节要改成符号 $s$ 的最终地址，计算方式是 $A + S$（或 $S - P$ 等）"。链接器做的就是在合并所有段之后，按条目把字节填回去。

**地址空间（address space）**：进程看到的一整套地址。x86-64 上用户空间是 47 位，即 $2^{47}$ 字节 = **128 TB**；从低到高依次是 `.text`（代码）、`.data/.bss`（全局数据）、堆（向高地址长）、mmap 区、栈（向低地址长）、最顶端是内核空间。

## 4. 分步例题

**例**：函数 `add(a, b)` 编译后有三条指令，机器码为 `89 f8 | 01 f0 | c3`。问：这个函数占几个字节？若它被链接到基址 `0x401000`，第三条指令的地址是多少？

1. 查长度：`89 f8` 是 2 字节（`mov %edi,%eax`），`01 f0` 是 2 字节（`add %esi,%eax`），`c3` 是 1 字节（`ret`）；
2. 求和：$2 + 2 + 1 = 5$ 字节（x86-64 指令长度**不固定**，在 1~15 字节之间，必须逐条译码才知道下一条从哪开始）；
3. 定地址：基址 `0x401000` 是第 0 字节；第 2 字节处是 `0x401002`；`ret` 在第 4 字节处，所以是 `0x401004`；
4. 反汇编器之所以能"从中间开始读也对得上"，是因为它先译码定长，再往后跳——**指令长度本身就是编码的一部分**。

### 实验 1（lab）：点一个方框，看这道工序的产物

```lab

```

点画布上任一阶段，下方会显示它的**输入 → 输出**与工具名；再切下面的 "C 源码 / 汇编 / 机器码" 三个标签看同一段函数 `add` 的三种形态。注意机器码那一行最右边的注释：三条指令一共 5 字节。

做三个观察：

- 停在"编译"这一步——它是唯一一个**换语言**的工序（C → 汇编），其余工序都只是换表示；
- 停在"汇编"——产物 `hello.o` 里地址全是 0，`nm hello.o` 会看到一堆 `U`（undefined，欠条）；
- 停在"链接"——欠条被赎清，同时 `libc` 也被拉了进来。这就是为什么一个几十字节的 hello world，动态链接后约 **16 KB**、静态链接后能到 **800 KB**。

### 实验 2（python）：手算一次重定位

```python title="目标文件里的欠条是怎么被赎清的"
# 两个模块：main.o 引用了 add.o 里定义的 add
modules = {                      # 字典：模块名 → {符号: 在本模块内的偏移}
    "main.o": {"main": 0x0000},
    "add.o":  {"add":  0x0020},
}
base = {"main.o": 0x401000, "add.o": 0x401000}   # 链接脚本给出的段基址

# 重定位条目：(所在模块, 要修补的字节位置, 引用的符号, 计算方式)
relocs = [
    ("main.o", 0x0009, "add", "S + A - P"),  # S = 符号最终地址，A = 加数，P = 被修补处
]

final = {}                       # 符号名 → 最终绝对地址
for mod, tbl in modules.items():
    for name, off in tbl.items():
        final[name] = base[mod] + off          # 绝对地址 = 段基址 + 段内偏移

for mod, at, sym, how in relocs:          # 元组解包：一次领出四个字段
    addend = -4                            # x86 的 call 是相对下一条指令的偏移
    value = final[sym] + addend - (base[mod] + at + 4)
    print(f"{mod}+0x{at:04x}  {sym}  →  写入 {value}（{how}，相对寻址）")

print("符号最终地址:", {k: hex(v) for k, v in final.items()})
```

输出里 `add` 的最终地址是 `0x401020`，而写进 `call` 指令的是**相对偏移**而不是绝对地址——这就是位置无关代码的雏形：只要相对量不变，整段代码搬到哪儿都能跑。

### 快问快答

```quiz
目标文件 hello.o 里，对 printf 的调用地址为什么暂时填 0？
- 因为 printf 的参数还没准备好
- 因为 printf 定义在别处，汇编时无从知道它最终落在哪个地址 [*]
- 因为编译器故意留空，让操作系统运行时再填
? 编译是以「单个文件」为单位进行的，编译器看不见 libc。地址只能等链接器把所有 .o 拼在一起、排好段之后才算得出来——那一格填 0 是占位，旁边的重定位条目才是真正的欠条。
```

:::warning[常见误区]

**误区一**："`gcc hello.c` 就是编译。"
你以为一条命令一道工序——其实 gcc 只是个**驱动程序**，它悄悄依次调了 cpp、cc1、as、ld 四个程序。加 `-v` 就能看到这四次调用，加 `-save-temps` 能把中间产物 `.i/.s/.o` 全留下来。**"编译"严格说只指 cc1 那一步。**

**误区二**："链接就是把几个文件首尾相接拼起来。"
你以为它只做拼接——其实链接器干两件事：**符号解析**（每个未定义符号必须找到唯一的定义，否则 `undefined reference`；找到两个则 `multiple definition`），以及**重定位**（按条目回填字节）。拼段只是副产品。

**误区三**："磁盘上的可执行文件里，地址就是运行时用到的地址。"
你以为地址是写死的——现代系统默认开启 **ASLR**（地址空间布局随机化），同一个程序每次运行的堆、栈、共享库基址都不同。所以可执行文件里存的多半是**相对量**，装载时再加随机偏移，这正是实验 2 里那个 `value` 的含义。

:::

## 6. 练习

**练习 1**：链接器算出 `add` 的最终地址后，忘了加上模块基址。修到输出 `0x401129`：

```exercise
# @title: 练习：链接器填的到底是什么地址
# @check: 0x401129
# @hint: 符号的绝对地址 = 段基址 + 符号在段内的偏移。代码只算了偏移
base = 0x400000     # 链接脚本给 .text 定的基址
offset = 0x1129     # 符号在段内的偏移
addr = offset       # ← 问题在这：只对「基址为 0」的目标文件成立
print(hex(addr))
```

**练习 2**：`add` 函数共 5 字节，被放在 `0x401020`；紧接着是 `main`，共 32 字节。问 `main` 的起始地址、以及两个函数之后第一个空闲字节的地址。

<details>
<summary>点开查看逐步解答</summary>

1. `add` 占 `0x401020` ~ `0x401024`（5 字节，右端点不含）；
2. 链接器通常按 **16 字节对齐**存放函数（利于指令预取），所以 `main` 从 `0x401030` 开始；
3. `main` 占 32 字节，到 `0x401050` 结束；
4. 所以第一个空闲字节是 `0x401050`。

对齐造成的那 11 字节空隙叫 **padding**，它不装任何指令，纯粹为了让 CPU 取指更省事——"空间换时间"在计算机系统里无处不在。

</details>

## 7. 选读：静态链接、动态链接与位置无关代码

<details>
<summary>选读 · 三种链接方式的取舍</summary>

**静态链接**（`gcc -static`）：把 libc 里用到的部分整份拷进可执行文件。优点是启动时没有外部依赖、没有符号查找开销；缺点是每个程序都带一份 libc ——一千个进程就是一千份相同的代码页。

**动态链接**（默认）：可执行文件里只记"我需要 `libc.so.6` 里的 `printf`"。装载时由动态链接器 `ld.so` 把共享库映射进来，第一次调用时再通过 **PLT/GOT** 两张表把地址补上（惰性绑定）。所有进程共享同一份物理页——这正是第 20 课要说的事。

**位置无关代码（`-fPIC`）**：共享库被映射到哪个地址事先不知道，所以库内部的一切引用都必须用**相对量**表达，全局符号则统一走 GOT 这张间接表。代价是每次访问全局变量多一次内存读取；收益是代码页可以在任意进程间共享。

一句话：**静态链接买启动速度，动态链接买内存与可维护性，PIC 是为共享付出的技术代价。**

</details>
