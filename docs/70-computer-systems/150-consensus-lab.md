# 分布式一致性

## 1. 从一个场景开始

五台机器组成一个集群，存同一份账本。现在两台宕机，一条网线还被挖断了。

剩下的机器仍然要回答一个问题：**账户余额是多少？** 而且它们给出的答案必须**一模一样**——不能纽约说是 100、东京说是 80。

问题是：没有任何一台机器知道全局真相，消息会延迟、会丢失、会乱序。**"同时"这个概念在分布式系统里根本不存在**，可我们偏偏要在这样的世界里达成一致。

## 2. 直觉解释

分布式一致性就是**一群人开会做决定**：

- 不能指望所有人都在场（有人请假、有人掉线），于是规定**过半数同意即通过**（多数派 / quorum）；
- 关键洞察：**任意两届会议的多数派，一定至少有一个人参加了两届**。这个人成了"记忆的载体"，把上一届的决议带到下一届；
- 于是规则变成：**想当主持人（leader），必须先证明你知道的至少和大家一样多**。

这就是 Raft 的全部直觉：**选一个主，让主来定顺序，用多数派把顺序固化下来。**

## 3. 正式定义

**共识（consensus）**：多个节点就某个值达成一致，满足三条性质：

| 性质 | 内容 |
| --- | --- |
| 一致性（Agreement） | 所有**达成决定**的节点，决定的是同一个值 |
| 有效性（Validity） | 被决定的值必须是某个节点**真正提议过**的 |
| 终止性（Termination） | 所有未崩溃的节点最终都会做出决定 |

**多数派（quorum）**：$n$ 个节点中，大小为

$$q = \left\lfloor \frac{n}{2} \right\rfloor + 1$$

的任何子集。**任意两个多数派必定相交**（因为 $2q > n$），这是全部安全性的根基。

**容错能力**：$n = 2f + 1$ 个节点可容忍 $f$ 个节点故障。3 节点忍 1 个、5 节点忍 2 个、7 节点忍 3 个——**所以集群几乎总是奇数个节点**，4 节点的容错能力与 3 节点相同却更贵。

**Raft 的三块积木**：

| 机制 | 内容 | 靠什么保证 |
| --- | --- | --- |
| 领导者选举 | 节点分 follower / candidate / leader；follower 超时未收到心跳则自增**任期（term）**并发起投票；拿到多数票即成 leader | 每个任期每个节点**只能投一票**，且随机超时（**150~300 ms**）让分裂投票极少发生 |
| 日志复制 | leader 把每条命令追加到自己的日志，并行发给所有 follower；**多数派复制完成即提交（commit）** | 已提交的条目必然存在于至少一个多数派里 |
| 安全性 | 投票时拒绝"日志不如自己新"的候选人（比较最后一条的任期与下标） | 已提交的条目一定会被新 leader 看到，因此**永远不会被覆盖** |

**真实量级**（etcd 默认值，与 Raft 论文同量级）：心跳间隔 **100 ms**，选举超时 **1000 ms**。也就是说，正常情况下每秒 10 次心跳；一旦 leader 失联，最多约 1 秒后就会有节点发起选举。

## 4. 分步例题

**例**：5 节点集群，网络被切成 3 + 2 两个分区。问：两个分区各能继续服务吗？

1. 多数派 $q = \lfloor 5/2 \rfloor + 1 = 3$；
2. **3 节点分区**：仍满足多数派 → 可以选出 leader、可以提交写入 → **继续服务**；
3. **2 节点分区**：$2 < 3$，任何写入都拿不到多数票 → 写入**永远无法提交**，读也可能拿到旧值 → 拒绝服务；
4. 分区恢复后：少数派那两台发现自己的任期落后，自动退回 follower，并**以多数派的日志为准**回滚自己那些未提交的条目；
5. 结论：分区期间系统**选择了 C（一致性）而放弃了 A（可用性）**——少数派宁可拒绝服务，也不给出可能错误的答案。这就是 CAP 定理的现场。

## 5. 动手实验

### 实验 1（lab）：五台机器，亲手制造故障

```lab
{
  "type": "consensus-lab",
  "title": "Raft：选主、日志复制与多数派提交"
}
```

按钮依次是：提议写入、注入/恢复网络分区、随机宕机一个、重置。**点画布上任一节点**可以把它宕机或拉起。实心方块是已提交的日志条目，空心方块是只在本地的。

按这个顺序玩：

- 先看它自己选出 leader（读数里 "Leader: N?"），心跳小圆点不断从 leader 飞向 follower；
- 点几次"提议写入 x=n"：日志先落在 leader（空心），一两轮心跳后变实心（**已提交 = 多数派复制完**）；
- 点"注入网络分区"：N3、N4 被划到右侧。它们收不到心跳，会不断发起选举但**永远拿不到多数票**（提示栏会说清楚）；此时再"提议写入"——主分区仍能提交；
- 点"随机宕机一个"：只要活着的不低于 3 个，服务不中断；
- 恢复分区：低任期的旧 leader 自动下台，未提交的条目被覆盖。

### 实验 2（python）：为什么多数派必须"超过一半"

```python title="两个多数派必然相交——这是安全性的全部根基"
def quorum(n, rule):
    if rule == "half":
        return n // 2                 # 错误的定义：只要一半
    return n // 2 + 1                 # 正确的定义：严格超过一半

print(f"{'节点数':>6}{'半数':>8}{'多数派':>10}{'容忍故障':>10}")
for n in [3, 5, 7, 9]:
    print(f"{n:>6}{quorum(n, 'half'):>8}{quorum(n, 'majority'):>10}{(n - 1) // 2:>10}")

n = 5
q = quorum(n, "majority")
print(f"\n5 节点、多数派 {q}：任取两组各 {q} 个，交集至少 {2 * q - n} 个 → 必有重叠")
half = quorum(n, "half")
print(f"若按「半数」{half}：两组各 {half} 个，可以完全不相交（{half} + {half} = {2 * half} ≤ {n}）→ 出现两个决议")

print("\n→ 结论：新 leader 的当选多数派 与 旧条目的提交多数派 必有一个公共节点，")
print("  它一定带着那条已提交的日志，所以已提交的东西永远不会被覆盖。")
```

最后那两行就是 Raft 安全性论证的核心：**不是靠"检查日志新旧"这条规则本身，而是靠两个多数派必然相交这个组合事实。** 日志比较规则只是把"交集里那个节点带着日志"这件事表达出来的手段。

### 快问快答

```quiz
5 节点集群被网络切成 3 + 2 两个分区，2 节点的那一半会怎么样？
- 继续正常服务，因为它还有 2 台机器
- 无法选出 leader、也无法提交任何写入，因为拿不到多数票（需要 3 票） [*]
- 会自己把数据同步给另一半
? 多数派是 ⌊5/2⌋+1 = 3。少数派分区里的节点会不断超时、发起选举、term 越涨越高，但永远拿不到 3 票。这正是 CAP 里「分区时牺牲可用性」的具体含义：宁可拒绝服务，也不给出可能与多数派冲突的答案。
```

:::warning[常见误区]

**误区一**："多数派就是'一半以上'，所以 4 个节点里 2 个也算多数。"
你以为一半就够——**必须严格超过一半**：$q = \lfloor n/2 \rfloor + 1$。6 个节点需要 **4** 票而不是 3 票，因为两组各 3 个可以完全不相交，各自通过不同的决议。**这也是为什么集群规模几乎总是奇数**：4 节点与 3 节点都只容忍 1 个故障，但要多养一台机器。

**误区二**："用了 Raft / Paxos，系统就是强一致的。"
你以为共识算法等于强一致——共识保证的是**日志顺序一致**，不等于**读到的值是最新**。若客户端把读请求发给一个落后的 follower（或 Leader 因分区被隔离却仍认为自己是 leader，即"僵尸 leader"），会读到旧值。要拿到**线性一致**的读，需要 leader 先确认自己仍是 leader（发一轮心跳拿到多数派响应），或用 **ReadIndex / Lease Read** 机制。

**误区三**："CAP 说三选二，所以我选 CA 就既一致又可用。"
你以为能一直三选二——**P（分区容忍）不是可选项**：网络分区是物理事实，你无法选择"不要分区"。CAP 的真实含义是：**当分区发生时，你只能在 C 与 A 之间选一个**；分区不发生时（正常情况），系统可以同时满足 C 与 A。所以更准确的表述是"**PACELC**"：分区时（P）在 A 与 C 间权衡，否则（E）在延迟（L）与一致性（C）间权衡。

:::

**练习 2**：3 节点集群（A、B、C），A 是 leader。此时 A 与 B、C 之间的网络断开（A 被隔离），B 与 C 之间正常。

1. 接下来会发生什么？
2. 若客户端仍在向 A 写入，这些写入会怎样？
3. 网络恢复后，A 的那些未提交条目会怎样？

<details>
<summary>点开查看逐步解答</summary>

1. B、C 收不到心跳，其中之一超时后自增任期、发起选举，从对方那里拿到 1 票，加上自己共 2 票 = 多数派（$\lfloor 3/2 \rfloor + 1 = 2$）→ **选出新 leader，任期 +1**；
2. A 仍是 leader 且收到写请求，但它**拿不到多数派的复制确认**（B、C 都不响应），所以这些条目**永远停在"未提交"状态**，客户端只会等到超时。这就是"僵尸 leader"——它还在，但已经做不了任何决定；
3. 网络恢复后，A 收到更高任期的消息，**立刻退回 follower**，并把自己的日志**以新 leader 的为准截断**：那些未提交的条目被丢弃；
4. **关键点**：已提交的条目不会丢——因为它们已经在多数派里，而新 leader 的选举多数派与那个多数派必有交集。这就是练习里"两个多数派必然相交"的用处；
5. 工程启示：**给客户端的写请求一定要设超时，并且超时后必须重试（带幂等键），因为"超时"可能意味着成功、失败，或者"根本没人处理"。**

</details>

## 7. 选读：FLP 不可能结果与"用随机性绕过它"

<details>
<summary>选读 · 为什么共识不可能被「完美」解决</summary>

1985 年，Fischer、Lynch 与 Paterson 证明了分布式系统里最著名的一个**不可能结果**：

> **FLP 不可能结果**：在**异步**系统模型下（消息延迟没有上界，但消息最终会送达），即使**只有一个**节点可能崩溃，也不存在任何确定性算法能保证在有限时间内达成共识。

证明的思想异常优雅：存在一种"**双歧（bivalent）**"的初始状态——从这里出发，系统既可能最终决定 0，也可能决定 1，取决于消息到达的顺序。若能证明从任何双歧状态出发，都存在一条"继续双歧"的消息调度路径（即可以把决定无限推迟），那么算法就永远可能不终止。

**这条定理不是说共识做不到，而是说"完美"做不到。** 工程上绕过它有三条路：

1. **放宽异步假设**：Raft / Paxos 用**超时**来"假装"系统是同步的——多数情况下消息在超时前到达，算法正常推进；一旦超时机制失效（网络极慢），它们确实可能长时间无法选出 leader。**这恰恰是 FLP 预言的行为。**
2. **随机化**：让节点在发起选举前随机等待一段时间（Raft 的 150~300 ms 随机超时），把"同时举手"的概率压到极低。**不是消除冲突，而是让冲突的概率趋近于零。**
3. **引入部分同步或故障检测器**：在"最终同步"的模型下，共识可解。

**一句话**：共识不是被"解决"了，而是被"在大多数时候"解决了。剩下的那一点点不确定性，就是你设超时、做重试、写幂等逻辑的原因。

</details>
