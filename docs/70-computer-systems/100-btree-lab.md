# 索引与 B 树

## 1. 从一个场景开始

一张两千万行的用户表，按主键查一行：**3 次磁盘 I/O**。

二十年前的人会觉得这是魔法。今天它只是常识——而制造这个魔法的不是更快的硬盘，是一个**又矮又胖的树**。

## 2. 直觉解释

二叉搜索树在内存里很棒，在磁盘上却是灾难：**每向下一层，就是一次磁盘 I/O（约 10 ms）**。一百万个键的二叉搜索树高约 20，一次查询 200 ms——慢到不能忍。

关键洞察：**磁盘不是按字节读的，是按"块"读的。** 你读 1 字节和读 4 KB 花的时间几乎一样。既然一次能白拿 4 KB，为什么要放一个键？

于是 B 树的设计原则只有一句话：**让一个节点刚好等于一个磁盘页**，节点里塞满键与指针。树因此变得极矮（3~4 层）极胖（上千个分叉）。

$$\text{磁盘 I/O 次数} = \text{树高} \quad\Longrightarrow\quad \text{优化目标从"比较次数"变成"树高"}$$

## 3. 正式定义

**$m$ 阶 B 树**：满足下列条件的多路搜索树

| 约束 | 内容 |
| --- | --- |
| 键数上限 | 每个节点最多 $m-1$ 个键、最多 $m$ 个孩子 |
| 键数下限 | 除根外，每个节点至少 $\lceil m/2 \rceil - 1$ 个键 |
| 平衡性 | **所有叶子在同一层**（这是它平衡的保证） |
| 有序性 | 节点内键升序；第 $i$ 个子树里的键介于第 $i-1$ 与第 $i$ 个键之间 |

**树高上界**（$n$ 个键、阶 $m$）：

$$h \le 1 + \log_{\lceil m/2 \rceil}\!\left(\frac{n+1}{2}\right)$$

注意底数是 $\lceil m/2 \rceil$ 而不是 $m$——**上界要按"最坏填充率"算**。

**B+ 树**（数据库的实际选择）与 B 树的两点差别：

1. **数据只在叶子上**：内部节点只存键与指针，所以同样一页能塞更多键 → 扇出更大 → 树更矮；
2. **叶子用链表串起来**：范围查询（"id 在 1000 到 2000 之间"）只需定位到起点，然后顺着链表扫，不用反复回到根。

**真实量级**（MySQL InnoDB）：页大小 **16 KB**，主键为 BIGINT（8 字节）+ 页指针（6 字节）= 14 字节/项 → 扇出 $\approx 16384 / 14 \approx 1170$。若每行约 200 字节，一个叶页放约 80 行，则：

- 2000 万行 → 叶页 25 万个 → 树高 **3**；
- 10 亿行 → 叶页 1250 万个 → 树高 **4**。

**这就是"3 次 I/O 查到一行"的全部秘密：不是硬盘快，是树矮。**

## 4. 分步例题

**例**：把键 10、20、30 依次插入一棵 3 阶 B 树（每节点最多 2 个键）。

1. 插入 10：叶子为空，直接放 → `[10]`；
2. 插入 20：仍不满 → `[10, 20]`（节点内保持升序）；
3. 插入 30：节点满了（3 个键 > $m-1 = 2$），**必须分裂**；
4. 分裂：取中间键 20 **上移**成新的根，剩下 `[10]` 与 `[30]` 做它的左右孩子；
5. 结果：根 `[20]`，两个叶子 `[10]`、`[30]`，树高从 1 变成 2；
6. **关键性质**：B 树只在**分裂时增高**，而且是从底部往上"长"出来的——它永远不会像二叉搜索树那样在某一侧悄悄长偏。

删除是分裂的逆过程：节点键数低于下限时，先向**兄弟借**；两边都借不到，就与兄弟**合并**，合并可能让父节点也低于下限，于是级联向上，甚至让整棵树变矮一层。

先用"随机插入 5 个"建一棵小树，再用"◀ 上一步 / 下一步 ▶"逐帧回放每一次分裂。读数里的 **B 树高度 vs BST 高度** 是最值得盯的一栏。

做三组观察：

- 拖"阶数 m"从 3 到 6：插入同样多的键，树高明显下降。**这就是扇出的威力**；
- 节点被填满时边框变红 → 下一次插入必定分裂；
- 删除时看提示："不足半满时先借兄弟，借不到就合并"——点几次"删除"直到树高减 1，那是根被合并空了。

### 实验 2（python）：扇出决定树高

```python title="16 KB 的页能装多少键？树高就是答案"
import math                      # 用其中的 ceil（向上取整）与 log（对数）

page = 16 * 1024                 # InnoDB 页大小 16 KB
entry = 8 + 6                    # BIGINT 键 8 B + 页指针 6 B
fanout = page // entry           # 一个非叶节点能放多少个「键 + 指针」
row_size = 200                   # 假设每行 200 字节
rows_per_leaf = page // row_size # 一个叶页能放多少行

def height(rows):
    leaves = rows / rows_per_leaf                       # 需要多少个叶页
    if leaves <= 1:
        return 1
    return 1 + math.ceil(math.log(leaves) / math.log(fanout))   # 叶子层 + 上面几层

print(f"扇出 ≈ {fanout}，每叶约 {rows_per_leaf} 行")
for rows in [10000, 1000000, 20000000, 1000000000]:
    h = height(rows)
    print(f"{rows:>12} 行 → 树高 {h}（点查最多 {h} 次磁盘 I/O，约 {h * 10} ms）")

# 对比：同样 2000 万行，用二叉搜索树要多少次 I/O？
n = 20000000
print(f"\n二叉搜索树：树高约 {math.ceil(math.log(n) / math.log(2))} → 约 {math.ceil(math.log(n) / math.log(2)) * 10} ms")
```

`3 → 30 ms` 与 `25 → 250 ms`，差了近十倍；这还是假设磁盘 10 ms 的机械盘。换成 SSD（约 0.1 ms），两者都很快，但**树高依然决定了比较次数与缓存未命中次数**。

### 快问快答

```quiz
数据库索引为什么几乎都用 B+ 树而不是 B 树？
- 因为 B+ 树的插入更快
- 因为 B+ 树把数据只放在叶子，内部节点能塞更多键 → 扇出更大、树更矮，而且叶子链表让范围扫描不必反复回到根 [*]
- 因为 B 树不支持删除
? 「内部节点只存键」意味着同样一页能放下几倍的键，扇出从几百涨到上千，树高直接少一层。而范围查询（BETWEEN、ORDER BY LIMIT）在 B 树里要反复中序遍历回根，在 B+ 树里顺着叶子链表一路扫过去就行。
```

:::warning[常见误区]

**误区一**："索引越多越好。"
你以为索引是免费的——**每多一个索引，每一次 INSERT/UPDATE/DELETE 就多一次 B 树维护**（可能触发分裂、合并、甚至页迁移），还要多占磁盘与缓冲池。真实系统里"索引太多导致写入变慢"比"索引太少导致查询变慢"更常见。**索引是拿写性能换读性能，换多少要算。**

**误区二**："有了 B 树索引，任何查询都会走索引。"
你以为建了索引就一定会用——**索引失效的经典场景**：对索引列套函数（`WHERE YEAR(date) = 2026`）、类型不匹配（字符串列传数字）、前导列不匹配（复合索引 `(a, b)` 只查 `b`）、或者优化器估算出"要回表的行数超过全表的 20~30%"从而干脆选择全表扫描。**索引不是开关，是优化器成本模型里的一个选项。**

**误区三**："哈希索引查找是 $O(1)$，比 B 树的 $O(\log n)$ 快，所以更好。"
你以为复杂度小就快——哈希只能做**等值查询**，做不了范围查询、排序、`LIKE 'abc%'` 前缀匹配，也不支持"最左前缀"。而"查一个区间的订单""按时间排序取最新十条"才是数据库里最常见的操作。**选索引结构时，先问查询形状，再问复杂度。**

:::

## 6. 练习

**练习 1**：这段算树高上界的代码给出 4，可最坏情况其实是 5。修到输出 `5`：

```exercise
# @title: 练习：树高上界的底数用错了
# @check: 5
# @hint: 上界必须按「最坏填充率」算，也就是每个节点只有最少分支数 ⌈m/2⌉ 个孩子。代码用了最多的分支数 m，算出来偏乐观
import math                      # 用其中的 ceil（向上取整）与 log（对数）

n = 1000000                      # 一百万个键
m = 128                          # 阶数：每节点最多 m-1 个键、最多 m 个孩子
branch = m                       # ← 问题在这：上界该用 ceil(m/2)，即 (m + 1) // 2
h = 1 + math.ceil(math.log((n + 1) / 2) / math.log(branch))
print(h)
```

**练习 2**：InnoDB 页 16 KB，主键 8 字节、指针 6 字节。若改用 UUID（16 字节）当主键，扇出变成多少？对 2000 万行的表，树高会多出一层吗？

<details>
<summary>点开查看逐步解答</summary>

1. 每项变成 $16 + 6 = 22$ 字节，扇出 $= 16384 / 22 \approx 744$（原来约 1170）；
2. 2000 万行、每叶约 80 行 → 叶页 25 万个；$\log_{744}(250000) = \ln 250000 / \ln 744 = 12.43 / 6.61 \approx 1.88$ → 向上取整 2 → 树高仍是 **3**；
3. 但代价是实打实的：扇出从 1170 掉到 744（**−36%**），每个内部节点能覆盖的范围缩水，同样的数据需要更多页，**缓冲池能缓存的索引页占比下降**，命中率随之下降；
4. 更糟的是 UUID 是**随机**的：新行插入的位置均匀分布，每次插入都可能触发页分裂与随机 I/O。而自增主键永远插在最右边，**顺序写、页利用率高**。这就是"为什么别用 UUID 当聚簇主键"的定量理由。

</details>

## 7. 选读：聚簇索引、二级索引与回表

<details>
<summary>选读 · 为什么「主键怎么选」会影响一切</summary>

**聚簇索引（clustered index）**：InnoDB 里，表数据本身就存在主键 B+ 树的叶子上——**整张表就是那棵树**。所以主键的选择决定了行的物理存放顺序。

**二级索引（secondary index）**：另一棵独立的 B+ 树，叶子上存的不是整行，而是"索引键 + 主键值"。用二级索引查整行时，要**先查二级索引拿到主键，再回主键树查一次**——这第二次叫**回表（bookmark lookup）**，通常是慢查询的主要来源。

两个推论：

- **覆盖索引（covering index）**：如果二级索引的叶子上已经包含了查询需要的全部列，就不必回表。`EXPLAIN` 里出现 `Using index` 就是在说这件事；
- **主键越长，所有二级索引都跟着变大**——因为每个二级索引的叶子都要存一份主键值。用 UUID 当主键时，这个代价会被每个索引放大一遍。

于是"主键怎么选"从一道小题变成了一道系统题：**自增 BIGINT 主键 + 业务唯一键做二级索引**，是绝大多数 OLTP 场景的稳妥解。

</details>
