# 从需求到样机：设计闭环

## 1. 从一个场景开始

两个团队各做一台相机云台。甲队：v1"功能全了"，v2 改电源，v3 改通信，v4 改结构——每版之间没有"为什么改"的记录，改 A 坏 B，第八版还在打转。乙队：v1 带着测试大纲出生，v2 就收敛定型。

差别不在聪明程度，在**把设计当流水线还是当闭环**：流水线以为需求→方案→实现走一遍就完；闭环知道**测试测出的偏差必须回流**——回流到模型、回流到方案、甚至回流到需求本身。这是工程控制论里"反馈"思想在开发流程上的投影：没有反馈的回路，误差只会累积。

本课做三件事：把闭环拆成八个环节、把"指标打架"数学化（帕累托前沿与加权取舍）、再演练一遍偏差清单的用法。

## 2. 直觉解释

**八环节闭环**像医院的诊疗循环：**需求**（主诉）→ **指标分解**（化验单：把"手感顺滑"翻译成可测的数）→ **方案**（选疗法）→ **建模**（病理模型）→ **仿真**（药理推演）→ **样机**（临床一期）→ **测试**（复诊数据）→ **迭代**（改处方）——最后一环绕回第一环，因为有的偏差要改的其实是"诊断"本身。

两个最容易被跳过的直觉：

- **指标会打架**。响应快 vs 功耗低、带宽高 vs 成本低、精度高 vs 体积小——**不存在两全的最优解，只存在一条"不可再两全"的前沿**（帕累托前沿）：站在线上，想再快一点，就必须多耗一点电。设计不是"找到最优点"，是**在前沿上选一个符合产品定位的点**；
- **偏差清单是闭环的心跳**。每次测试记下"实测 vs 指标"的差，每轮迭代对着清单逐条销账。清单变短，闭环健康；清单只是变长，你做的不是迭代，是随机游走。

## 3. 正式定义

**闭环八环节**（每环的输入输出）：

| 环节 | 输入 | 输出 |
| --- | --- | --- |
| 1 需求 | 用户/市场需求 | 需求规格（功能 + 约束） |
| 2 指标分解 | 需求规格 | 可验证的量化指标 |
| 3 方案 | 量化指标 | 候选架构与关键选型 |
| 4 建模 | 选定架构 | 数学模型 / 状态方程 |
| 5 仿真 | 模型 + 工况 | 性能预测、敏感度 |
| 6 样机 | 仿真确认的参数 | 可测试的物理样机 |
| 7 测试 | 样机 + 测试大纲 | 实测数据、偏差清单 |
| 8 迭代 | 偏差清单 | 改设计 / 改模型 / 改指标 |

**带宽-上升时间关系**（引用控制系统经典结论，带宽取控制频率的十分之一）：

$$t_r \approx \frac{0.35}{f_{bw}}, \qquad f_{bw} \approx \frac{f}{10} \;\Longrightarrow\; t_r \approx \frac{3.5}{f}$$

**功耗模型**（静态 + 开关损耗，引用数字电路动态功耗随频率线性上升的结构）：

$$P(f) = P_0 + kf$$

**加权归一代价**（响应权重 $w$、功耗权重 $1-w$，各自除以本方案的"最差值"做归一）：

$$J(f) = w\,\frac{t_r(f)}{t_{r,\max}} + (1-w)\,\frac{P(f)}{P_{\max}}, \qquad w \in [0,1]$$

**帕累托前沿**：可行方案集中，不被任何其他方案**同时**在两项指标上不劣且至少一项更优的方案集合。

| 符号 | 名字 | 单位 | 含义 |
| --- | --- | --- | --- |
| $t_r$ | 上升时间 | ms | 阶跃响应的 10%→90% 时间 |
| $f$ | 控制频率 | Hz | 控制环离散执行频率 |
| $P(f)$ | 平均功耗 | mW | 随控制频率线性增长 |
| $w$ | 响应权重 | — | 越大越偏重"快"，越小越偏重"省" |
| $J$ | 综合代价 | — | 归一加权后的单一目标 |

## 4. 分步例题

**例**：云台的控制频率可在 10~1000 Hz 之间取。$t_r = 3.5/f$ ms（最快档 $t_{r,\max}=350$ ms），$P = 20+0.08f$ mW（最费档 $P_{\max}=100$ mW）。产品定位"均衡"，取 $w=0.5$，求最优控制频率；再对比"性能优先"（$w=0.9$）。

1. **写代价**：$J(f) = 0.5\times\dfrac{3500/f}{350} + 0.5\times\dfrac{20+0.08f}{100} = \dfrac{5}{f} + 0.1 + 0.0004f$；
2. **三点试算**：$J(10) = 0.604$；$J(112) \approx 0.189$；$J(1000) = 0.505$——两端都差，中间低；
3. **极小点**（对 $f$ 求导置零，$5/f^2 = 0.0004$）：$f \approx 112$ Hz，$J \approx 0.189$；
4. **换权重**：$w = 0.9$ 时 $J = 9/f + 0.02 + 0.00008f$，极小点移到 $f \approx 335$ Hz；
5. **读结论**：权重从 0.5 滑到 0.9，最优控制频率从 112 Hz 滑到 335 Hz——**最优点沿帕累托前沿滑动**。没有哪个 $f$ "绝对最优"：均衡型产品选 112，竞技型选 335，**产品定位（权重）才是设计参数的真正来源**。

## 5. 动手实验

### 实验 1（lab）：八环节闭环与帕累托前沿

```lab
{
  "type": "design-closure",
  "title": "设计闭环：八环节与快慢-功耗取舍",
  "sliders": [
    { "name": "w", "label": "响应速度权重（0=只看功耗）", "min": 0, "max": 1, "step": 0.02, "value": 0.5 }
  ]
}
```

画布上半部是八个环节围成的闭环（**点击任一圆点**，读数面板给出该环节的输入、输出与常用工具——从"访谈、KANO"到"根因分析、DOE"）；下半部是帕累托前沿曲线与当前权重下的最优点。值得做的三件事：

- **把 w 从 0 拖到 1**：黄色最优点沿前沿从省电端滑到响应端——亲手验证"权重决定取舍"；
- **点第 2 环"指标分解"**：看它把"需求规格"变成"可验证的量化指标"——**这是整个闭环里最便宜、也最值钱的一环**，指标写错后面七环全白干；
- **点第 8 环"迭代"**：它的输入是"实测 vs 指标的偏差"、输出有三种流向（改设计/改模型/**改指标**）——允许指标被实测修正，闭环才算真的闭合。

### 实验 2（python）：权重扫一遍，最优点滑多远

```python title="权重变化时最优控制频率的轨迹"
def tr(f):           # 上升时间 ms：带宽 ≈ f/10，tr ≈ 0.35/带宽
    return 3500 / f
def p(f):            # 平均功耗 mW：静态 20 + 开关损耗随频率线性上升
    return 20 + 0.08 * f
TR_MAX, P_MAX = tr(10), p(1000)   # 归一基准：最慢档 / 最费档
for w in (0.1, 0.5, 0.9):         # 响应速度权重三档
    best_f, best_cost = 0, 1e9     # 最优解初值：先放一个无穷大代价
    f = 10.0
    while f <= 1000:               # 对数细扫控制频率（每步乘 1.03）
        cost = w * tr(f)/TR_MAX + (1 - w) * p(f)/P_MAX   # 加权归一代价
        if cost < best_cost:       # 打擂台：遇到更小的代价就换庄
            best_f, best_cost = f, cost
        f *= 1.03
    print("响应权重 %.1f → 最优 %5.0f Hz（tr = %5.1f ms，P = %5.1f mW，J = %.3f）"
          % (w, best_f, tr(best_f), p(best_f), best_cost))
```

三行输出：37 → 112 → 335 Hz。权重从省电滑向响应，最优点沿着前沿走了整整一个数量级。**这就是指标分解的价值**："响应多快才够"不是工程师拍脑袋，是产品定位（权重）+ 前沿（物理）+ 客户预算（约束）三者共同选出来的。

### 快问快答

```quiz
实测发现样机功耗超了指标，但响应速度完全达标。按闭环流程，第一步该做什么？
- 直接降低控制频率，牺牲响应换功耗
- 回到指标分解：确认功耗指标是否合理、响应指标是否留了冗余，再决定往哪边改 [*]
- 更换更省电的芯片，其他不动
? 偏差先回流到「指标」再回流到「设计」：也许响应指标定得过剩（本可用一半带宽），也许功耗指标本就不可达。直接动设计参数而不过指标，就是「随机游走式迭代」——改了功耗，响应悄悄超标都不知道。
```

:::warning[常见误区]

**误区一**：「指标可以边做边定。」
你以为需求自然会长出指标——**不可量化的指标不可验证**："手感顺滑"没法判定完成，只能判定吵架。指标分解就是把"顺滑"翻译成"0→90° 阶跃 ≤ 200 ms、超调 ≤ 5%、稳态误差 ≤ 0.2°"。**指标写得可测量，闭环才转得起来。**

**误区二**：「仿真通过，设计就完成了。」**
你以为绿色波形是验收单——模型永远少算东西：器件公差、温漂、装配应力、线的寄生参数。仿真的正确用途是**比较方案**（A 比 B 好多少），测试才是**判定合格**（到底达没达标）。仿真绿了就投产的团队，样机数量一定超预算——这一条与上一章方法地图课的告诫完全一致。

**误区三**：「闭环就是多改几版。」
你以为迭代次数等于勤奋——**没有偏差清单与根因分析的迭代是随机游走**：每次改动还可能悄悄破坏已达标的其他指标（回归测试就是防这个）。闭环的健康判据只有一条：**偏差清单每一圈都在变短**。变长，说明你改的不是根因。

:::

## 6. 练习

**练习 1**：控制频率 $f = 112$ Hz、$w = 0.5$ 时算综合代价。下面代码把归一化的分母写错了，修到输出 `0.189`：

```exercise
# @title: 练习：归一化的分母写错了
# @check: 0.189
# @hint: 上升时间的归一基准应是「最慢档」350 ms（f=10 Hz 时的 tr），不是最快档 3.5 ms
w = 0.5
f = 112.0
tr = 3500 / f                      # 上升时间 ms
p = 20 + 0.08 * f                  # 功耗 mW
J = w * tr / 3.5 + (1 - w) * p / 100    # ← 问题在这：分母应为 350
print(round(J, 3))
```

**练习 2**：客户要求云台"跟随快"，给出指标"0→90° 阶跃 ≤ 80 ms、整机待机功耗 ≤ 40 mW"。先按 $t_r = 3.5/f$ 估算需要的控制频率，再判断这对指标能否同时满足，最后给出处理建议。

<details>
<summary>点开查看逐步解答</summary>

1. **反解控制频率**：$t_r \le 80$ ms → $f \ge 3.5/0.08 = 43.75$ Hz；留 20% 余量取 $f \approx 55$ Hz；
2. **估功耗**：$P(55) = 20 + 0.08\times55 = 24.4$ mW——若整机其他部分 20 mW，合计 44.4 mW **超过 40 mW 指标**；
3. **上前沿看**：这对指标一个要快、一个要省，正是帕累托冲突。三个出口按闭环顺序走：
4. **先回指标分解**：80 ms 是硬需求吗？若用户真实场景是 120 ms 也够，指标一改全盘皆活；"待机功耗"与"运动功耗"分开定义更合理（待机时控制环降频到 10 Hz，功耗仅 20.8 mW）；
5. **再改设计**：动态调频（空闲降频）——同一闭环，功耗按工况走，两项指标都保住；
6. **最后才是堆料**：换低功耗驱动/芯片是**最贵的解法**，通常也最没必要。
7. **结论**：指标冲突的第一站永远是**指标分解与方案**，不是 BOM 清单。

</details>

## 7. 选读：加权和的盲区——凹前沿与 ε-约束法

<details>
<summary>选读 · 为什么加了权重也未必找到"你要的点"</summary>

把两项目标加权成一个数 $J$，是优化里最常用的**标量化**手法。它保证：**加权最优解一定落在帕累托前沿上**（否则存在两全其美的改进，$J$ 还能更小）。

但它有个盲区：**凹形前沿**。想象前沿中段向内凹进去（"弯回原点"）。加权和的等值线是直线族 $\{J = \text{常数}\}$，切到凹段时，切点常常不是你想要的折中点——**凹段上的非凸解永远取不到**，权重再怎么扫都会跳过它们。

工程里的补法叫 **ε-约束法**：不融合目标，而是把一项硬性约束住（功耗 ≤ ε），对另一项单独求优。换一个 ε，得到前沿上另一个点——这样**凸的凹的都能扫出来**。

顺带一条实际经验：真实产品的取舍往往不止两维（快、省、便宜、小、可靠……）。多维前沿画不出来，但流程不变：**锁定其余项的约束，对最关键的两维画前沿**——闭环里"指标分解"环节产出的指标树，就是为这一步准备的弹药。

</details>
