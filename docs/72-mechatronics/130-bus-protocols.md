# 通信总线：UART、I2C、SPI 与 CAN

## 1. 从一个场景开始

板子上有一颗 MCU、一枚温度传感器、一块 OLED、一片 Flash，还有一台远在强干扰环境里的电机驱动器。它们都要和 MCU"说话"，可引脚只有那么几个：温度传感器只要偶尔报一个数，OLED 刷屏要带宽，Flash 读写要快，驱动器那边干扰满天飞。

四条总线——UART、I2C、SPI、CAN——就是四份不同的"说话合同"。选错合同的症状很统一：**要么慢到刷屏卡顿，要么快到乱码满天飞，要么省了引脚却把整板拖垮。**本课把四份合同的条款逐条读一遍，再算清楚每份合同的"隐形开销"。

## 2. 直觉解释

把四种总线想成四种交流方式：

- **UART 像打电话**：一根发话线、一根受话线，没有"现在开始"的口令。双方必须**事先约好语速**（波特率）——你按 115200 的语速说，我按同样的语速听。语速约错，听到的全是乱码。
- **I2C 像广播点名**：一根数据线、一根时钟线挂在同一间教室里，谁都能听。老师（主机）喊"0x50 号，交作业"，别的设备装没听见，被点到的必须应一声（ACK）。
- **SPI 像一对一门铃专线**：每个从机配一根"门铃"（片选 CS），铃一响就开始对讲，节拍由主机敲。没有点名开销，所以快——但每多一个从机，就多一根门铃线。
- **CAN 像抢话筒的圆桌会议**：谁都可以同时开口，但规则保证 **ID 号小的人嗓门大**——同时说话时，ID 大的发现自己被压过，立刻闭嘴改听。一次"碰撞"不需要重来，赢家的报文一字不损地发完。

四份合同还有一条共通的账：**说话本身有开销**。点名、应答、起止口令都占时间——真正"干活"的数据只占帧里的一部分。开销多少，正是后面要算的账。

## 3. 正式定义

**位时间与速率**：

$$t_b = \frac{1}{R}$$

**帧结构与开销**（每帧传输 $n$ 个数据字节）：

| 总线 | 每帧总位数 $N$ | 说明 |
| --- | --- | --- |
| UART | $10n$ | 每字节 1 起始 + 8 数据 + 1 停止 |
| I2C | $11 + 9n$ | 地址字节 9 位（7 地址 + R/W + ACK）+ 每数据字节 9 位 + 起止 |
| SPI | $8n + 2$ | 几乎纯数据，仅 CS 拉低/抬高各折合 1 位 |
| CAN | $44 + 8n$ | 仲裁段 + 控制段 + CRC + ACK + EOF 等固定开销 |

**有效吞吐与协议效率**：

$$\eta = \frac{8n}{N}, \qquad R_{\text{eff}} = R\,\eta$$

**CAN 非破坏性仲裁**：总线为"线与"——显性位 0 压过隐性位 1；节点边发边听，发出 1 却听到 0 即判负退让，ID 越小优先级越高。

| 符号 | 名字 | 单位 | 含义 |
| --- | --- | --- | --- |
| $t_b$ | 位时间 | 秒 s | 一个比特在总线上占据的时间 |
| $R$ | 总线速率 | bit/s | UART 习惯称波特率，此处每符号 1 bit |
| $N$ | 每帧总位数 | bit | 含全部协议开销 |
| $n$ | 数据字节数 | 字节 | 一帧里的有效负载 |
| $\eta$ | 协议效率 | — | 有效位占总位数的比例 |

## 4. 分步例题

**例**：同一份传感器数据（2 字节）分别走三条总线，速率取各自典型值：UART 115200 bit/s、I2C 400 kHz、CAN 500 kbit/s。求每帧时长与有效吞吐。

1. **UART**：$N = 10 \times 2 = 20$ bit，$t = 20/115200 = 173.6$ µs；$\eta = 16/20 = 80\%$，$R_{\text{eff}} = 92.2$ kbit/s；
2. **I2C**：$N = 11 + 18 = 29$ bit，$t = 29/400000 = 72.5$ µs；$\eta = 16/29 = 55\%$，$R_{\text{eff}} = 220.7$ kbit/s；
3. **CAN**：$N = 44 + 16 = 60$ bit，$t = 60/500000 = 120$ µs；$\eta = 16/60 = 27\%$，$R_{\text{eff}} = 133.3$ kbit/s；
4. **读账本**：CAN 的毛速率是 SPI 常用速率的零头，但它用 44 bit 的固定开销买到了**仲裁、CRC、错误处理与差分抗干扰**。开销不是浪费，是保险费——付不付，取决于你的总线工作在客厅里还是车间里。

图上是逐位的数字波形，读数面板给出位时间、一帧时长、有效吞吐与开销百分比。值得做的四件事：

- 用分段按钮从 UART 切到 I2C：多出一条 SCL 时钟线；SDA 上能看到 START（时钟为高时拉低）、地址 0x50、两个 ACK、STOP——**I2C 的开销全都长在波形上**；
- 切到 SPI：只有 CS/SCLK/MOSI 三条线、数据连着发，开销掉到接近零；再切 SPI 模式 0~3，看采样沿怎么挪——**主从双方 CPOL/CPHA 不一致就是乱码**；
- 切到 CAN：看 CAN_H 与 CAN_L 的差分关系与仲裁段标注；把 n 拖到 8，固定开销 44 bit 不变、占比被摊薄——**帧越长，保险越划算**；
- 把速率档位从 0 拖到 100：位时间以对数刻度缩短，而开销百分比**纹丝不动**——开销是结构性的，提速救不了它。

### 实验 2（python）：把开销账算成表

```python title="同一份数据，四种总线的真实成本"
buses = [   # (名称, 典型速率 bit/s, 帧位数公式)
    ("UART 115200",  115200, lambda n: 10 * n),
    ("I2C 400k",     400000, lambda n: 11 + 9 * n),
    ("SPI 8MHz",   8000000, lambda n: 8 * n + 2),
    ("CAN 500k",    500000, lambda n: 44 + 8 * n),
]
n = 2                                # 一帧 2 字节数据
print("%-14s %10s %10s %7s" % ("总线", "帧时长µs", "有效吞吐", "效率"))
for name, rate, frame_bits in buses: # 逐行解包元组
    bits = frame_bits(n)             # 每帧总位数（含开销）
    t_us = bits / rate * 1e6         # 一帧时长，微秒
    eff = rate * 8 * n / bits / 1000 # 有效吞吐，kbit/s
    print("%-14s %10.1f %9.1fk %6.0f%%" % (name, t_us, eff, 100 * 8 * n / bits))
```

四行输出里 SPI 一骑绝尘——但别急着下结论：**SPI 的 8 MHz 需要短走线与一致的采样模式，I2C 的两根线却能挂十几个设备**。开销表只告诉你"每帧贵多少"；选总线还要数引脚、看距离、看环境——这正是两课之后 EMC 要接着算的账。

### 快问快答

```quiz
两个 CAN 节点同时开始发送，报文 ID 分别是 0x123 和 0x045，总线上的结果是什么？
- ID 大的 0x123 先发完，0x045 等总线空闲后重发
- ID 小的 0x045 赢得仲裁完整发出，0x123 边发边听发现被压过，立刻退让转为接收 [*]
- 两个节点都发送失败，总线报告错误并整体重发
? CAN 是线与逻辑：显性 0 压过隐性 1，而 ID 越小，高位越早出现 0。仲裁段里 0x045 把 0x123 压成隐性，0x123 发现自己发的与听到的不一致即判负，转为接收且不产生错误帧——赢家报文一字不损，这就是「非破坏性仲裁」。
```

:::warning[常见误区]

**误区一**：「波特率拉满，通信就更快了。」
你以为瓶颈在速率——其实**开销是结构性的**：I2C 每字节必付 1 位 ACK，CAN 每帧必付约 44 位固定开销。速率翻倍，帧时长减半，效率百分比一分不变。而速率越高，信号边沿就越接近走线 RC 时间常数（第 68 章 RC 课的 $2.2\tau$），波形变圆、采样出错——**乱码十有八九不是协议错，是物理层撑不住**。

**误区二**：「SPI 快，所以全都用 SPI。」
你以为快就是好——SPI 没有地址、没有 ACK、没有流控：**发错了没人告诉你**；每个从机还要独占一根 CS 线，设备一多引脚先爆。I2C 两根线挂一整条总线、天然支持多主；UART 点对点最省心。**选总线先数引脚与距离，再看带宽。**

**误区三**：「CAN 是因为快才统治汽车。」
你以为汽车图它的速度——CAN 最高只有 1 Mbit/s 且仅限短线。它赢在**差分抗干扰 + 非破坏性仲裁 + CRC 与自动重发**：十几台控制器挂同一对线，优先级高者先说话，大电流电机的干扰也压不垮它。可靠性选型的逻辑是「环境多脏、谁不能错」，不是「谁跑得快」。

:::

**练习 1**：I2C 400 kHz 总线一帧读 2 字节。下面代码把帧位数算少了，修到输出 `72.5`：

```exercise
# @title: 练习：I2C 一帧到底多少位
# @check: 72.5
# @hint: 首字节是「7 位地址 + 1 位读写 + 1 位应答」，加上起止条件折合的 2 位：N = 11 + 9n，不是 9n
rate = 400000        # 总线速率 bit/s
n = 2                # 数据字节数
bits = 9 * n         # ← 问题在这：漏了地址字节与起止条件
t_us = bits / rate * 1e6
print(round(t_us, 1))
```

**练习 2**：一颗压力传感器每 1 ms 上报一次 3 字节数据。用 UART 9600 bit/s 够不够？若不够，给出三个改造方向。

<details>
<summary>点开查看逐步解答</summary>

1. 每帧位数：$N = 10 \times 3 = 30$ bit；
2. 一帧时长：$30/9600 = 3.125$ ms > 1 ms——**不够**，上一帧还没发完，下一帧已经到了；
3. 方向一：**提速率**。提到 38400 bit/s（$30/38400 = 0.78$ ms）以上，代价是时钟精度与走线要求变高；
4. 方向二：**换总线**。挂到板上已有的 I2C 400 kHz 总线复用引脚，或改 SPI；
5. 方向三：**降负载**。改成上位机轮询，或把 3 字节压成 2 字节定点数（牺牲分辨率）。
6. 注意方向三才是嵌入式里最常用的：**带宽不够，先砍需求**——通信预算和内存预算一样，是设计出来的，不是买来的。

</details>

## 7. 选读：UART 为什么要求双方时钟误差不超过约 2%

<details>
<summary>选读 · 异步接收的采样容限推导</summary>

UART 没有时钟线，接收方靠**起始位的下降沿**对齐，之后按约定的 $t_b$ 逐位计数、在每位**中点**采样。

设收发双方位周期的相对偏差为 $\varepsilon$，则采样第 $k$ 位时的累计时间误差为 $k\,\varepsilon\, t_b$。要保证采样本位中点以内，须：

$$k\,\varepsilon\, t_b < \frac{t_b}{2} \quad\Longrightarrow\quad \varepsilon < \frac{1}{2k}$$

10 bit 帧里最晚采样的是停止位（$k \approx 9.5$），得 $\varepsilon < 5\%$——这是**收发双方合计**的预算。若双方各错一半，每边约 2.5%；再扣除起始沿的检测延迟与噪声裕量，工程规范建议**每边不超过 2%**。

这也解释了两件工程事实：115200 这类速率下，MCU 波特率发生器分频凑不出精确值时，宁可换一个整除得到的速率；而**同步总线（SPI/I2C/CAN）没有这条约束**——时钟由主机统一发，从机跟着节拍走。

</details>
