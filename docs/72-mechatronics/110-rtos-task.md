## 1. 从一个场景开始

无人机飞控上同时跑着三个任务：姿态解算每 10 ms 一次、电机控制每 5 ms 一次、遥测上报每 50 ms 一次。它们抢同一个 CPU——谁来决定谁先跑？

如果用桌面操作系统的"时间片轮转"：每个任务分一截时间，跑完就切。可电机控制要是等姿态解算跑完才轮到，5 ms 的截止期早就过了——电机失控、飞机翻滚、摔机。

嵌入式系统的命脉是**截止期**（deadline）：不是"越快越好"，而是"**不能晚于**"。实时操作系统（RTOS）的全部工作就是回答一个问题：**给定一组周期性任务，CPU 来不及怎么办？**——以及更重要的：**来不来得及，能不能提前算出来。**

## 2. 直觉解释

想象三个厨师共一口锅：一个每 10 分钟做一道菜（需 2 分钟）、一个每 15 分钟做一道（需 3 分钟）、一个每 25 分钟做一道（需 2.5 分钟）。谁能保证三道菜都按时上桌？

朴素方案：谁先到谁做，做完才让下一个。这叫**协作式**——坏处是长任务会卡住所有人。

聪明一点：规定谁更紧急谁插队。怎么定"更紧急"？

- **RMS**（速率单调调度）：周期最短的最优先。10 ms 的任务比 50 ms 的更优先——因为它的截止期更紧。简单、静态（优先级固定，不用运行时计算），但不是最优。
- **EDF**（最早截止期优先）：每次都看谁先到期。动态优先级，理论上是**最优**的——如果 EDF 都调度不开，别的算法也不行。

但有个隐藏账：CPU 总占用率 $U = \sum C_i/T_i$。三个任务 $2/10 + 3/15 + 2.5/25 = 0.2 + 0.2 + 0.1 = 0.5$。CPU 只用了 50%，看上去很轻松。可如果 $U > 1$，神仙也救不了——CPU 100% 占满也跑不完。EDF 的临界条件就是 $U \le 1$。RMS 更保守：$U \le n(2^{1/n}-1)$，$n=3$ 时上界只有 0.78——这 0.28 的差距是 RMS 保守性付出的代价。

## 3. 正式定义

$n$ 个周期性任务 $\tau_i = (C_i, T_i)$，$C_i$ 为执行时间，$T_i$ 为周期。截止期 $D_i = T_i$（隐式截止期）。

| 调度策略 | 优先级规则 | 类型 | 可调度上界 |
| --- | --- | --- | --- |
| 协作式 | 先来先做，不可抢占 | 静态 | 无保证 |
| 固定优先级 | 编号小者优先 | 静态 | 取决于优先级分配 |
| RMS | $T_i$ 越短优先级越高 | 静态 | $U \le n(2^{1/n}-1)$ |
| EDF | $D_i$ 最近者最高 | 动态 | $U \le 1$ |

CPU 利用率：

$$
U = \sum_{i=1}^{n} \frac{C_i}{T_i}
$$

RMS 充分条件（Liu & Layland, 1973）：

$$
U \le n\left(2^{1/n} - 1\right)
$$

| $n$ | 上界 |
| ---: | ---: |
| 1 | 1.000 |
| 2 | 0.828 |
| 3 | 0.780 |
| 5 | 0.743 |
| $\infty$ | $\ln 2 \approx 0.693$ |

RMS 上界只是**充分条件**——$U$ 超过上界不代表一定超时，只是没有理论保证。EDF 的 $U \le 1$ 是**充要条件**。

## 4. 分步例题

**例**：三个任务 $\tau_1 = (2, 10)$、$\tau_2 = (3, 15)$、$\tau_3 = (2.5, 25)$（单位 ms）。

1. **利用率**：$U = 0.2 + 0.2 + 0.1 = 0.5$。
2. **RMS 上界**（$n=3$）：$3 \times (2^{1/3}-1) = 0.780$。$0.5 < 0.780$ → RMS 可调度。
3. **EDF 上界**：1.0。$0.5 < 1.0$ → EDF 也可调度。
4. **RMS 优先级**：$\tau_1$（$T=10$）> $\tau_2$（$T=15$）> $\tau_3$（$T=25$）。
5. **验证**：$\tau_1$ 每 10 ms 跑 2 ms，剩余 8 ms；$\tau_2$ 在 $\tau_1$ 跑完后跑 3 ms，$T_2=15$ ms 内够；$\tau_3$ 25 ms 内需要 $2\times 2 + 2\times 3 + 2.5 = 12.5$ ms < 25 ms。无超时。

```lab
  "policy": "rms",
  "C1": 2,
  "T1": 10,
  "C2": 3,
  "T2": 15,
  "C3": 2.5,
  "T3": 25
}
```

红色三角是超时——任务在截止期前没跑完。把 $C_1$ 拖到 8 ms 看看：RMS 会让 $\tau_2$ 和 $\tau_3$ 全部超时，但 EDF 可能还撑得住。

### 实验 2：自己算（Python）

```python title="RMS 上界与可调度性判定"
n = 3
bound = n * (2 ** (1/n) - 1)
tasks = [(2, 10), (3, 15), (2.5, 25)]
U = sum(c/t for c, t in tasks)
print(f"任务数 n={n}")
print(f"RMS 上界 = {bound:.3f}")
print(f"利用率 U = {U:.3f}")
if U <= bound:
    print(f"U <= {bound:.3f} → RMS 保证可调度")
elif U <= 1.0:
    print(f"RMS 上界不满足，但 U <= 1 → EDF 可调度，RMS 不保证（需仿真验证）")
else:
    print(f"U > 1 → 任何策略都调度不开，需降低负载")
```

## 6. 常见误区

:::warning[常见误区]
- **「实时 = 快」**——实时（real-time）的核心不是"快"而是"可预测"。只要保证在截止期内完成就行——哪怕截止期是 1 秒。一个 1 ms 跑完但偶尔 10 ms 才响应的系统**不是实时**系统。
- **「利用率低就不会超时」**——$U < 1$ 是 EDF 的充要条件，但 RMS 下即使 $U < 0.78$ 也不保证不超时——上界只对**充分条件**成立。协作式调度连 $U < 0.5$ 都可能超时（长任务卡住短任务）。
- **「动态优先级一定比静态好」**——EDF 理论最优，但每次调度都要比较截止期，开销大；RMS 优先级固定，查表即可，在几十 kHz 的控制环里这个差很要命。工程上 RMS 用得更多。
:::

```exercise
# @title: 计算 RMS 可调度上界
# @check: 0.780
# @hint: 上界 = n * (2**(1/n) - 1)
# 给定任务数 n=3，计算 RMS 的利用率上界，保留 3 位小数。
n = 3
bound = n * (2 ** (1/n) - 1)
print(f"{bound:.3f}")
```

<details>
<summary>选读 · Liu & Layland 1973 定理的直觉</summary>

为什么 RMS 上界是 $n(2^{1/n}-1)$ 而不是 1？关键在**最坏情况相位**：所有任务同时到达。

$n$ 个任务同时到达时，$\tau_1$（最短周期）先跑，跑完 $\tau_2$ 跑……最不利的时刻是所有任务的周期在某个时间点"挤在一起"——这比"均匀错开"的利用率低很多。Liu & Layland 证明了：当 $U \le n(2^{1/n}-1)$ 时，**无论任务相位如何**，RMS 都不会超时。

$n \to \infty$ 时上界趋于 $\ln 2 \approx 0.693$——CPU 只能用 70%。这"浪费"的 30% 是静态优先级策略的固有代价。EDF 通过动态优先级把这 30% 找回来了，但代价是每次调度都要算截止期。

工程上这 30% 换来的是**确定性**——RMS 的优先级在编译时就定死了，没有运行时分支，最坏执行时间（WCET）可以静态分析。这在安全关键系统（DO-178C 航空认证、IEC 61508 工业安全）里是硬性要求。

</details>
