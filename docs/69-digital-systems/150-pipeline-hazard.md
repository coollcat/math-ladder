# 流水线与冒险

## 1. 从一个场景开始

第 130 课的单周期数据通路里，一条指令一拍跑完——看起来很干净，但它有个致命的代价：**时钟周期必须装得下最慢的那条指令**。取指、译码、执行、访存、写回全挤在一拍里，时钟就快不起来。

工厂早就遇到过一模一样的问题：一辆车从头装到尾要 10 小时，难道每 10 小时才出厂一辆？不——把流程切成 10 个工位，每个工位只干一件事，**传送带每 1 小时就把一辆新车送出去**。车在厂里的总时间没变，**出厂速率快了 10 倍**。

CPU 把指令执行切成五段之后，同样的魔法出现了：理想情况下**每一拍都有一条指令完工**。但只要相邻两条指令"共用同一台机器"，魔法就会卡壳——这一课就讲它卡在哪、怎么救。

## 2. 直觉解释

洗衣店有三台机器：洗涤、漂洗、甩干。一批床单要走完三道工序。若等一批全部做完再放下一批，4 批床单要 12 拍；改成一批洗完就进漂洗、下一批立刻进洗涤——流水起来后只需 $3 + (4-1) = 6$ 拍。**头几拍在"填管道"，之后每一拍都有批次出炉**。

CPU 的五段流水线一模一样：

| 段 | 缩写 | 干什么 |
| --- | --- | --- |
| 取指 | IF | 从内存拿出指令 |
| 译码 | ID | 解码，读寄存器 |
| 执行 | EX | ALU 运算 |
| 访存 | MEM | 读写内存 |
| 写回 | WB | 结果写回寄存器 |

洗衣店里"漂洗机和洗涤机是分开的"，所以从不打架。CPU 的麻烦在于：**相邻指令常常要用同一个东西**——第 2 条要读的寄存器，第 1 条还没写回去；第 3 条是分支，跳不跳还不知道。这些"抢同一台机器"的时刻就是**冒险**：不是电路坏了，而是指令流本身带着依赖。

## 3. 正式定义

**流水线**：把指令执行切成 $k$ 个阶段，各阶段并行处理不同指令。$N$ 条指令的总拍数为

$$T = k + (N - 1) \qquad \text{（无冒险的理想情况）}$$

**CPI**（Cycles Per Instruction，每条指令平均拍数）：

$$\text{CPI} = \frac{T}{N} = \frac{k + N - 1}{N} \xrightarrow{N \to \infty} 1$$

流水线不缩短单条指令的延迟（它甚至更长——段与段之间要加锁存器），**它提高的是吞吐率**。

**三类冒险**：

| 冒险 | 何时发生 | 本章的解法 |
| --- | --- | --- |
| 结构冒险 | 两条指令同一拍要用同一段硬件 | 五级流水按"每段每拍一条"天然规避 |
| 数据冒险 | 后面的指令要读前面还没写回的寄存器（RAW：写后读） | 停顿（气泡）或**转发** |
| 控制冒险 | 分支指令没出结果，不知道下一条取哪 | 等分支出结果，或**预测不转移** |

**转发**（forwarding）：ALU 的结果在第 3 段（EX）末尾就已经出炉，访存数据在第 4 段（MEM）末尾出炉——不必等它慢悠悠走完第 5 段写回寄存器，直接**从段间寄存器拉一根线绕回来**给下一条指令的 EX 用。

**load-use 冒险**：`lw` 的数据要到 MEM 段**末尾**才出炉，而紧跟它用这个数的指令在 ID 段就要读寄存器——转发线再快也追不上这一拍，**至少停 1 拍**，这是转发也救不了的一个。

## 4. 分步例题

用这段 7 条指令的小程序（就是动手实验里的默认程序），数一数三种模式各要多少拍。理想拍数是 $7 + 4 = 11$。

1. **找出数据冒险**：`lw→add`（用 $1）、`add→add`（用 $2）、`add→sw`（用 $3）——三对相邻的 RAW；
2. **无转发**：每对 RAW 都要干等到写回，各停 2 拍，共 6 拍；分支 `beq` 出结果前取指也得等，再停 2 拍。总拍数 $11 + 8 = \textbf{19}$，CPI $= 19/7 \approx 2.71$；
3. **开转发**：三对 RAW 全靠转发躲过（ALU 结果 EX 末出炉、来得及），只剩 load-use 停 1 拍 + 分支停 2 拍。总拍数 $11 + 3 = \textbf{14}$，CPI $= 2.00$；
4. **转发 + 预测不转移**：这条分支恰好不成立，预测对了零开销，只剩 load-use 那 1 拍。总拍数 $11 + 1 = \textbf{12}$，CPI $\approx 1.71$。

从 19 拍到 12 拍，**没有换任何硬件，只是别让流水线空转**。这就是为什么"指令调度"是编译器的一门正经手艺（见第 7 节）。

## 5. 动手实验

### 实验 1（lab）：看着气泡被一台一台消灭

```lab
{
  "type": "pipeline-hazard",
  "title": "无转发先看白等：切「转发」再看气泡消失",
  "program": [
    { "t": "lw  $1, 0($0)", "dst": 1, "src": [0], "kind": "load" },
    { "t": "add $2, $1, $1", "dst": 2, "src": [1, 1], "kind": "alu" },
    { "t": "add $3, $2, $1", "dst": 3, "src": [2, 1], "kind": "alu" },
    { "t": "sw  $3, 4($0)", "dst": -1, "src": [3, 0], "kind": "store" },
    { "t": "beq $1, $6, +1", "dst": -1, "src": [1, 6], "kind": "branch" },
    { "t": "add $4, $4, $1", "dst": 4, "src": [4, 1], "kind": "alu" },
    { "t": "add $5, $2, $3", "dst": 5, "src": [2, 3], "kind": "alu" }
  ],
  "m": 4,
  "k": 5,
  "mode": "stall",
  "height": 300
}
```

时空图上，虚线空格就是**气泡**——流水线白转的一拍；橙色边框是"卡在这一段没动"，红色小三角标出卡住的原因。开局 $m=4$、$k=5$，`beq` 不成立。依次做四件事：

- 先待在「无转发」：读数应是 19 拍、额外开销 8 拍——和第 4 节手算对上；
- 切到「转发」：气泡大批消失，绿色虚线箭头就是转发路径，只剩 load-use 那 1 拍躲不掉（14 拍）；
- 再切「预测不转移」：分支白等也消失（12 拍）。把 $k$ 滑块拖到 4 让分支**成立**——预测错了，已取的两条被冲掉（画叉的格子），拍数又弹回去；
- 最后**拖指令行重排**：把一条无关指令塞进 `lw` 和用它那条之间，load-use 气泡当场消失——这正是编译器指令调度干的事。

顺带一提：上面的程序是我们特意排过的。组件自带的默认程序里，最后一条 `add` 依赖被 `beq` 跳过的那条指令写入的寄存器——把 $k$ 拖回 4 让分支成立、又待在「无转发」模式时，流水线会当场卡死在原地（一条解不开的 RAW 死锁，一直卡到画布尽头）。想亲眼见识死锁长什么样，把 program 换回默认即可。

### 实验 2（python）：三种模式的 CPI 账单

```python title="三种模式的拍数与 CPI"
N = 7                      # 指令条数
base = N + 4               # 流水线填充满 4 拍 + 之后每拍出一条
# 各模式的额外停顿拍数：无转发 = 3 对 RAW×2 拍 + 分支 2 拍
modes = [("无转发", 8), ("转发", 3), ("转发+预测不转移", 1)]
for name, extra in modes:
    total = base + extra
    print(f"{name}: 总拍数 {total}, CPI = {total/N:.2f}")
print(f"理想（零冒险）: 总拍数 {base}, CPI = {base/N:.2f}")
```

CPI 从 2.71 一路压到 1.71，理想值 1.57——**每个百分点都是白等出来的**。真实处理器的流水线更深（十几段），冒险的种类更多，但"数气泡"这套算法是同一个。

### 快问快答

```quiz
开了转发，为什么 load-use 冒险还是要停 1 拍？
- 转发线路有故障，偶尔失灵
- lw 的数据要到 MEM 段末尾才出炉，而用它的指令在 ID 段就要读寄存器，转发线追不上这一拍 [*]
- 寄存器堆容量不够，要先腾位置
? 转发能救「EX 末出炉」的 ALU 结果，救不了「MEM 末出炉」的访存数据——物理上那一刻数据还不存在。唯一彻底的解法是编译器把无关指令挪进这两条之间。
```

::::warning[常见误区]

**误区一**："流水线让每条指令跑得更快了。"
你以为单条指令的延迟缩短了——其实**单条更慢**：切五段要加四个段间锁存器，每段还得按最慢的那段对时钟。流水线提高的是**吞吐率**：完工速率从 5 拍一条变成 1 拍一条。买流水线买的是"出货速度"，不是"单件工期"。

**误区二**："开了转发，数据冒险就全没了。"
你以为转发是万能胶——load-use 那 1 拍它就是追不上（数据 MEM 末才出炉）。另外它对控制冒险毫无作用，分支照样要让取指等两拍或者赌一把预测。

**误区三**："分支预测就是碰运气。"
你以为预测是掷硬币——它是**基于历史的统计决策**：循环里的分支绝大多数时候"不转移/回跳"，预测器靠这张成绩单把正确率做到 95% 以上。猜错的代价（冲掉已取指令）才是要省的东西，第 90 课的状态机思想正是预测器的骨架。

::::

## 6. 练习

**练习 1**：五级流水线里，`lw` 后面紧跟一条用它的 `add`。即使开了转发，总拍数也应为 `7`。这段代码忘了算 load-use 的气泡：

```exercise
# @title: 练习：load-use 的那 1 拍
# @check: 7
# @hint: 数据要等 MEM 段末才出炉，用它的指令在 ID 段就要读寄存器——转发也追不上这一拍。把 bubbles 改成 1
N = 2          # 两条指令：lw 后面紧跟一条用它的 add
base = N + 4   # 五级流水线的无冒险总拍数
bubbles = 0    # ← 问题在这：即使开了转发，load-use 也要停 1 拍
total = base + bubbles
print(total)
```

**练习 2**：把上面实验程序的 `beq` 改成**成立**（$k$ 拖到 4），开转发模式。手算总拍数，再到组件里核对。

<details>
<summary>点开查看逐步解答</summary>

1. 分支成立时跳过下标 5 那条 `add $4`，直接落到下标 6 的 `add $5, $2, $3`——它只读 $2 和 $3，都是早就出炉的值，**转移目标不依赖被跳过的指令**，流水线不受阻；
2. 实际执行 $7 - 1 = 6$ 条指令，理想拍数 $6 + 4 = 10$；
3. 额外开销：load-use 停 1 拍 + 分支在 EX 末出结果、取指等 2 拍 = 3 拍；
4. 总拍数 $10 + 3 = \textbf{13}$（无转发是 18 拍：RAW 6 拍 + 等分支 2 拍）。

注意"成立"与"不成立"在纯转发模式下代价相同（都是等 2 拍）——**预测不转移只在不成立时才省钱**；成立时预测错了反而要多冲两条。真实分支预测器赌的是历史规律，不是无脑"不转移"。

</details>

## 7. 选读：编译器也会"拖指令行"

<details>
<summary>选读 · 指令调度与为什么五级流水没有 WAR/WAW</summary>

**指令调度**（instruction scheduling）：编译器在生成机器码时，把相互独立的指令塞进两条相关指令中间，用有效工作填满本该是气泡的拍子。实验 1 里"拖指令行"就是在人肉干这件事——把 `add $5, $2, $3`（不读 $1、不写 $4）挪到 load-use 间隙里，那 1 拍就不再是白等。调度的约束只有一条：**不能改变程序的可观察行为**（每条指令看到的寄存器值必须与原顺序一致）。

**为什么这套五级流水里只有 RAW，没有 WAR 和 WAW？** WAR（写后读）与 WAW（写后写）要出现，得允许后面的指令**越过**前面的指令先写寄存器——也就是乱序。而在定序的五级流水里，指令按顺序进 ID：写回永远按程序顺序发生（WB 段排队），读也按顺序发生（ID 段排队），再加上"写回在 WB 前半拍、读寄存器在 ID 后半拍，同一拍一写一读不算冒险"的安排，后写的永远不会被先读抢了先。乱序处理器（第 70 章会遇到的现代 CPU 就是）引入寄存器重命名后，WAR/WAW 才真正浮出水面。

</details>
