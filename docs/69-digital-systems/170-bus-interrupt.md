# 总线、中断与 I/O

## 1. 从一个场景开始

你按下键盘上的 A，屏幕上出现 A——中间只隔了不到一眨眼。可 CPU 手里的主程序跑得正欢，它既没有盯着键盘，也没有盯着鼠标、网卡、磁盘。几十个设备凭什么各得其所，谁也不漏、谁也不抢？

答案是一对搭档：**总线**负责"大家共用一条走廊说话"，**中断**负责"有事才敲门，没事别打扰"。这一课把这两个机制拆开看：走廊怎么排队，门铃怎么按响，CPU 怎么在打断与续上之间不弄丢一个字节。

## 2. 直觉解释

**总线**像一条只容一人通行的走廊。CPU、内存、各设备都挂在两侧，任何时刻只能有一对"说话—听话"。谁来发言靠**仲裁**：按优先级排队，不能一拥而上。地址线喊"去哪儿"，数据线搬"货"，控制线喊"开始/结束"——三条线各司其职。

**设备怎么通知 CPU**？两个流派：

- **轮询**（polling）：CPU 每隔一会儿挨个问一遍"有事吗？"——像保姆每五分钟推开婴儿房门看一眼。简单，但**不管有没有事都要跑一趟**；
- **中断**（interrupt）：设备有事就拉响门铃，CPU 暂停手头工作去处理——像装了婴儿监视器，**有事才响应**。

被门铃叫醒之后还有一套完整礼仪：**把手头这条指令做完**（不能做一半就跑，否则现场保不干净）→ **保存现场**（把断点 PC 和寄存器压栈）→ **跳去执行中断服务程序 ISR** → **恢复现场** → **回到断点若无其事地继续**。整个过程里主程序毫无察觉——它只是觉得时间过了那么几拍。

## 3. 正式定义

**总线**（bus）：一组共享的信号线。

| 线组 | 职责 |
| --- | --- |
| 地址线 | 指明读写的目的地 |
| 数据线 | 搬运数据本身 |
| 控制线 | 时序与命令（读/写、申请/应答） |

**总线仲裁**：多个主设备同时申请时按优先级裁决，一次只许一个占用。

**轮询成本**：若轮询间隔为 $g$ 拍、每次检查花 $c$ 拍，轮询占用的 CPU 比例恒为

$$\text{轮询占比} = \frac{c}{g}$$

**注意它只取决于轮询多勤快，与事件多少无关**——没人敲门也得按时巡逻。

**中断开销**：一次中断的总代价分四段——

$$\text{一次开销} = t_{\text{响应}} + t_{\text{保存现场}} + t_{\text{服务体}} + t_{\text{恢复现场}}$$

$t_{\text{响应}}$ 是请求到达后等**当前指令执行完**的时间（平均约半条指令）。若事件平均每 $G$ 拍来一次，中断占用比例 = 一次开销 $/ G$——**它只取决于事件多少，与响应要求多苛刻无关**。轮询与中断正好互补：一个怕"响应急"，一个怕"事件多"。

**优先级与嵌套**：给设备分等级。高优先级（如定时器，错过一个节拍就丢数据）可以**打断**正在执行的低优先级 ISR——嵌套；低优先级只能排队等。**屏蔽**：把某设备的中断先按住不受理，请求线一直挂着（不丢弃），解除屏蔽后再受理。

## 4. 分步例题

**题 A**：某传感器平均每 2000 拍发一次请求，要求**最坏 5 拍内**被响应。轮询方案：检查一次 2 拍，间隔必须 ≤5 拍——占用 $2/5 = 40\%$ 的 CPU。中断方案：响应约 4 拍、保存 18 拍、服务体 40 拍、恢复 18 拍，共 80 拍——占用 $80/2000 = 4\%$。**响应要求越苛刻，轮询越烧钱，中断的开销却岿然不动。**

**题 B**：同样的设备，如果请求平均每 50 拍就来一次呢？中断占用变成 $80/50 = 160\%$——**忙不过来了**。此时轮询（或批量打包处理）反而合理。分诊口诀：**事件稀而要快，用中断；事件密而可等，用轮询**。

**题 C**：定时器 ISR 执行到一半，键盘请求到了。定时器是高优先级，键盘被**嵌套打断**：先保存键盘现场入栈（和定时器的现场分开叠），跑完键盘 ISR，恢复，回来继续定时器 ISR——像两摞盘子，后放上去的先端走。

## 5. 动手实验

### 实验 1（lab）：一次中断的完整一生

```lab
{
  "type": "bus-interrupt",
  "title": "拖动请求到达时刻，看响应延迟怎么变",
  "tA": 30,
  "tB": 38,
  "lenA": 20,
  "lenB": 18
}
```

整块画布是一条时间线：红色三角是定时器（高优先级）、青色三角是键盘（低优先级），琥珀色播放头逐拍扫过。默认开局就是题 C 的嵌套现场——键盘请求落在定时器 ISR 中途。做四件事：

- 拖红色三角：请求来得越贴近指令边界，CPU 停得越干脆（响应延迟短）；越落在长指令中间，等得越久；
- 看 CPU 那一行：响应前它一定先把**当前指令**执行完——礼仪第一步；
- 点「屏蔽定时器」再播放：请求线拉高后一直挂着没人理，解除屏蔽才受理——屏蔽是按住，不是丢弃；
- 把键盘三角拖出定时器 ISR 的范围：嵌套消失，键盘排队等定时器跑完。

### 实验 2（python）：轮询与中断的分界线

```python title="响应要求越苛刻，轮询越烧 CPU"
poll_cost = 2          # 每次查一遍状态寄存器（拍）
ovh = 4 + 18 + 40 + 18 # 一次中断：响应 + 保存现场 + 服务体 + 恢复现场
event_gap = 2000       # 平均每 2000 拍来一个请求
for deadline in [100, 50, 20, 5]:   # 要求最坏响应延迟 ≤ deadline 拍
    poll_gap = deadline              # 轮询间隔必须压到 deadline 以内
    poll_pct = poll_cost / poll_gap * 100
    int_pct = ovh / event_gap * 100
    print(f"最坏延迟 {deadline:>3} 拍 → 轮询占 {poll_pct:5.1f}%   中断占 {int_pct:.1f}%")
```

两列数字讲了整个故事： deadline 宽松时轮询便宜（不用装门铃）；deadline 压到 5 拍，轮询烧掉 40% 的 CPU，中断还是那 4%——**中断把"响应快"从 CPU 的日常巡逻变成了一次性的固定开销**。反过来把 `event_gap` 改成 50 再跑，中断就忙不过来了：口诀的分界线亲眼看一遍。

### 快问快答

```quiz
中断请求到达时，CPU 为什么不能立刻跳去执行 ISR？
- 中断信号不可靠，要连续确认三次才响应
- 必须先把当前这条指令执行完，否则断点与寄存器的现场保不干净 [*]
- CPU 太忙，要等它主动闲下来
? 流水线里一条指令已经走了一半（比如 EX 段结果未出、MEM 段正在访存），此刻保存的现场是不完整快照。做完当前指令再保存，恢复后才能无缝续跑——这就是响应延迟的第一段来源。
```

::::warning[常见误区]

**误区一**："中断一定比轮询先进。"
你以为门铃全面碾压巡逻——中断每次要付响应 + 保存 + 恢复的固定开销，**事件一密开销就爆炸**（题 B 里 160% 的占用率）。网卡高速收包时反而靠轮询式驱动把开销摊薄。先进的从来不是机制，是**按场景选机制**。

**误区二**："屏蔽一个设备的中断 = 丢弃它的事件。"
你以为屏蔽就是拉黑——请求线是电平，屏蔽期间它**一直挂着**，解除后照样受理（丢不丢数据取决于设备自己撑不撑得住）。屏蔽的真正用途是保护临界区：改共享数据的那几拍，谁也不许插话。

**误区三**："总线就是一根更粗的电线。"
你以为总线只是并联——它是一条**一次只能一个说话**的走廊，仲裁失败者要排队等待。设备越多、越快，走廊越挤，这才有了把高速设备分散到多条总线、甚至点对点直连的现代架构。

::::

**练习 2**：一块 MCU 挂了定时器和键盘两个中断源。定时器每 1 ms 必须被打招呼一次，键盘事件晚 50 ms 无人在意。请给两者排优先级，并说明理由与屏蔽策略。

<details>
<summary>点开查看逐步解答</summary>

1. **定时器高优先级，键盘低优先级**。判据是"错过会怎样"：定时器错过一个节拍，节拍数据永久丢失且时基漂移；键盘晚 50 ms，人的手指根本分辨不出来；
2. **嵌套方向**：定时器 ISR 可以打断键盘 ISR（高打断低）；反之键盘 ISR 执行时把定时器中断打开，保证节拍不丢；
3. **屏蔽策略**：只在"同时改两个设备共享数据"的临界区里短暂屏蔽低优先级的键盘；定时器几乎不屏蔽；
4. 反过来排（键盘高）会怎样：一次键盘 ISR 拖上 1 ms 以上，定时器就错过节拍——**优先级排错，症状出现在"被耽误的那个"身上**，这正是分诊时最容易看错方向的故障。

</details>

## 7. 选读：DMA——让设备绕过 CPU 直接搬数据

<details>
<summary>选读 · 搬大件为什么要请搬家公司</summary>

按中断的路子从网卡收 1500 字节：CPU 每收 2~4 字节就被打断一次，几十次中断、几百拍的保存恢复，**全花在仪式上**。数据量大时这套礼仪不划算。

**DMA**（Direct Memory Access，直接内存访问）的解法：给设备配一个"搬运工"。CPU 只对 DMA 控制器交代三句话——源地址、目的地址、长度——然后回去做自己的事；搬运工在总线上自己排队、自己搬，**搬完才响一次中断**。几十次中断缩成一次，仪式开销被摊薄到近乎为零。

DMA 与缓存的互动有个著名的坑：搬运工直接写内存，**缓存里那几行还留着旧数据**。体系结构要么让 DMA 走缓存一致性协议，要么要求驱动先把相关缓存行作废——驱动工程师最经典的"玄学 bug"之一就源于此。

</details>
