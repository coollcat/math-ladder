# 计算机系统方法地图

## 1. 从一个场景开始

凌晨三点，服务告警：接口 P99 从 20 ms 涨到 3 秒。

你手上有十六门课的工具：调度、分页、索引、锁、事务隔离级别、拥塞窗口、路由、多数派……**先查哪一个？**

学完一整章工具最大的风险不是忘了公式，而是"拿着锤子看什么都是钉子"。本课不添任何新定理，只做三件事：把全章排成一张**导诊地图**、演练一遍**分诊两问法**、然后把那串"必须背下来的数量级"一次性钉死。

## 2. 直觉解释

系统故障的分诊只需连问两个问题：

**第一问——现象属于哪一类？**

| 类别 | 典型症状 | 谁负责 |
| --- | --- | --- |
| **资源争抢** | 排队、超时、吞吐上不去 | 调度、锁、连接池、线程池 |
| **内存/存储** | 突然变慢、磁盘狂响、OOM | 分页、缺页率、文件系统、缓存 |
| **数据/算法** | 慢但资源很闲、数据量一大就崩 | 关系代数、索引、B 树、复杂度 |
| **并发正确性** | 数据不对、偶发、难复现 | 死锁、隔离级别、冲突图 |
| **网络** | 抖动、地域性故障、连接超时 | 分层、拥塞控制、路由 |
| **分布式** | 少数派不可用、脑裂、数据分叉 | 共识、多数派、CAP |

**第二问——特征尺度是什么？**

- **时延**：µs（内存）、ms（局域网/磁盘）、百 ms（跨洋）；
- **数据量**：千行、百万行、十亿行；
- **并发度**：几个连接、几千连接、几十万连接。

两问答案往表上一对，科室基本锁定。剩下的分歧多半发生在"多种工具都能凑合"的地带——那时再比成本、复杂度与可维护性。

## 4. 分步例题

**题 A**：接口 P99 从 20 ms 涨到 3 秒，磁盘 I/O 从 5% 涨到 95%，CPU 反而更闲了。

1. 第一问：**内存/存储**（CPU 在等 I/O）；第二问：时延从毫秒级涨到秒级；
2. 定位：缺页率飙升或缓存命中率崩塌。去查 [分页](./50-paging-lab.md) 的工作集——多半是刚上线的功能引入了一个大对象的全量扫描，把热数据挤了出去；
3. 处方：**先测缺页率，再谈加内存**。加内存能解决"工作集放不下"，解决不了"局部性差"（后者要改访问模式）；
4. 反例检验：如果是 [索引](./100-btree-lab.md) 缺失导致的全表扫描，磁盘也会忙，但 CPU 通常**也忙**（在做比较与过滤）。**CPU 忙不忙是区分这两者的第一刀。**

**题 B**：并发量一上去吞吐就不涨了，CPU 打满，线程数从 8 加到 200 毫无改善。

1. 第一问：**资源争抢**（吞吐封顶、CPU 空转在等）；第二问：并发度几百、单次操作 µs 级；
2. 定位：**锁竞争**。线程越多，花在"抢锁、排队、上下文切换"上的时间越多（回顾 [调度](./30-scheduler-lab.md) 的切换开销与 [进程线程](./20-process-thread.md) 的共享代价）；
3. 处方：**缩小临界区 → 换读写锁 → 分片（把一把大锁拆成 16 把）→ 无锁结构**。顺序不能反：先测出锁在哪（`perf lock`、采样看栈），再动手；
4. 顺带查 [死锁](./40-deadlock-lab.md)：如果吞吐是**掉到零**而不是"封顶"，那是死锁或活锁，不是竞争。

**题 C**：两机房部署的集群，机房之间光纤被挖断，写入全部失败。

1. 第一问：**分布式**（地域性、少数派）；第二问：3 机房 5 节点，多数派 3；
2. 定位：断掉的那个机房只剩 2 个节点，$2 < 3$ → 拿不到多数票 → **写入必然失败**（[共识](./150-consensus-lab.md)）；
3. 这不是 bug，是设计：**CAP 下选择了 C**；
4. 若要提高可用性：改成 3 机房各 3 节点（9 节点，多数派 5，容忍整个机房故障），代价是每次写入要跨机房拿到 5 票 → **写入时延上升**。**可用性与时延也是一场交换。**

## 5. 动手实验

### 实验 1（python）：给故障自动挂号

```python title="按症状开具科室单"
def triage(disk_busy, cpu_busy, throughput_stuck, slow_queries, partition):
    # 优先级闸门：越可能造成数据损坏或不可恢复的越早分流
    if partition:
        return "consensus（先确认多数派还在不在）"
    if slow_queries:
        return "btree-lab（查索引与执行计划）"
    if cpu_busy and throughput_stuck:
        return "deadlock-lab（查锁竞争与死锁）"
    if disk_busy and not cpu_busy:
        return "paging-lab（查缺页率与工作集）"
    return "scheduler-lab（查排队与调度）"

cases = [
    ("光纤被挖断，写入全失败", False, False, False, False, True),
    ("报表查询从 2 s 涨到 200 s", False, False, False, True, False),
    ("并发翻倍，吞吐纹丝不动", False, True, True, False, False),
    ("磁盘 95%，CPU 20%", True, False, False, False, False),
    ("任务排队，机器很闲", False, False, False, False, False),
]
for note, a, b, c, d, e in cases:          # 元组解包：一次领出整行
    print(f"{triage(a, b, c, d, e):<34} | {note}")
```

五行输出就是五张挂号单。**注意 `if` 的台阶顺序本身就是知识**：分区（可能导致数据分叉）排第一，锁竞争（可能掉到零）排第二。**分诊永远先看会不会丢数据，再看舒不舒服。**

### 实验 2（python）：把数量级钉在脑子里

```python title="每个系统工程师脑内必备的数字"
print("── 时延 ────────────────────────")
for name, t in [("L1 缓存", 1e-9), ("内存访问", 1e-7), ("SSD 随机读", 1e-4),
                ("机械盘寻道", 1e-2), ("同城 RTT", 1e-3), ("跨洋 RTT", 1.5e-1)]:
    print(f"{name:>14}: {t * 1e3:>12.4f} ms")

print("\n── 大小与容量 ──────────────────")
print("  页 4 KB / 大页 2 MB      InnoDB 页 16 KB，扇出 ~1170")
print("  MSS 1460 B               以太网 MTU 1500 B")
print("  TCP 首部 20 B            IPv4 首部 20 B")

print("\n── 经验系数 ────────────────────")
print("  TLB 命中率 99% → 平均访存 ~105 ns")
print("  缺页率 0.1%    → 慢约 100 倍")
print("  上下文切换 1~10 µs（间接开销常更大）")
print("  多数派 ⌊n/2⌋+1 → n=2f+1 容忍 f 个故障")
```

**判断一个设计靠不靠谱，往往不需要精确计算，只需要看数量级对不对。** 看到"每次请求一次磁盘随机读"就该想到 10 ms 与每秒 100 次的天花板；看到"跨洋单连接传大文件"就该想到 BDP 与窗口扩大。

### 快问快答

```quiz
一个服务突然变慢，磁盘很忙但 CPU 很闲，最应该先查什么？
- 锁竞争，因为吞吐上不去多半是锁的问题
- 缺页率或缓存命中率：CPU 在等 I/O，说明瓶颈不在计算而在存储层 [*]
- 网络拥塞，因为慢通常都是网络引起的
? CPU 忙不忙是分诊的第一刀：CPU 忙而吞吐不涨 → 争抢（锁/调度）；CPU 闲而 I/O 忙 → 存储（缺页/磁盘/索引缺失）；CPU 与 I/O 都闲 → 排队或外部依赖。先量再猜，别跳过测量直接改代码。
```

:::warning[常见误区]

**误区一**："先优化，慢的地方肯定就是热点。"
你以为直觉能定位热点——**没有测量就没有优化**。真实系统里的热点几乎总是反直觉的：一个不起眼的日志格式化占了 30% CPU、一次 N+1 查询占了 90% 的时延、一个未对齐的结构体让缓存命中率掉了 20%。**先采样（`perf`、`flamegraph`、慢查询日志），再动手。**

**误区二**："加机器就能解决性能问题。"
你以为扩容是万能解——**只有无状态、无共享瓶颈的服务才线性扩展**。加锁的临界区、单主数据库、分布式共识（多数派投票）都不会因为机器变多而变快，甚至更慢（节点越多，达成多数派的通信量越大）。**先画出共享资源在哪，再谈扩容。**

**误区三**："方法地图是一条通关路线。"
它是按需查阅的工具书，不是进度条。真实工作从来只摘用其中两三页。这张表真正想教的是**分诊的顺序**：先看会不会丢数据（分区、一致性、持久化），再看服务是否可用（死锁、OOM），最后才优化性能（索引、缓存、调度）。**顺序错了，会越修越坏。**

:::

## 6. 练习

**练习 1**：分诊台把两个判据写反了，于是"磁盘忙"被开成了锁竞争的号。修到输出 `paging / lock / index`：

```exercise
# @title: 练习：分诊台的两个判据对调了
# @check: paging
# @check: lock
# @check: index
# @hint: 缺页的特征是「磁盘忙而 CPU 闲」（CPU 在等 I/O）；锁竞争的特征是「CPU 忙但吞吐不涨」。代码把这两个分支的返回值对调了
def triage(disk_busy, cpu_busy, throughput_stuck, slow_queries):
    if slow_queries:
        return "index"
    if disk_busy and not cpu_busy:
        return "lock"          # ← 问题在这：这该是 paging
    if cpu_busy and throughput_stuck:
        return "paging"        # ← 问题在这：这该是 lock
    return "profile"

print(triage(True, False, False, False))    # 磁盘忙、CPU 闲
print(triage(False, True, True, False))     # CPU 忙、吞吐不涨
print(triage(False, False, False, True))    # 慢查询
```

**练习 2**：一个刚上线的接口，单机 QPS 只有 200，而同机器的其他接口能到 5000。它每次请求做：1 次主键查询、1 次磁盘随机读、2 次跨机房 RPC（RTT 40 ms）、1 次 JSON 序列化。请估算瓶颈并给出优化顺序。

<details>
<summary>点开查看逐步解答</summary>

1. 逐项估算（单次）：主键查询走 B 树约 3 次 I/O，多半命中缓存 → ~0.1 ms；磁盘随机读 **~10 ms**；两次跨机房 RPC = $2 \times 40 = 80$ ms；JSON 序列化 ~0.05 ms；
2. 合计约 **90 ms/次** → 单线程上限约 11 QPS；要跑到 200 QPS 需要至少 18 个并发；**瓶颈 100% 在 RPC**；
3. 优化顺序：① **把两次串行 RPC 改成并行**（80 ms → 40 ms，立刻翻倍）；② **能不能合并成一次调用**（40 ms → 20 ms）；③ **加缓存，把 RPC 结果按主键缓存**（命中后趋近 0）；④ 最后才是磁盘那 10 ms——它在 90 ms 里只占 11%，先优化它是典型的"优化错地方"；
4. 结论：**先量出每一项占多少，再按占比从大到小做。** 凭直觉优化，八成会去优化那个 0.05 ms 的序列化（它最好优化，也最没用）。

</details>

## 7. 选读：三条游览路线

<details>
<summary>选读 · 不同胃口的吃法</summary>

**后端工程线**（最快上手干活）：程序生命周期 → 进程线程 → 调度 → 同步死锁 → 分页 → 文件系统 → 关系代数 → 索引 B 树 → 事务 ACID。走完这九课，你已经能设计并调试一个有数据库的后端服务，也看得懂大部分线上事故。

**系统纵深线**（做基础设施的读法）：补上网络分层 → 拥塞控制 → 路由 → 分布式一致性，再回头深挖编译原理两课与虚拟内存。这条线直通分布式存储、服务网格与云原生基础设施。

**性能专精线**：以"测量—定位—验证"为纲重读：分页（缺页率）、B 树（树高与扇出）、TCP（窗口与 BDP）、共识（多数派与往返数）。重点不在"记住结论"，而在**每个数字背后都有一个可测量的量**——**能被测量的东西才能被优化。**

三条线最后都汇入同一句话：**系统工程的本质不是记住多少机制，而是在相互矛盾的约束之间做取舍**——吞吐与时延、一致性与可用性、内存与速度、通用与专用。地图能帮你找到工具，取舍只能靠你自己拍板。

</details>
