# 同步、互斥与死锁

## 1. 从一个场景开始

两个人在窄巷里迎面相遇，同时侧身让路——**同时往同一边让，于是又堵上了**。两个人都在等对方先动，谁也没动。

程序遇上的是同一件事：线程 A 握着锁 1 等锁 2，线程 B 握着锁 2 等锁 1。它们没有崩溃、没有报错、CPU 占用为零，只是**永远地、安静地停在那里**。

## 2. 直觉解释

把资源想成**筷子**，进程想成**吃面的人**：

- 一双筷子才能吃面，一人先拿左、一人先拿右，就僵住了；
- 破解办法有四种：**别让他们同时抢**（破坏"持有并等待"）、**允许从手里抢走筷子**（破坏"不可抢占"）、**给筷子编号，规定必须从小的拿起**（破坏"环路等待"）、**或者等僵住了再强行收走一双**（检测与恢复）。

死锁不是"程序写错了"，而是**四个条件恰好同时成立**。破掉任意一个，死锁就不存在。

## 3. 正式定义

**死锁的四个必要条件（Coffman 条件）**：

| 条件 | 内容 | 破坏它的常见做法 |
| --- | --- | --- |
| 互斥 | 资源一次只能被一个进程占有 | 改成可共享（只读副本、无锁结构） |
| 持有并等待 | 已占有资源的同时还在申请新资源 | **一次性申请全部资源**（要么全给，要么不给） |
| 不可抢占 | 资源不能被强行收回 | 允许抢占（数据库回滚、超时放弃） |
| 环路等待 | 存在进程—资源的循环等待链 | **资源全局编号，按序申请** |

**资源分配图（RAG）**：二部图，节点集为进程 $P$ 与资源 $R$；**请求边** $P_i \to R_j$（在等），**分配边** $R_j \to P_i$（已占有）。

$$\text{每类资源只有一个实例} \implies \text{图中存在环} \iff \text{死锁}$$

若某类资源有多个实例，有环只是**必要条件**——环上的进程可能还能从别处等到资源。

**银行家算法（避免）**：分配之前先"试算"一次，只有当结果仍是**安全状态**才真正分配。记

$$\text{Need}[i] = \text{Max}[i] - \text{Allocation}[i]$$

| 符号 | 含义 |
| --- | --- |
| $\text{Available}[k]$ | 资源 $k$ 当前空闲的**实例数**（向量，不是布尔） |
| $\text{Allocation}[i][k]$ | 进程 $i$ 当前**已占有**的实例数 |
| $\text{Max}[i][k]$ | 进程 $i$ **总共可能**申请的最大数量（事先声明） |
| $\text{Need}[i][k]$ | 进程 $i$ **还差**多少才能跑完 |

**安全性算法**：令 $\text{Work} = \text{Available}$，反复寻找满足 $\text{Need}[i] \le \text{Work}$ 且未完成的进程 $i$，把它"跑完"并令 $\text{Work} \mathrel{+}= \text{Allocation}[i]$。若所有进程都能被安排完，则存在**安全序列**，状态安全。

## 4. 分步例题

**例**（教科书经典）：3 类资源、5 个进程，$\text{Available} = (3,3,2)$，Allocation 与 Max 如表。判断状态是否安全。

| 进程 | Allocation | Max | Need = Max − Allocation |
| --- | --- | --- | --- |
| P0 | 0 1 0 | 7 5 3 | 7 4 3 |
| P1 | 2 0 0 | 3 2 2 | 1 2 2 |
| P2 | 3 0 2 | 9 0 2 | 6 0 0 |
| P3 | 2 1 1 | 2 2 2 | 0 1 1 |
| P4 | 0 0 2 | 4 3 3 | 4 3 1 |

1. $\text{Work} = (3,3,2)$。扫一遍：P1 的 Need $(1,2,2) \le$ Work → P1 可完成，$\text{Work} = (3,3,2)+(2,0,0) = (5,3,2)$；
2. 继续扫：P3 的 Need $(0,1,1) \le (5,3,2)$ → $\text{Work} = (7,4,3)$；
3. P4 的 Need $(4,3,1) \le (7,4,3)$ → $\text{Work} = (7,4,5)$；
4. P0 的 Need $(7,4,3) \le (7,4,5)$ → $\text{Work} = (7,5,5)$；
5. P2 的 Need $(6,0,0) \le (7,5,5)$ → $\text{Work} = (10,5,7)$；
6. 全部安排完毕 → **状态安全**，安全序列为 $\text{P1} \to \text{P3} \to \text{P4} \to \text{P0} \to \text{P2}$。

注意：安全序列**不唯一**，而且"安全"的意思是"存在一种安排让谁都不卡"，不是"接下来随便怎么走都行"。

## 5. 动手实验

### 实验 1（lab）：上半场检测，下半场避免

```lab

  "type": "deadlock-lab",
  "title": "死锁：资源分配图找环，银行家算法找安全序列"
}
```

**资源分配图模式**：点 3×3 的格子循环切换 `· → R→P（已占有）→ P→R（在等待）`。默认就摆着一个环（P1→R2→P3→R3→P1 之类），读数会显示"发现环路 → 死锁"并把环上的节点标红。把环上任意一格点掉，判定立刻翻绿——**因为每类资源只有一个实例，有环就是死锁**。

**银行家算法模式**：点"试下一个请求"逐条检验四个请求（含非法的、资源不足的、试分配后不安全的）。注意看第二条：请求本身没超过手里资源，但**试分配之后进入不安全状态，照样拒绝**——这就是"避免"和"检测"的分水岭。

### 实验 2（python）：把安全性算法写出来

```python title="银行家算法：试分配之前先算一次安全性"
avail = [3, 3, 2]
alloc = [[0, 1, 0], [2, 0, 0], [3, 0, 2], [2, 1, 1], [0, 0, 2]]
maxd = [[7, 5, 3], [3, 2, 2], [9, 0, 2], [2, 2, 2], [4, 3, 3]]

# 列表推导嵌套：外层生成 5 行，内层生成每行的 3 列
need = [[maxd[i][k] - alloc[i][k] for k in range(3)] for i in range(5)]

def safe(avail, alloc, need):
    work = avail[:]                       # 切片 [:]：复制一份，别就地改坏原表
    finish = [False] * len(alloc)
    seq = []
    for _ in range(len(alloc)):           # 最多找 n 轮，每轮至少完成一个
        moved = False
        for i in range(len(alloc)):
            if finish[i]:
                continue
            if all(need[i][k] <= work[k] for k in range(3)):   # all：三个分量都要够
                for k in range(3):
                    work[k] = work[k] + alloc[i][k]            # 跑完 → 把它占的全还回来
                finish[i] = True
                seq.append("P" + str(i))
                moved = True
        if not moved:                     # 一整轮没人能推进 → 卡住了
            break
    return all(finish), seq               # 返回 (是否安全, 安全序列)

ok, seq = safe(avail, alloc, need)
print("Need:")
for i in range(5):
    print("  P" + str(i), need[i])
print("安全" if ok else "不安全", "→", " → ".join(seq))
```

跑出来的序列正是例题里的 `P1 → P3 → P4 → P0 → P2`。**关键在 `work[k] += alloc[i][k]` 这一行**：安全性算法的全部魔力就是"假设它跑完，然后把它占有的东西全部收回"。

### 快问快答

```quiz
银行家算法为什么在分配之前而不是之后做检查？
- 因为分配之后再检查就来不及了：进程一旦拿到资源，除非回滚或抢占，否则收不回来 [*]
- 因为分配之后再检查计算量更大
- 因为进程必须在申请时就声明最大需求量
? 「避免」的本质是：只在「分配之后仍然安全」时才真的分配。它要求每个进程事先声明 Max——这在真实系统里往往做不到（你很难预知一次查询会锁多少行），所以实际系统多半改用「检测 + 超时回滚」或者「按序加锁」这种预防手段。
```

:::warning[常见误区]

**误区一**："资源分配图里有环就一定死锁。"
你以为有环等于死锁——**只有每类资源都恰有一个实例时，有环才等价于死锁**。有 3 台打印机时，环上的进程完全可能等到环外进程释放的那台，环路自行解开。**有环是必要条件；单实例才是充要条件。**

**误区二**："死锁预防的四条里，破坏'互斥'最彻底。"
你以为破互斥最根本——**互斥是最难破的一条**：打印机、写锁、缓冲区本来就不能同时给两个人用，硬改成共享会直接产生数据损坏。工程上最容易破的是**环路等待**：给所有资源编个全局序号，规定必须按升序申请，环路在数学上就不可能出现（选读部分给出证明）。

**误区三**："死锁预防和避免是一回事。"
你以为只是叫法不同——**预防**是静态地破坏四个条件之一（代价是资源利用率下降，比如一次性申请全部资源会让打印机在大部分时间闲置）；**避免**是运行时动态判断（银行家算法，代价是要事先知道 Max）。还有第三条路：**检测 + 恢复**（定期建图找环，找到了就杀掉一个进程或回滚），以及第四条路——**鸵鸟算法**，即假装死锁不存在。真实操作系统（包括 Linux、Windows）在多数场景下选的就是鸵鸟算法。

:::

## 6. 练习

**练习 1**：这段安全性算法跑出来是"不安全"，可这个状态明明是安全的。修到输出安全序列：

```exercise
# @title: 练习：安全性算法忘了回收资源
# @check: P1 → P3 → P4 → P0 → P2
# @hint: 每判定一个进程「能跑完」，就要把它当前占有的资源全部还回 work（work[k] += alloc[i][k]）。代码里这一步漏了，于是 work 永远停在 [3, 3, 2]
avail = [3, 3, 2]
alloc = [[0, 1, 0], [2, 0, 0], [3, 0, 2], [2, 1, 1], [0, 0, 2]]
maxd = [[7, 5, 3], [3, 2, 2], [9, 0, 2], [2, 2, 2], [4, 3, 3]]
need = [[maxd[i][k] - alloc[i][k] for k in range(3)] for i in range(5)]

work = avail[:]
finish = [False] * 5
seq = []
for _ in range(5):
    for i in range(5):
        if finish[i]:
            continue
        if all(need[i][k] <= work[k] for k in range(3)):
            finish[i] = True
            seq.append("P" + str(i))     # ← 问题在这：判定通过后没有把 alloc[i] 还回 work
print(" → ".join(seq) if all(finish) else "不安全")
```

**练习 2**：两个线程分别要同时拿到锁 A 与锁 B，一个先 A 后 B，另一个先 B 后 A。用 Coffman 四条件逐条分析：这里哪几条成立？若给锁编号 A=1、B=2 并规定必须按升序申请，会发生什么？

<details>
<summary>点开查看逐步解答</summary>

1. 互斥：成立（锁一次只能被一个线程持有）；
2. 持有并等待：成立（拿着 A 还在等 B）；
3. 不可抢占：成立（锁不会被强行剥夺）；
4. 环路等待：成立（T1 → B → T2 → A → T1）；
5. 四条齐了 → 死锁**可能**发生（是否发生取决于时序，这正是它难查的原因）；
6. 编号后：两个线程都必须先申请 A 再申请 B。T1 拿到 A 后申请 B；T2 想先申请 A，只能等。于是 T1 顺利拿到 B 走完流程并释放，T2 再继续——**等待链变成了单向的一条线，环在结构上不可能出现**；
7. 现实中的对应物：数据库的行锁按主键排序、内核的锁顺序校验器（lockdep）自动检查加锁顺序是否成环。

</details>

## 7. 选读：为什么"按序申请"能消灭环路

<details>
<summary>选读 · 一个三行的反证</summary>

设资源被赋予全局序号 $1, 2, \ldots, m$，规定任何进程必须按**严格升序**申请资源。

反设存在环路等待链 $P_1 \to R_{a_1} \to P_2 \to R_{a_2} \to \cdots \to P_n \to R_{a_n} \to P_1$，其中 $P_i$ 持有 $R_{a_{i-1}}$ 并在等待 $R_{a_i}$（下标模 $n$）。

按规则，进程 $P_i$ 在持有 $R_{a_{i-1}}$ 后申请 $R_{a_i}$，必须满足 $a_{i-1} < a_i$。于是沿环走一圈得到

$$a_1 < a_2 < \cdots < a_n < a_1$$

而严格小于关系具有**传递性与非自反性**（第 27 章的偏序），$a_1 < a_1$ 是矛盾。故环路不存在，死锁的第四个条件被彻底摧毁。

这个证明漂亮的地方在于：它**不需要任何运行时检查**，代价只是"申请顺序上的一个纪律"。工程上真正的难点是把这套编号维护下去——一旦有人偷偷逆序加锁，保护就消失了。

</details>
