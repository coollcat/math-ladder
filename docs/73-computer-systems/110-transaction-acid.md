# 事务与 ACID

## 1. 从一个场景开始

A 给 B 转 100 元。程序要做三步：读 A 的余额、减 100、给 B 加 100。

如果第二步之后机房断电，B 没加上，A 却少了 100——**钱凭空消失**。如果同时 C 也在给 B 转账，两笔操作交错执行，B 的余额可能只加了 100。

数据库凭什么保证"要么全做、要么全不做"，并且"交错执行的结果与某种串行执行一样"？

## 2. 直觉解释

事务是一份**契约**，数据库向你承诺四个字母：**ACID**。

| 字母 | 名字 | 大白话 | 谁来兜底 |
| --- | --- | --- | --- |
| A | 原子性 Atomicity | 要么全做，要么像没发生过 | undo 日志（回滚） |
| C | 一致性 Consistency | 前后都得满足约束 | 应用 + 约束共同负责 |
| I | 隔离性 Isolation | 并发执行看起来像串行 | 锁 / MVCC |
| D | 持久性 Durability | 提交后掉电也不丢 | redo 日志（第 60 课的 WAL） |

隔离性是最微妙的一条：数据库并不真的串行执行（那太慢了），而是让**并发调度的结果等价于某个串行调度**。判断"等价"的工具，是一张**冲突图**。

## 3. 正式定义

**调度（schedule）**：多个事务的操作按实际执行顺序排成的序列，如 $R_1(x)\, W_2(x)\, R_1(x)\, W_2(x)$。

**冲突（conflict）**：两个操作 $o_i, o_j$ 冲突，当且仅当同时满足三条：

1. 属于**不同**事务；
2. 作用于**同一**数据项；
3. **至少一个是写**（即 R-W、W-R、W-W 冲突，**R-R 不冲突**）。

**冲突等价**：通过反复交换**相邻的非冲突操作**能互相转化的两个调度。

**冲突可串行化**：调度冲突等价于某个**串行调度**。

**优先图（precedence graph）**：节点是事务；若 $o_i$ 与 $o_j$ 冲突且 $i$ 先执行，则画一条 $T_i \to T_j$ 的有向边。

$$\text{调度冲突可串行化} \iff \text{优先图无环}$$

| 异常现象 | 描述 | 需要什么级别才不出现 |
| --- | --- | --- |
| 脏读 | 读到了别人**未提交**的写入 | 读已提交（含）以上 |
| 不可重复读 | 同一事务内两次读同一行，值不同 | 可重复读（含）以上 |
| 幻读 | 同一事务内两次按条件计数，行数不同 | 串行化 |
| 丢失更新 | 两个"读-改-写"交错，后写的覆盖了前写的 | 可重复读以上 + 显式加锁，或串行化 |

**真实默认级别**：MySQL InnoDB 默认 **REPEATABLE READ**（用 MVCC + 间隙锁，实际上也挡住了大部分幻读）；PostgreSQL 默认 **READ COMMITTED**。**别背默认值，先查你用的那个库。**

## 4. 分步例题

**例**：调度 $R_1(x)\ R_2(x)\ W_1(x)\ W_2(x)$（经典的"丢失更新"）。它冲突可串行化吗？

1. 找冲突对：$R_1(x)$ 与 $W_2(x)$ → $T_1 \to T_2$；$R_2(x)$ 与 $W_1(x)$ → $T_2 \to T_1$；$W_1(x)$ 与 $W_2(x)$ → $T_1 \to T_2$；
2. 图中同时有 $T_1 \to T_2$ 与 $T_2 \to T_1$ → **有环**；
3. 结论：**不可串行化**。无论排成 $T_1;T_2$ 还是 $T_2;T_1$，结果都与这个调度不同；
4. 后果：设 $x$ 初值 5，两个事务都执行 $x \mathrel{+}= 1$。交错执行后 $x = 6$，而任何串行执行都该得 **7**——**一次自增凭空消失**；
5. 处方：把"读-改-写"包进一条原子语句（`UPDATE t SET x = x + 1`），或 `SELECT ... FOR UPDATE` 显式加锁，或提高隔离级别到串行化。

第一排选场景（脏读 / 不可重复读 / 幻读 / 丢失更新），第二排选隔离级别（读未提交 → 读已提交 → 可重复读 → 串行化）。拖"执行到第几步"逐步重放，下方日志会写清每一步读到了什么、值来自哪里。

做三组对照：

- **脏读**场景：读未提交下 T2 读到了 T1 尚未提交的值（日志标红），随后 T1 回滚——**T2 手里的数从来就不存在过**。切到"读已提交"，同样一步读到的是旧值；
- **丢失更新**场景：看读数里的"丢失更新：出现（x=6，应为 7）"。切到串行化，调度被重排成 T1 全部做完再做 T2，`x` 变成正确的 7；
- 每个场景都看最下面那行判定：**"冲突图无环 → 等价于某个串行调度"** 或 **"冲突图有环 → 不可串行化"**。串行化级别的做法其实就是"重排到无环为止"。

### 实验 2（python）：把冲突图画出来

```python title="建优先图，看它有没有环"
ops = [("T1", "R", "x"), ("T2", "R", "x"), ("T1", "W", "x"), ("T2", "W", "x")]

def conflict(a, b):
    ta, oa, da = a
    tb, ob, db = b
    if ta == tb:
        return False                 # 同一事务内部的操作顺序不可交换
    if da != db:
        return False                 # 不同数据项，互不影响
    return oa == "W" or ob == "W"    # 关键：至少一个是写（R-R 不冲突）

edges = set()                        # set：自动去重的边集合
for i in range(len(ops)):
    for j in range(i + 1, len(ops)):
        if conflict(ops[i], ops[j]):
            edges.add((ops[i][0], ops[j][0]))     # 先执行的指向后执行的

print("冲突边:", sorted(edges))
cyclic = ("T1", "T2") in edges and ("T2", "T1") in edges
print("冲突可串行化:", "否（有环）" if cyclic else "是（无环）")
```

输出 `否（有环）`——正是"丢失更新"那个调度。把 `ops` 改成 `[("T1","R","x"), ("T1","W","x"), ("T2","R","x"), ("T2","W","x")]`（真正串行）再跑一次，边只剩 `T1 → T2`，判定翻成"是"。

**注意 `conflict` 的最后一行**：`R-R` 不算冲突，这是最容易写错的一条（练习 1 就是这个坑）。

### 快问快答

```quiz
两个事务都只对同一行做读操作，它们之间会产生冲突边吗？
- 会，只要访问同一个数据项就有冲突
- 不会：冲突要求至少有一个是写操作，读与读可以任意交换顺序 [*]
- 取决于隔离级别
? 交换两个相邻的读操作，谁读到的值都不变，所以它们不冲突。「至少一个写」是冲突定义里的第三条——漏掉它，优先图就会多出一堆虚假的边，把本来可串行化的调度误判成有环（练习 1 就是这个 bug）。
```

:::warning[常见误区]

**误区一**："把隔离级别设成 SERIALIZABLE，性能一定崩。"
你以为串行化等于真的一条一条排队——现代数据库用 **MVCC（多版本并发控制）** 实现快照隔离：读不加锁、读的是历史版本，写才加锁。串行化级别通常再加 **SSI（可串行化快照隔离）**，只在真正会成环时才中止一个事务。**代价确实有（更多事务被中止重试），但不是"退化成单线程"。**

**误区二**："脏读、不可重复读、幻读是三个严重程度递增的 bug，所以都要消灭。"
你以为级别越高越好——它们是三种**不同的**异常，对应三种不同的业务容忍度。报表统计通常能容忍不可重复读（快照到 5 分钟前反而更好）；而对账系统必须串行化。**隔离级别是业务需求的函数，不是越高越好。**

**误区三**："REPEATABLE READ 已经能保证余额不会算错。"
你以为可重复读挡住了所有并发问题——它挡不住**丢失更新**：两个事务各自读到旧值、各自算出新值、各自写回，后写的赢。MySQL 的 REPEATABLE READ 下 `UPDATE t SET x = x + 1` 因为**当前读**（读最新已提交版本并加锁）而正确，但"先 SELECT 再 UPDATE"的写法依然会丢。处方：**把读-改-写写成一条语句，或者显式 `SELECT ... FOR UPDATE`。**

:::

## 6. 练习

**练习 1**：这段判定把本来可串行化的调度误判成有环。修到输出"是"：

```exercise
# @title: 练习：读读之间不该建边
# @check: 是
# @hint: 构成冲突要同时满足三条：不同事务、同一数据项、至少一个是写。两个读之间可以随意交换，不该建边。代码漏掉了第三条
ops = [
    (1, "W", "x"),     # T1 写 x
    (2, "R", "x"),     # T2 读 x
    (2, "R", "y"),     # T2 读 y
    (1, "R", "y"),     # T1 读 y
]
edges = set()
for i in range(len(ops)):
    for j in range(i + 1, len(ops)):
        ta, oa, da = ops[i]
        tb, ob, db = ops[j]
        if ta == tb:                       # 同一事务：内部顺序不可交换
            continue
        if da != db:                       # 不同数据项：互不影响
            continue
        edges.add((ta, tb))                # ← 问题在这：两个 R 之间也建了边

cyclic = (1, 2) in edges and (2, 1) in edges
print("否（冲突图有环）" if cyclic else "是")
```

**练习 2**：$x$ 初值 100。事务 T1 执行 $x \mathrel{-}= 30$，T2 执行 $x \mathrel{*}= 2$，每个事务都是"读-改-写"三步。写出两种串行顺序的结果，并说明为什么它们不相等——这说明了什么？

<details>
<summary>点开查看逐步解答</summary>

1. 串行 $T_1; T_2$：$(100 - 30) \times 2 = 140$；
2. 串行 $T_2; T_1$：$(100 \times 2) - 30 = 170$；
3. **两个"合法"的串行顺序结果不同**，说明"可串行化"保证的是"结果等于**某一个**串行顺序"，不是"等于你心里那个顺序"；
4. 交错调度（都先读 100，再各自算 70 与 200，最后写）的结果取决于谁后写：70 或 200，**两个都不是合法的串行结果** → 不可串行化；
5. 这揭示了一件重要的事：**可串行化保证正确性，但不保证"哪个正确"。** 当业务对顺序敏感（比如"先扣款再打折"和"先打折再扣款"差钱），必须靠应用层显式加锁或业务规则来定序——数据库管不了你的语义。

</details>

## 7. 选读：两阶段封锁与 MVCC

<details>
<summary>选读 · 保证可串行化的两条路</summary>

**两阶段封锁（2PL, Two-Phase Locking）**：每个事务分两阶段——**增长阶段**只加锁不释放，**收缩阶段**只释放不加锁。

**定理**：遵守 2PL 的调度一定是冲突可串行化的。

证明思路：设优先图有环 $T_1 \to T_2 \to \cdots \to T_n \to T_1$。每条边来自一对冲突操作，意味着后一个事务加锁时，前一个事务还持有那把锁。于是 $T_1$ 在 $T_2$ 获得某锁之前持有某锁……绕环一圈得到"$T_1$ 必须在释放锁之后再获得锁"，与两阶段性矛盾。

代价是**死锁**（第 40 课的场景在这里天天发生）与并发度下降。

**MVCC（多版本并发控制）** 走的是另一条路：每个写操作产生一个新版本，读操作按"事务开始时刻的快照"选取可见版本。于是**读不阻塞写、写不阻塞读**——这对读多写少的 OLTP 是巨大的性能红利。

但 MVCC 默认给出的是**快照隔离（Snapshot Isolation）**，它**严格弱于可串行化**：经典的"写偏斜（write skew）"在快照隔离下会发生（两个事务各自读到一致快照、各自修改不同行、合起来破坏了一个跨行约束，比如"至少有一名医生值班"被两个人同时请假破坏）。要补上这个洞，需要 SSI ——它在运行时检测"危险的环结构"并中止其中一个事务。

**一句话总结**：2PL 用"悲观地先锁"换正确性，MVCC 用"乐观地留版本"换并发度，SSI 在 MVCC 之上补回可串行化。

</details>
