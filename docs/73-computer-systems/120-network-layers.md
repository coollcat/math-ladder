# 网络分层与协议栈

## 1. 从一个场景开始

你在聊天框里敲了一个字"好"，按下发送。这一个字节要穿过你的键盘、操作系统、网卡、交换机、光纤、路由器、数据中心，落到对方屏幕上。

**一个字节的东西，线上跑的却是几十个字节。** 多出来的那些是什么？

## 2. 直觉解释

网络通信就是**寄快递**：

- 你要寄的是一支笔（应用数据）；
- 先装进小盒子、贴上面单（传输层：加端口号与序号）；
- 再装进大箱子、写上收件地址（网络层：加 IP 地址）；
- 最后套上快递袋、写上"下一站到哪里"（数据链路层：加 MAC 地址与校验）；
- 卡车拉走（物理层：变成电信号/光信号）。

每套一层，就多一张面单；对方收到后**从外往里一层层拆**。这个"装"叫**封装（encapsulation）**，拆叫**解封装**。

分层的意义在于：**每一层只关心自己那张面单上写的东西**。快递员不需要知道箱子里是笔还是书；你也不需要知道卡车走哪条高速。

## 3. 正式定义

**协议数据单元（PDU）**：每一层自己处理的那块数据，各有名字。

| OSI 层 | 名字 | PDU | 典型协议 | 干什么 |
| --- | --- | --- | --- | --- |
| 7 | 应用层 | 报文 Message | HTTP / DNS / SMTP / MQTT | 面向用户的语义 |
| 6 | 表示层 | 表示数据 | TLS / JSON / JPEG / gzip | 编码、加密、压缩 |
| 5 | 会话层 | 会话数据 | RPC / TLS 会话 | 建立、维持、断开对话 |
| 4 | 传输层 | 段 Segment / 数据报 | TCP / UDP / QUIC | 端口号、序号、重传、拥塞控制 |
| 3 | 网络层 | 包 Packet | IP / ICMP / OSPF / BGP | 跨网寻址与选路 |
| 2 | 数据链路层 | 帧 Frame | Ethernet / Wi-Fi / ARP | 相邻两点成帧、MAC、CRC |
| 1 | 物理层 | 比特 Bit | 1000BASE-T / 光纤 / 无线电 | 把 0/1 变成真实信号 |

**TCP/IP 四层模型**是实际使用的简化版：应用层 ≈ OSI 的 5–7 层，网络接口层 ≈ OSI 的 1–2 层，传输层与网际层一一对应。

**封装**：数据从上往下走，每层在前一层的结果前面（偶尔后面）加上自己的首部。

$$\text{线上字节} = L_{\text{app}} + H_{\text{TCP}} + H_{\text{IP}} + H_{\text{Eth}}$$

**真实数字**（以太网 + IPv4 + TCP 的典型值）：

| 量 | 值 | 说明 |
| --- | --- | --- |
| MTU | 1500 B | 以太网一次能承载的最大 IP 包 |
| MSS | **1460 B** | TCP 报文段里数据部分的上限 $= 1500 - 20 - 20$ |
| TCP 首部 | 20 B（含选项最多 60 B） | 源/目的端口、序号、确认号、窗口、校验和 |
| IPv4 首部 | 20 B（含选项最多 60 B） | 源/目的 IP、TTL、协议号 |
| 以太网首部 + FCS | 14 + 4 = 18 B | MAC 地址对、类型、帧校验序列 |
| 最小帧长 | 64 B | 保证冲突能被检测到（CSMA/CD 遗产） |

## 4. 分步例题

**例**：发送 100 字节的应用数据，线上总共跑多少字节？首部开销占百分之几？有效吞吐是多少？

1. 加 TCP 首部：$100 + 20 = 120$ B（段）；
2. 加 IP 首部：$120 + 20 = 140$ B（包）；
3. 加以太网首部与 FCS：$140 + 18 = 158$ B（帧）；
4. 首部开销：$\dfrac{58}{158} \approx 36.7\%$；
5. 有效吞吐：若链路带宽 100 Mbps，则真正用于传数据的只有 $100 \times 63.3\% \approx 63.3$ Mbps；
6. 极端例子：发 1 字节（比如一次按键），线上却是 $1 + 58 = 59$ B——**98% 都是包装**。这就是为什么游戏与实时通信拼命把多次输入合并成一个包。


左边是 OSI 七层，右边是 TCP/IP 四层，虚线把两组对齐。**点左边任一层**，下方显示它的 PDU 名称、典型协议与职责；最下面那条彩色长条就是封装动画：数据一层层变长。

做三个观察：

- 依次点 7→4→3→2，看每层的 PDU 名字怎么变（报文 → 段 → 包 → 帧）；
- 看读数里的"封装总长 **158 字节（首部开销 37%）**"——这就是例题的现场验算；
- 注意 TCP/IP 的"应用层"横跨了 OSI 的第 5、6、7 三层：**TLS 到底算第几层**至今有争议（它既做加密（表示层的活）又管会话（会话层的活）），这正是"参考模型"与"实用模型"的差别。

### 实验 2（python）：小包为什么这么浪费

```python title="首部开销随数据量的变化"
mss = 1460                 # TCP 最大报文段长度 = 1500(MTU) − 20(IP) − 20(TCP)
fixed = 20 + 20 + 18       # TCP + IP + 以太网的固定首部开销

print(f"{'应用数据':>10}{'线上字节':>10}{'首部占比':>10}{'有效吞吐':>10}")
for app in [1, 100, 536, mss, mss * 10]:
    total = app + fixed
    print(f"{app:>10}{total:>10}{fixed / total * 100:>9.1f}%{app / total * 100:>9.1f}%")

bw = 100.0                 # 链路带宽 100 Mbps
rate = mss / (mss + fixed) * 100
print(f"\n按 MSS 满载发送时，{bw} Mbps 链路最多跑出 {bw * rate / 100:.1f} Mbps 有效数据")
```

最后一行给出 **96.2 Mbps**——**没有一条 100 Mbps 的链路能跑满 100 Mbps 的应用数据**，那 3.8% 是协议必须付的"运费"。传 1 字节的按键时，这个数字会掉到 1.7 Mbps。

### 快问快答

```quiz
以太网 MTU 是 1500 字节，为什么 TCP 一次最多只能发 1460 字节的应用数据？
- 因为 TCP 首部至少 20 字节，IP 首部至少 20 字节，要从 MTU 里扣掉 [*]
- 因为以太网帧头占 40 字节
- 因为操作系统限制每次最多发 1460 字节
? MSS = MTU − IP 首部 − TCP 首部 = 1500 − 20 − 20 = 1460 字节。注意「以太网首部 18 字节」不在这个减法里——MTU 指的是 IP 包的上限，以太网首部在 IP 包之外，由网卡自己加。把这个减法学清楚，MTU 相关的故障（分片、PMTUD 黑洞）就都能算明白了。
```

:::warning[常见误区]

**误区一**："OSI 七层模型是网络的标准，网络就是按它建的。"
你以为它是建筑图纸——**OSI 是"参考模型"，是事后的总结；TCP/IP 是先有实现后有总结**。今天真实运行的网络里，没有哪个协议严格分成七层：TLS 横跨会话与表示，MPLS 塞在 2.5 层，还有人开玩笑说"钱和政治在第 8 层"。OSI 的真正价值是**提供一套词汇**（"这是二层问题还是三层问题"），不是规范。

**误区二**："分层只是教科书里的抽象，实际代码里看不到。"
你以为它只存在于考试——**每一层的边界都对应一个真实的可编程接口**：应用层调 `send()`，传输层给它一个 socket，网络层由内核协议栈填 IP 头，链路层由网卡驱动填 MAC 头。`tcpdump` 抓到的每一个字节，都能按这张表逐层拆开。

**误区三**："加了首部就是浪费，所以头部越短越好。"
你以为开销越小越好——首部承载的恰恰是**可靠性的全部代价**：TCP 的序号与确认号（可靠传输）、校验和（检错）、TTL（防止包在网络里无限转圈）、长度字段（拆包定位）。第 130 课会看到，为了做拥塞控制，TCP 还要再多用几个字节的窗口通告。**"开销"换的是"可诊断性与可扩展性"。**

:::

## 6. 练习

**练习 1**：这段代码算首部开销，给出 58.0，正确答案是 36.7。修到输出 `36.7`：

```exercise
# @title: 练习：首部开销的分母用错了
# @check: 36.7
# @hint: 首部开销 = 首部字节 ÷ 封装后的总字节（158 B）。代码拿应用数据 100 B 当分母了。结果保留一位小数
app = 100                 # 应用数据 100 字节
tcp = 20                  # TCP 首部
ip = 20                   # IPv4 首部
eth = 18                  # 以太网首部 + FCS
headers = tcp + ip + eth
total = app + headers
overhead = headers / app * 100     # ← 问题在这：分母应该是封装后的总长度 total
print(f"{overhead:.1f}")
```

**练习 2**：一条横跨大洋的链路，带宽 1 Gbps，单向时延 75 ms（即 RTT 150 ms）。若发送窗口受 MSS 限制为 64 KB，这条链路最多能跑多快？要提高吞吐该怎么办？

<details>
<summary>点开查看逐步解答</summary>

1. 一个 RTT 内最多发出一个发送窗口的数据：$64\ \text{KB} = 65536\ \text{B} = 524288\ \text{bit}$；
2. 吞吐上限 $= \dfrac{524288\ \text{bit}}{0.15\ \text{s}} \approx 3.5\ \text{Mbps}$；
3. 而链路带宽是 1 Gbps —— **利用率只有 0.35%**，99.6% 的带宽在"等回信"中空转；
4. 瓶颈是**带宽时延积（BDP）**：$1\ \text{Gbps} \times 0.15\ \text{s} = 150\ \text{Mbit} = 18.75\ \text{MB}$，发送窗口必须至少这么大才能填满链路；
5. 处方：启用**窗口扩大选项**（TCP window scaling，把窗口从 64 KB 提到 MB 级）。这也是为什么高带宽长时延链路（"长肥管道"）必须专门调参——**第 130 课要讲的拥塞控制，本质上就是在动态寻找这个窗口该多大。**

</details>

## 7. 选读：端到端原则

<details>
<summary>选读 · 功能该放在哪一层</summary>

1984 年，Saltzer、Reed 与 Clark 提出了网络设计中最重要的一条经验法则：

> **端到端原则**：只有当功能在**通信端点**（应用层）实现才能完全正确时，就应该把它放在端点；放在低层实现可以是性能优化，但不能是正确性的唯一保障。

经典例子是**可靠传输**：无论链路层的 CRC 校验做得多好，数据仍可能在路由器里被丢弃、在端系统缓冲区里被破坏。所以"端到端的校验和 + 重传"必须由传输层（TCP）来做——链路层的可靠传输（如 Wi-Fi 的重传）只是**减少重传次数**的优化，不能替代 TCP。

反过来的例子是**拥塞控制**：它必须在网络深处（路由器）与端点（TCP）配合完成，因为只有端点知道自己的发送速率，只有路由器知道队列有多长。

这条原则解释了互联网的很多"为什么"：

- 为什么 IP 层这么简单（best-effort，尽力而为）：把复杂留给端点，网络核心才能快速演进；
- 为什么 QUIC 把可靠传输放到了**应用层之上**（跑在 UDP 上）：因为内核里的 TCP 已经改不动了（中间设备会检查/篡改 TCP 头），要创新只能绕开。

**一句话**：分层不是随便切的，每一层的边界都对应"这个功能该由谁负责到底"的判断。

</details>
